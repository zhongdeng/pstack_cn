# TDD 缺陷修复

在用一条清晰、廉价的测试路径修复缺陷时，先让坏掉的行为变得可执行，再改生产代码。目标是一个聚焦的回归测试，修复前失败，修复后通过。

当测试不切实际时，不要硬加测试。如果现有的测试需要大范围的测试夹具搭建、脆弱的 mock、缓慢的端到端基础设施、仅生产环境才有的状态、含糊的复现步骤，或大量无关的测试夹具搅动，就跳过新增测试，改用最接近的有用验证。

## 流程

1. **理解这个缺陷。** 确定预期行为、当前行为、受影响的路径，以及最小的可观察复现。
2. **选择最窄的可执行检查。** 优先用那条代码路径上已经在用的、最接近的单元、组件、集成或回归测试。如果看不出实用的测试路径，不要为了满足这套流程而从零造一个。
3. **先写失败的测试。** 加上本可以抓住这个缺陷的、最小的聚焦测试。测试应该编码预期行为，而不是照搬当前实现。
4. **在修复之前运行新测试。** 确认它因预期的原因而失败。如果它通过了，或因无关的原因失败，就在改实现之前先改正测试或复现。
5. **修复这个缺陷。** 做满足预期行为的最小生产代码改动，同时保住邻近的约定。
6. **重新运行回归测试。** 确认测试现在通过。

## 如果失败测试不切实际

改用最接近的可执行回归检查：有针对性的脚本、手动复现命令、浏览器自动化、快照对比、日志断言，或聚焦的集成检查。

宁可不加新测试，也不要一个坏测试。坏测试是这样一种：主要在测 mock、编码了当前实现细节、依赖时序或无关的全局状态、为一个小修复需要昂贵的基础设施，或者在证明修复之后马上就会被删掉。

## 护栏

- 不要只为了迎合一个错误的实现而改测试。
- 不要削弱已有断言，除非预期行为确实变了，而且原因清楚。
- 让回归测试聚焦在这个缺陷上。避免大范围的夹具变动或无关的覆盖扩张。
- 如果缺陷是不稳定的，就在可能的地方让测试确定，并记下正在锁定的那个信号。
- 如果缺陷暴露出更广的一类失败，先落地聚焦的回归路径，再考虑额外的同类覆盖。

## 最终回复

报告证据，而不只是结果：

- 点明修复前失败的测试或可执行检查，以及它产生的失败。
- 点明修复后通过的测试运行，以及做过的任何邻近验证。
- 如果无法展示修复前失败的证据，说明为什么，并描述改用的最接近的回归检查。
