# TDD 修 bug

当修一个 bug 有清晰、成本低的测试路径时，先让坏掉的行为变成可执行的，再改生产代码。目标是写一个聚焦的回归测试，修复前失败，修复后通过。

如果测试不现实，就不要硬写。如果可用的测试需要大范围搭测试框架、脆弱的 mock、缓慢的端到端基础设施、只在生产环境才有的状态、含糊的复现步骤，或者大量无关的 fixture 改动，那就跳过新增测试，改用最接近的有用验证方式。

## 工作流程

1. **理解 bug。** 弄清预期行为、当前行为、受影响的路径，以及最小的可观察复现。
2. **选最窄的可执行检查。** 优先用这条代码路径上已有的、最接近的单元测试、组件测试、集成测试或回归测试。如果没有明显的可行测试路径，不要为了走流程而从零造一个。
3. **先写失败测试。** 加上最小的、聚焦的、本来能抓住这个 bug 的测试。测试应该表达预期行为，而不是照抄当前实现。
4. **修之前先跑新测试。** 确认它是因为预期的原因失败。如果它通过了，或者因为无关原因失败，先修正测试或复现，再改实现。
5. **修 bug。** 做满足预期行为的最小生产代码改动，同时保住附近的契约。
6. **重跑回归测试。** 确认测试现在通过。

## 如果失败测试不现实

改用最接近的可执行回归检查：一个针对性的脚本、手动复现命令、浏览器自动化、快照对比、日志断言，或者聚焦的集成检查。

宁可没有新测试，也不要坏测试。坏测试是指：主要在测 mock、把当前实现细节写死、依赖时序或无关的全局状态、为一个小修复需要昂贵的基础设施，或者刚证明完修复就该被删掉。

## 护栏

- 不要为了让测试匹配一个错误的实现而改测试。
- 不要削弱已有的断言，除非预期行为确实变了，而且原因清楚。
- 让回归测试聚焦在这个 bug 上。避免大范围 fixture 改动或无关的覆盖率扩张。
- 如果 bug 是 flaky 的，尽量让测试确定化，并记录下被锁定的信号。
- 如果这个 bug 暴露出更广的一类失败，先落地聚焦的回归路径，再考虑补同类的其他覆盖。

## 最终回复

报告证据，而不只是结果：

- 说出修复前失败的那个测试或可执行检查，以及它产生的失败。
- 说出修复后通过的那次测试运行，以及做过的附近验证。
- 如果无法展示修复前失败的证据，说明原因，并描述改用过的、最接近的回归检查。
