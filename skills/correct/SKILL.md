# Correct

操作者一直在为同样的错误纠正这个仓库里的智能体。改仓库，让下一个智能体犯不了这些错。

假设每个贡献者都是智能体：它只看自己打开的文件，照抄最近的例子，走能编译的最短路径。把仓库设计成从一个文件看是对的改动，对整个仓库也是对的。

## 找出错误类别

先读最近的提交、回滚、评论、智能体指令文件，以及解释 workaround 的注释。把错误归成类别。一个类别发生过两次才算数。

## 在能起作用的最高层级上修每个类别

1. **用架构消灭它。** 每份状态只有一个所有者，每个任务只有一种受支持的做法。把内部实现藏起来，让错误的 import 直接失败。把手工同步的列表换成单一事实来源。删掉智能体会照抄的旧做法和死代码。
2. **用类型强制它，让坏状态写不出来。** 如果坏代码还能编译，就加一条 lint 或 CI 检查，让报错信息里写明该用哪个文件、类型或函数。如果这种写法已经很常见，只在改动新增了更多时才失败。
3. **测试行为。** 修掉或删掉这样的测试：它检查的行为坏了却仍然通过，或者只有内部实现变了它就失败。
4. **文档或智能体规则放最后写，只写需要判断的地方。** 智能体跳过它们不会有任何东西失败。

## 修好并证明

然后现在就修最常见的几个类别，每个类别一个提交。每个新检查都要用一个真实发生过的错误来证明它会失败。本地和 CI 跑同一条命令。例外写在出问题的那一行上，附上原因、过期日期和一个人的批准。

## 维护规则表

最后，在智能体指令文件里维护一张表，把每条规则和强制它的东西配对。操作者纠正你时，修掉这个错误并加上这条规则。如果规则本来就在、却没有任何东西强制它，那就是重复，在同一次改动里按最高层级修掉。一条规则对应的错误不可能再发生之后，就把它删掉。

**回复：** 每个类别附上证据、你选的层级，以及为什么更高的层级没起作用。
