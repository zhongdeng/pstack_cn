# 纠正

操作者一直在这个仓库里为同样的错误纠正 agent。改仓库，让下一个 agent 做不出这些错。

假定每个贡献者都是一个 agent：它只看自己打开的文件，抄最近的例子，走能编译通过的最短路径。把仓库设计成：从一个文件看起来对的改动，对整个仓库也是对的。

## 找出错误的类别

先读最近的 commit、回退、评审评论、agent 指示文件，以及解释变通的注释。把错误分成类。一类要发生过两次才算数。

## 在管用的最高一层修每一类

1. **用架构把它消掉。** 每一份状态一个所有者，每一项任务只留一种支持的做法。藏起内部实现，让错误的导入失败。用单一事实来源替换手工同步的清单。删掉 agent 会去抄的旧做法和死代码。
2. **用类型强制它，让坏状态写不出来。** 如果坏代码仍然能编译，就加一条 lint 或 CI 检查，它的报错点名应该改用的文件、类型或函数。如果这种模式已经很常见，就只在改动又增加更多时才失败。
3. **测试行为。** 修掉或删掉这样的测试：它检查的行为坏了它仍然通过，或者只改了内部实现它就失败。
4. **文档或 agent 规则最后写，只留给需要判断的决定。** agent 跳过它们时，没有任何东西会失败。

## 修好并证明

然后现在就修最常出现的几类，每一类一个 commit。证明每条新检查会在一个真实的历史错误上失败。同一条命令在本地和 CI 里都跑。例外标在出问题的那一行上，附上理由、到期日，以及一个人的批准。

## 维护规则表

最后，在 agent 指示文件里维护一张表，把每条规则和强制它的东西配成对。操作者纠正你时，修掉这个错误，并把规则加上。如果规则已经在那儿、却没有东西强制它，那就是一次重复，所以在同一次改动里把它修到最高一层。一旦对应的错误不可能再发生，就删掉这条规则。

**回复：** 每一类，附上证据、你选的层级，以及为什么更高的层级行不通。
