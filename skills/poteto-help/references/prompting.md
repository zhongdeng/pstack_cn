# 写好提示词

一条提示词陈述意图和完成的检查。步骤由行动手册提供，所以几句白话胜过一份规格。

## 写进去

- 目标。说出什么是错的，或用户想要什么。
- 完成检查。它能通过或失败。「把它变得更好」和一段时长都不是检查。
- 要展示的证明。要求真实的命令输出、一段流程的视频、存下的值，或一个前后数字。
- 用户已经知道的。一个症状、一个复现步骤、一份日志或一个链接，能省掉代理一次搜索。
- 真正的约束。「先复现」、「先不要改任何代码」、「行为零变化」和「继续之前让我审查」各自会改变代理做什么。

## 留在外面

- 方法。说出要达成什么，给代理留下找到更好办法的空间。
- 一份技能或步骤的列表。手写的顺序会丢掉或重排行动手册所保留的步骤。只有为了覆盖某一个选择时才点名一项技能。
- 用户对原因的理论，直到代理把问题复述出来。一个说出来的猜测会收窄搜索。

## 先加载上下文

- 对于一份嘈杂的报告，请代理在做任何其他事之前，用它自己的话、用白话把底层问题复述出来。误读会在任何代码存在之前显出来。
- 在一段新对话里，用 `/recall` 这个话题上更早的工作。旧对话里有新代理所缺少的上下文。
- 在改动不熟悉的代码之前，用 `/how` 问机制，用 `/why` 问原因。一个没有追踪清楚的模型的代理，会在第一个说得通的位置上修症状。
- 请 `/teach` 为一个选择摆出理由，例如「说服我它修的是原因而不是症状」。一份理由比一份摘要更容易核对。

## 先设计，再计划

- 绝不要接受第一个设计。要求几个选项的原型，界面要有截图或视频，并根据证据来挑。
- 让原型来回答未决问题。不要对抗式地审查一份抽象计划，因为审查者会发明出从不发生的风险。
- 对于共享的包或 API，先要 README 或一篇教程，再回到代码。文档变成代理用来核对自己的目标。
- 只在设计定下来之后才要计划。计划的每一步都以一个检查结束。

## 短跟进

- 一旦对话里已经有了这项任务，「做吧」、「继续」和「一直做到完」就是完整的提示词。
- 话题变了就以「新任务」开头。否则模式会把这条消息当成下一步。

## 离开之前

- 说「我要去睡觉了」或「我先离开一下」，这样代理就不再提问。
- 把完成写成每次迭代都能跑的检查，并把那个谓词交给 `/loop`。
- 要求一个从指定基线拉出的新工作树。
- 预先回答代理会停下来问的事，例如「提交之前不要问我」。
- 要求一份以后可以审计的决策日志。
- 给一个出口：「如果你在几个小时后真的卡住了，就停下并写明为什么」。

## 用一行来驾驭

- 重述目标：「我说的目标是复现。我还没有要求修复。」
- 点名原则：「应用 prove it works。给我看真实输出，不要构建日志。」
- 原则名字能起作用，是因为代理已经读过那条规则。它的回复会点明这条规则改变了的那个决定。
