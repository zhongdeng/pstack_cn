# 把提示词写清楚

提示词说清意图和完成检查。步骤由作战手册提供，所以几句大白话胜过一份规格说明。

## 要写进去

- 目标。说清哪里不对，或者用户想要什么。
- 完成检查。它得能通过或失败。“做得更好一点”和一段时长都不是检查。
- 要展示的证据。要真实的命令输出、流程录屏、存下来的值，或者前后对比的数字。
- 用户已经知道的东西。一个症状、一个复现步骤、一段日志或一个链接，能省掉智能体一次搜索。
- 真实的约束。“repro first”、“don't change any code yet”、“zero behavior change”、“let me review before proceeding”，每一条都会改变智能体的做法。

## 要省掉

- 怎么做。说清要达到什么，给智能体留出找更好办法的空间。
- 技能或步骤清单。手写的顺序会丢掉或打乱作战手册里的步骤。只有要覆盖某个选择时，才点名一个技能。
- 用户对原因的理论，等智能体复述完问题再说。说出猜测会收窄搜索范围。

## 先加载上下文

- 面对一份混乱的报告，先让智能体用自己的话、用大白话复述底层问题，再做别的。理解错了，在写出任何代码之前就会暴露。
- 在新会话里，用 `/recall` 调出之前在这个话题上的工作。旧会话里有新智能体缺的上下文。
- 改动不熟悉的代码之前，用 `/how` 问清机制，用 `/why` 问清原因。没有追踪过模型的智能体，会在第一个看起来合理的地方修症状。
- 用 `/teach` 让智能体为某个选择立论，比如“说服我它修的是原因而不是症状”。立论比摘要更容易检查。

## 先设计，再计划

- 永远不要拿第一个设计。要几个方案的雏形，UI 就配截图或视频，从证据里挑。
- 让雏形回答悬而未决的问题。不要对抗式地评审一份抽象计划，因为评审者会凭空造出根本不会发生的风险。
- 对共享包或 API，先要 README 或教程，再倒推回代码。文档就成了智能体对照自查的目标。
- 设计定下来之后再要计划。计划的每一步都以一个检查收尾。

## 跟进要短

- “do it”、“continue”、“keep going until done”，只要会话里已经有任务，这些就是完整的提示词。
- 话题变了，就用“new task”开头。否则模式会把这条消息当成下一步。

## 离开之前

- 说“im going to bed”或“im stepping away”，智能体就不会再追问。
- 把完成写成每轮迭代都能跑的检查，把这个判定条件交给 `/loop`。
- 要一个基于指定基线的新 worktree。
- 预先回答智能体会停下来问的事，比如“don't ask me before committing”。
- 要一份决策日志，方便以后审计。
- 给一个退出条件：“if you're truly stuck after a few hours, stop and write up why”。

## 一句话纠偏

- 复述目标：“i said the goal is to repro. i did not ask for a fix yet.”
- 点名原则：“apply prove it works. show me the real output, not the build log.”
- 原则的名字管用，是因为智能体已经读过那条规则。它的回复会点出这条规则改变了哪个决定。
