# 创建一个验证 skill

每个正经项目都需要一种脚本化的办法来驱动真实应用并证明行为：把它启动起来，像用户那样走一遍一个功能，并捕获证据。这个 skill 把那套东西生成成一个项目本地的 skill（`.cursor/skills/verify-<app>/`），按这个仓库来裁。生成器的产出是写给下一个 agent 的，不是写给人的：一个从没见过这个应用的 agent，会在任务做到一半时毫无上下文地读它。

## 1. 访谈仓库，而不是用户

从代码库里回答这些问题，只有你观察不到的才去问用户：

- **交互面：** 用户实际碰到的是什么？Web UI、CLI/TUI、桌面应用、API、移动应用，还是库？一个仓库可以有好几样；选主要的那个，其余的记一笔。
- **运行：** 应用在本地怎么启动？优先用仓库自己文档里的开发命令（package 脚本、Makefile、README 快速上手）。记下端口、环境变量、种子数据、认证。
- **驱动：** agent 怎样以编程方式跟它交互？已有的测试装置优先——Playwright/Cypress 规格、expect 脚本、PTY 辅助、可以 curl 的端点、调试端口。然后才选一套通用配方：Web 和 Electron 用浏览器/CDP，CLI/TUI 用 tmux/PTY 测试装置，服务用纯 HTTP。
- **观察：** 能捕获什么证据？截图、终端记录、响应体、日志、退出码、数据库状态。
- **隔离：** 两个实例能不能并排跑（端口、数据目录、配置档）？如果不能，就在生成的 skill 里写明：拒绝去双重驱动一个共享实例，好过弄坏用户的会话。

如果这份检出按原样构建不了或启动不了，先把那个修好（或精确地报告它），再生成；对着一个坏底座写出来的 skill，教的是错的步骤。当一个不相干的缺失资产挡住启动（API 从不提供的静态目录、一份示例配置），生成的 skill 可以创建它，明确标成验证脚手架，并在清理时删掉。

## 2. 生成 skill

写 `.cursor/skills/verify-<app>/SKILL.md`，带上 YAML frontmatter（`name: verify-<app>`，以及一段 `description`，点名这个应用、这个交互面，以及什么时候该伸手去拿它——没有 frontmatter，这个 skill 永远不会注册），再加上这些节，每一节都扎在访谈实际发现的东西上（不留占位符）：

- **启动：** 为验证启动应用的确切命令，以及怎么判断它就绪了（一行日志、一个提示符）。启动必须能从空的数据目录到达可用状态，包括任何迁移和种子数据。就绪意味着能用，不只是有个进程在应答。数据库健康检查可以在初始化脚本还在跑的时候就通过。包括拆卸。短命的 CLI 或 TUI 没有要保活的服务器：启动意味着把二进制构建一次（或装好依赖），然后每次驱动都在它自己隔离的 PTY 或 tmux 会话里开始。
- **诊断：** 一项只读检查，回答「这个实例值得驱动吗？」——进程在、版本/构建对、端口是我们的、认证有效。任何东西看起来不对时，agent 先跑这个。
- **驱动：** 测试装置的配方，用这个仓库里真实的选择器/命令，不要用例子。优先用稳定的把手（ARIA 标签、data 属性、提示字符串、路由路径），而不是坐标和 Tab 顺序。
- **证据：** 一份证明要捕获什么、放到哪里。写明证明标准：走真实的用户路径，不要走内部 setter 或仅供测试的端点；捕获动作和随之而来的状态，不只是最终画面；在可见内容之外，核对其副作用（写入的文件、插入的行、发出的消息）；只有生产边界已经把外部系统隔离开的地方才用 mock。安全路径是 dry-run 或测试模式时，用观察（文件、网络、git ref）去核实它实际跳过了什么，不要相信它的名字：有些 dry-run 仍然会碰网络或打开浏览器。
- **清理：** 怎么拆掉这次运行创建的实例。永远不要按进程名杀；杀你启动的那个。清理去掉的是实例和临时状态，永远不是证据：证明产物在拆卸之后仍然留着，放在 skill 点名的位置。
- **辅助脚本：** skill 带上的任何脚本都是可执行的，并且 skill 正文里展示了怎么调用它。读者还得反向工程才能用的辅助脚本，不算辅助脚本。

## 3. 种下功能地图

创建 `.cursor/skills/verify-<app>/features/README.md`，再加上你能识别出的每个面向用户的功能各一个文件（一开始瞄准最重要的 3 到 5 个，从路由、命令、菜单或文档里来）。形态遵循 [`references/feature-map-example/`](references/feature-map-example/)，一份 README 索引，每个功能一个文件。每个文件从用户的视角回答：这个功能是什么、怎么到达它、怎么用测试装置驱动它，以及什么样的可观察终态证明它能工作。四个 H2 是 `Sub-features`、`How to get to it (user POV)`、`Driving it with <harness>` 和 `Gotchas`。如果种子数据缺了某段旅程需要的前置条件，这段旅程就报告失败，原因写进该功能的 `Gotchas`。永远不要为了让旅程通过而把它放宽。这张地图是仓库维护中的验证来源；地图还列了其他入口时，只驱动一个顺手入口的证明是不完整的。

## 4. 移交之前先证明生成的 skill

把它自己的指示端到端走一遍：启动、诊断、驱动一个已映射的功能（一个就够；地图的存在是为了让以后的运行覆盖其余的）、捕获证据、清理。清理之后，确认证据仍然在点名的位置——把证明吃掉的清理，这一步就算失败。修掉失败的地方，每次失败的迭代之后也要跑生成的清理，免得坏掉的尝试把进程和端口丢在那儿。从没执行过的生成 skill 是草稿，不是交付物。如果你是在真实目标的替身上证明的（用容器代替一台全新的虚拟机，用本地技术栈代替远程的），列出替身做了、而目标不会做的每一步搭建。这些步骤在真实目标上的一次运行覆盖它们之前，都算未验证。

## 5. 给出维护循环

让用户去用 `/maintain-verification-skill`，在应用变化时让地图保持诚实。只有他们问了才建议节奏。
