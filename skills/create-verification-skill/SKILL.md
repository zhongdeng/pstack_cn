# 创建验证技能

每个正经项目都需要一种脚本化的方式来驱动真实应用并证明行为：把它启动起来，像用户那样走一遍某个功能，再把证据留下来。这个技能会把这件事生成为一个项目本地的技能（`.cursor/skills/verify-<app>/`），针对这个仓库量身定制。你写的是给下一个智能体看的生成结果，不是给人看的：它会在任务进行中被一个从没见过这个应用的智能体冷读。

## 1. 访谈仓库，而不是访谈用户

从代码库里找答案，只问用户你观察不到的东西：

- **界面：** 用户实际接触的是什么？Web UI、CLI/TUI、桌面应用、API、移动应用、还是一个库？一个仓库可能有好几种，挑出主要的那个，其余的记下来。
- **运行：** 应用在本地怎么启动？优先用仓库自己文档里的开发命令（package scripts、Makefile、README 快速上手）。记下端口、环境变量、种子数据、认证。
- **驱动：** 智能体怎么用程序的方式和它交互？先找现成的测试装置：Playwright/Cypress 用例、expect 脚本、PTY 辅助工具、能用 curl 调的接口、调试端口。实在没有，再选通用方案：Web 和 Electron 用浏览器/CDP，CLI/TUI 用 tmux/PTY 装置，服务用纯 HTTP。
- **观察：** 能抓到什么证据？截图、终端记录、响应体、日志、退出码、数据库状态。
- **隔离：** 两个实例能并排跑吗（端口、数据目录、profile）？不能的话，就在生成的技能里写清楚：拒绝同时驱动一个共享实例，好过弄坏用户的会话。

如果检出后原样构建不起来或启动不了，先把它修好（或者精确地报告出来）再生成；对着一个坏掉的基线写出来的技能会教出错误的步骤。当某个无关的缺失资源挡住了启动（一个 API 根本不提供的静态目录、一份示例配置），生成的技能可以把它创建出来，明确标注为验证脚手架，并在清理时删掉。

## 2. 生成技能

写 `.cursor/skills/verify-<app>/SKILL.md`，带 YAML frontmatter（`name: verify-<app>`，以及一个 `description`，写明应用名、界面类型、什么时候该用它。没有 frontmatter 技能根本不会注册），并包含下面这些小节，每一节都要落在访谈实际找到的东西上（不留占位符）：

- **启动：** 为验证启动应用的确切命令，以及怎么判断它已经就绪（一行日志、一个提示符）。启动必须能从空数据目录到达可用状态，包括所有迁移和种子数据。就绪意味着可用，而不只是有个进程在应答。数据库健康检查可能已经通过，而它的初始化脚本还在跑。要包含拆除步骤。对于短命的 CLI 或 TUI，没有需要一直活着的服务器：启动指的是把二进制构建一次（或装一次依赖），然后每次驱动都在自己独立的 PTY 或 tmux 会话里开始。
- **体检：** 一个只读检查，回答“这个实例值不值得驱动？”：进程在跑、版本/构建对得上、端口是我们自己的、认证有效。只要哪里看着不对，智能体就先跑这个。
- **驱动：** 测试装置的配方，用这个仓库里真实的 selector/命令，不要用示例。优先用稳定的句柄（ARIA 标签、data 属性、提示符字符串、路由路径），而不是坐标和 Tab 顺序。
- **证据：** 一次证明要抓什么、放在哪里。写清证明标准：走真实的用户路径，而不是内部 setter 或只给测试用的接口；抓动作和动作之后的状态，而不只是最后那一屏；除了看得见的东西，还要验证副作用（写出的文件、插入的行、发出的消息）；只有在生产边界已经隔离了外部系统的地方才用 mock。当安全路径是 dry-run 或测试模式时，要通过观察（文件、网络、git refs）来验证它实际跳过了什么，而不是相信它的名字：有些 dry-run 照样会碰网络或者打开浏览器。
- **清理：** 怎么拆掉这次运行创建的实例。绝不按进程名杀进程；只杀你自己启动的。清理删的是实例和临时状态，绝不删证据：证明产物要在拆除之后存活，放在技能里写明的某个位置。
- **辅助脚本：** 技能附带的任何脚本都必须可执行，并且它的调用方式要写在技能正文里。一个需要读者自己去逆向的辅助脚本不叫辅助脚本。

## 3. 播种功能地图

创建 `.cursor/skills/verify-<app>/features/README.md`，再为你能识别出的每个面向用户的功能建一个文件（一开始瞄准前 3-5 个，从路由、命令、菜单或文档里找）。按 [`references/feature-map-example/`](references/feature-map-example/) 里的形状来，一个 README 索引加每个功能一个文件。每个文件都从用户视角回答：这个功能是什么、怎么到达它、怎么用测试装置驱动它、什么可观察的最终状态能证明它工作。四个 H2 是 `Sub-features`、`How to get to it (user POV)`、`Driving it with <harness>` 和 `Gotchas`。如果种子数据缺少某条旅程需要的前置条件，这条旅程就报失败，原因写进那个功能的 `Gotchas`。绝不要为了让旅程通过而削弱它。地图是这个仓库维护的验证来源；当地图列出了多个入口时，只驱动一个方便入口的证明是不完整的。

## 4. 交付前先证明生成的技能

把它的说明从头到尾跑一遍：启动、体检、驱动地图上的一个功能（一个就够；地图存在就是为了让后续运行覆盖其余的）、抓证据、清理。清理之后，确认证据还在写明的那个位置：一个把证明吃掉的清理会让这一步失败。修掉失败的地方，而且每次失败的迭代之后也要跑一遍生成的清理，免得坏掉的尝试留下进程和端口。一个从没被执行过的生成技能是草稿，不是交付物。如果你是在真实目标的替身上证明的（用容器代替全新的 VM，用本地栈代替远程栈），把替身做了而真实目标不会做的每一个搭建步骤都列出来。这些步骤在真实目标上跑过之前都算未验证。

## 5. 提供维护循环

把用户引向 `/maintain-verification-skill`，让地图在应用变化时保持诚实。只有他们问了，才建议一个节奏。
