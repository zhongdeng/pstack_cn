# Notes 验证地图

这个目录是验证 Notes 用户可见行为的维护来源。先读索引，再驱动应用，然后用对应的功能文件当操作配方。

## 基线前置条件

- 在 `http://127.0.0.1:4173` 启动 Notes，使用一次性的数据目录。
- 设置 `NOTES_DATA_DIR=/tmp/notes-verify-$RUN_ID`，让并发运行不共享状态。
- 预置标题为 `Quarterly plan` 和 `Grocery list` 的笔记。
- 把 `control-notes` 和 `notes` CLI 放到 `PATH` 上。
- 运行 `control-notes doctor`，要求 URL、数据目录和构建版本都符合预期。
- 绝不要驱动不是本次验证运行启动的实例。

## 驱动约定

- 除非前置条件另有说明，每个配方都从基线状态开始。
- 优先用 ARIA 角色和可访问名称，而不是 CSS 选择器或 DOM 位置。
- 把每条命令都当作字面量。引号里的名称和 flag 保持不变。
- 通过 `control-notes browser` 执行浏览器操作。
- 通过 `control-notes cli -- <command>` 执行终端操作。
- 变更之后恢复预置数据。清理时不要删掉证据产物。

## 证据与跳过报告

- 记录用户操作和操作后的状态，而不只是最终画面。
- UI 证据包括 ARIA 快照和一张能看到应用标识的截图。
- CLI 证据包括命令、stdout、stderr 和退出码。
- 变更证据包括对存储值的只读二次查看。
- 每份产物都记录所用的功能 ID 和入口点。
- 报告无法到达的路径时，附上尝试过的命令和未满足的前置条件。
- 不要把跳过的入口点报告成通过另一条路径验证过。

## 功能文件约定

每个功能文件以 H1 标题开头，加一段描述用户可见行为的文字。然后严格按以下顺序使用四个 H2 小节。

1. `Sub-features` 列出短 ID，每个行为一行。
2. `How to get to it (user POV)` 列出所有用户入口点。
3. `Driving it with <harness>` 以 `Preconditions:` 开头，用带标签的条目把每个用户操作与一条确切命令和可观察结果配对。
4. `Gotchas` 列出可能浪费或作废一次验证运行的坑。

地图里不要写实现细节。只写用户路径、稳定句柄、必需状态、命令和可观察证据。

## 功能

- [创建笔记](./create-note.md) 覆盖浏览器和 CLI 的创建、取消、持久化和清理。
- [搜索笔记](./search.md) 覆盖工具栏、键盘和 CLI 搜索，包括匹配、空结果和清除状态。
