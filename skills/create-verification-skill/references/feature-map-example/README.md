# Notes 验证地图

这个目录是验证 Notes 面向用户行为的维护来源。驱动应用之前先读索引，然后把对应的功能文件当作配方。

## 基线前置条件

- 在 `http://127.0.0.1:4173` 启动 Notes，使用一次性的数据目录。
- 设置 `NOTES_DATA_DIR=/tmp/notes-verify-$RUN_ID`，让并发运行不共享状态。
- 种下标题为 `Quarterly plan` 和 `Grocery list` 的笔记。
- 把 `control-notes` 和 `notes` CLI 放到 `PATH` 上。
- 跑 `control-notes doctor`，并要求 URL、数据目录和构建修订号都是预期的。
- 永远不要驱动不是这次验证运行启动的实例。

## 驱动约定

- 每份配方都从基线状态开始，除非它的前置条件另有说明。
- 优先用 ARIA role 和可访问名称，而不是 CSS 选择器或 DOM 位置。
- 每条命令都按字面对待。引号里的名字和旗标保持不变。
- 浏览器动作通过 `control-notes browser` 来跑。
- 终端动作通过 `control-notes cli -- <command>` 来跑。
- 变更之后恢复种下的数据。清理时不要去掉证明产物。

## 证明与跳过报告

- 捕获用户动作和随之而来的状态，不只是最终画面。
- UI 证明包括一份 ARIA 快照，以及一张能看见应用身份的截图。
- CLI 证明包括命令、stdout、stderr 和退出码。
- 变更证明包括对存储值的第二个只读视图。
- 每份产物都记下用的功能 ID 和入口。
- 报告走不到的路径时，附上尝试过的命令和没满足的前置条件。
- 不要把跳过的入口报告成经由另一条路径已验证。

## 功能入口契约

每个功能文件以一个 H1 标题开头，加一段描述用户可见行为的话。然后按这个顺序恰好使用四个 H2 节。

1. `Sub-features` 列出短 ID，每种行为一行。
2. `How to get to it (user POV)` 列出每一个用户入口。
3. `Driving it with <harness>` 以 `Preconditions:` 开头，并用带标签的条目，把每个用户动作配上一条确切命令和可观察的结果。
4. `Gotchas` 列出会浪费或作废一次验证运行的陷阱。

实现细节不要写进地图。只点名用户路径、稳定把手、必需状态、命令和可观察的证明。

## 功能

- [创建笔记](./create-note.md) 覆盖浏览器和 CLI 的创建、取消、持久化，以及清理。
- [搜索笔记](./search.md) 覆盖工具栏、键盘和 CLI 搜索，含匹配、空结果和清除这几种状态。
