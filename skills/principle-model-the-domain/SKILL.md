# 为领域建模

把真实领域编码进数据结构，而不是把它撒在条件分支里。一个匹配领域的结构让非法状态无法表示，并删掉分支。在写的时候选择它很便宜。事后再补，读起来像一次重构，于是就被推迟。

可以伸手去拿：

- 用状态机，而不是散落的布尔、阶段或生命周期检查。
- 用有类型的模型，而不是松散参数或重复的形状假设。
- 用映射、注册表、查找表或可区分联合，而不是摊在多个文件里的分支。
- 用 reducer 或命令/事件模型，而不是临时的状态变更。
- 用围绕一整块领域知识组织的模块，而不是 load、validate、transform、save 这样的序列。执行顺序不是所有权。
- 用一块小的模块边界，把重复的行为、所有权或不变量收拢起来。
- 在访问模式需要时，用队列、缓存、索引、图、树或规范化集合。
- 任何其他合适的结构。当没有一个合适时，先弄清代码绝不能允许什么、数据如何被读取，再找到恰好编码这些的结构。

不要硬套抽象。如果当前形状已经清楚、局部、而且不太会长大，就用无聊的代码。对那种只增加间接、却不去掉分支、重复规则、非法状态或生命周期风险的抽象，保持怀疑。

你跳过了这条原则的迹象是：一个新功能让现有的 if/else 链又多出一个分支，或第二个必须与第一个保持同步的布尔。时间分解是另一个迹象。以阶段命名的模块会在各步骤之间重复同一套领域规则。
