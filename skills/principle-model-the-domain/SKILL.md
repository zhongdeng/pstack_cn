# 为领域建模

把真实的领域编码进一个数据结构，而不是把它散落在各种条件判断里。一个贴合领域的结构能让非法状态无法表示，还能删掉分支。写代码时就选好它，成本很低。事后再补回来，看起来就像一次重构，于是被一直拖着。

优先考虑：

- 用状态机代替散落的布尔值、阶段或生命周期检查。
- 用带类型的模型代替松散的参数或反复出现的形状假设。
- 用 map、注册表、查找表或可辨识联合代替散落在多个文件里的分支。
- 用 reducer 或命令/事件模型代替随手改状态。
- 用一个围绕单块领域知识组织的模块，代替 load、validate、transform、save 这样的顺序。执行顺序不等于归属。
- 用一个小模块边界把重复的行为、归属或不变量收拢起来。
- 在访问模式需要时，用队列、缓存、索引、图、树或规范化集合。
- 任何其他合适的结构。都不合适时，先想清楚代码绝不能允许什么、数据会怎么被读取，再找出恰好能编码这两点的结构。

不要硬套抽象。如果当前的形状已经清晰、局部、而且不太可能增长，就选无聊的代码。对一个只增加间接层、却不消除分支、重复规则、非法状态或生命周期风险的抽象，要保持怀疑。

你跳过这一步的信号是：一个新功能让已有的 if/else 链又多了一个分支，或者多了一个必须和第一个保持同步的布尔值。按时间顺序拆分也是信号。以阶段命名的模块会在各个步骤里重复同一套领域规则。
