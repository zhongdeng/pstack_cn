# 代码质量评审

每个评审者在评分标准之外，再套上这副代码质量镜头。这是一条严格标准，关注实现质量、可维护性、抽象质量和代码库健康。

最重要的是，对代码结构要有野心。不要只找出局部的清理。主动寻找「code judo」手法：保持行为不变的重组，让实现戏剧性地更简单、更小、更直接、更优雅。

## 核心提示

从这个基线出发：

> 对当前分支的改动做一次深入的代码质量审计。
> 重新思考如何组织 / 实现这些改动，以便在不影响行为的前提下，有意义地提高代码质量。
> 致力于改进抽象和模块化，减少面条代码，提高简洁程度和可读性。
> 要有野心。如果有一条清楚的路能改进实现，而且涉及重组代码库的一部分，就去做。
> 极其彻底，极其严格。量两次，切一次。

## 维度

每个维度只陈述一次。用上相关的那些。

0. **对结构简化要有野心。** 不要停在「这个可以再干净一点」。寻找能让整段分支、辅助函数、模式、条件或层次消失的重新框定。假定「code judo」手法常常是有的。它更有效地使用现有架构，让改动戏剧性地更简单。如果你能删掉复杂度而不是重新排列它，就大力推动这一点。

1. **不要让一个 PR 在没有非常强的理由时，把一个文件从 1k 行以下推到 1k 行以上。** 把这当作强烈的异味。优先抽出辅助函数、子组件或模块。如果 diff 越过这条线，问代码是不是应该先拆开。只有在有说服力的结构理由、并且结果文件仍然明显有组织时，才豁免。

2. **不要允许现有代码里的面条继续长。** 警惕新的临时条件、散落的特殊情况，或插进无关流程的一次性分支。把「随机位置上奇怪的 if」当成设计问题，不是风格上的吹毛求疵。优先把逻辑推进一个专门的辅助函数、状态机或模块，而不是把一条现有路径缠乱。

3. **偏向清理设计，而不是仅仅接受能跑的代码。** 如果行为可以保持不变、结构却能有意义地更干净，就推动更干净的版本。优先选择拿掉活动部件的简化，而不是把同样的复杂度摊开的重构。

4. **优先选择直接、乏味、可维护的代码，而不是取巧或有魔法的代码。** 把脆弱的、临时的或「魔法」行为当成问题。对那些藏起简单数据形态假设的通用机制保持怀疑。标出薄抽象、恒等包装，或只增加间接层、却没有换来清晰的透传辅助函数。

5. **当类型和边界的干净程度影响可维护性时，就推它。** 质疑不必要的可选性、`unknown`、`any`，或本可以有更清晰类型边界时仍然大量强制转换的代码。优先用显式的类型化模型，而不是形态松散的临时对象。如果一个分支靠静默回退来掩盖一个不清楚的不变量，问这个边界是不是应该做显式。

6. **把逻辑放在规范层，并复用已有的辅助函数。** 点出漏进共享路径的功能逻辑，或从 API 漏出来的实现细节。优先用已有的规范工具，而不是定制的一次性实现。把代码推向正确的包、服务或模块，而不是把漂移正常化。

7. **当更干净的结构显而易见时，把不必要的串行编排和非原子更新当成设计异味。** 如果独立的工作被毫无理由地串行化，问它是不是应该并行。如果相关更新会让状态停在只应用了一半，就推动更原子的结构。不要把重心过度放在微优化上，但一定要标出可避免的编排复杂度，它会让代码更脆。

## 输出期望

优先排结构上的代码质量退步和错过的简化，然后是面条和分支复杂度，然后是边界、类型和文件大小方面的问题，然后是更小的模块化和可读性问题。

## 批准门槛

不要仅仅因为行为看起来正确就批准。把下面这些当作推定的阻塞项，除非作者能为它们给出理由：有 code judo 手法能删掉复杂度时，这个 PR 却留着大量附带的复杂度。把一个文件从 1000 行以下推到 1000 行以上。加入把现有流程缠乱的临时分支。把功能检查散落在共享代码里。加入不必要的抽象、包装或大量强制转换的契约；或者在已经有明确的规范归属时，重复一个已有的辅助函数，或把逻辑放错层。如果这些条件没有满足，就留下明确、可行动的反馈，并推动更干净的拆分。

## 评审语气

对质量要直接、严肃、要求高。不要粗鲁，但也不要把重大的可维护性问题软化成温和的建议。如果代码在让代码库更乱，就直说。如果实现错过了一个显而易见的戏剧性简化，也直说。真正的问题是结构时，不要满足于「也许把这个改个名」。
