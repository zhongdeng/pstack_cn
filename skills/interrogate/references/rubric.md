# 评审评分标准

通过那些相关的镜头来评审。不是每副镜头都适用于每一次改动。

## 正确性

代码真的做了意图所说它该做的事吗？

- 边界情况：空输入、nil/undefined、边界值、并发访问
- 错误处理：错误是被接住、传出去，还是被静默吞掉？
- 差一、类型强制、整数溢出、字符串编码
- 状态管理：竞态、过期的闭包、悬空引用
- 顺利路径和失败路径都走得通吗？
- 幂等：这个操作跑两次会怎样，或者上一次跑到一半崩溃了会怎样？如果答案是「这取决于留下了什么样的状态」，就缺了一步调和。
- 并发：如果多个行动者能碰到同一份可变状态（文件、分支、共享数据），访问是在结构上被串行化的（锁、顺序阶段、独占所有权），还是靠守不住的约定？

当你发现一个潜在缺陷，追执行路径。不要只标出「这可能是 nil」。把让它成为 nil 的调用链亮出来。

## 根因与症状

代码是在修真正的问题，还是在把症状糊上一层？

回答这个，常常得看改动文件以外的地方。读周围的代码（调用方、被调用方、类型定义、同级模块），理解这次改动所处的架构。用你手头的工具（Read、Grep、Glob）跟着调用链走，读类型，在判断这次改动有没有打在正确的层上之前，先弄懂这段代码为什么存在。

- 掩盖更深层不变量违反的守卫子句
- 藏起破损契约的重试逻辑
- 把建模错误消音的类型转换
- 一处变通：为什么需要它？正经的修法长什么样？
- 模块 A 里的修复，其实应该修的是模块 B 的契约
- 本该用结构却用了说明的地方：如果修复是一条说「不要做 X」的注释，或一条得靠人记住的约定，就问它能不能换成类型约束、lint 规则，或让做错变得不可能的运行时检查

## 结构完整性

代码是否很好地嵌进它所属的系统？

- 边界纪律：校验是在系统边界，还是散在业务逻辑里？数据进入系统的地方校验一次，然后在内部信任它。
- 抽象层次：代码是不是把高层编排和低层细节混在一起？
- 耦合：这次改动有没有引入会让以后的改动更难的依赖？
- 数据模型是否贴合：数据结构是否对得上实际的访问模式？
- 是外挂上去的，还是融进去的：如果一开始就知道这个新需求，代码会是现在这样，还是这次改动像是补在现有设计上？
- 遗留双路径：这次改动是不是引入了新 API，同时让旧 API 继续活着？如果没有外部消费者，就在同一波里把调用方迁走并删掉旧路径。不要留下会变成永久设施的兼容层。

不要因为简单代码缺了抽象就罚它。过早的抽象比重复更糟。

## 验证

读它的时候，你能判断这段代码是能工作的吗？

- 有测试吗？它们测的是行为，还是实现细节？
- 有能抓住回归的断言或不变量吗？
- 如果这是一处缺陷修复：有针对这个缺陷的测试吗？
- 如果这碰到了集成边界：整条路径测过了吗？
- 检查真实的东西，不要检查代用品。如果代码靠文件 mtime 或缓存的状态来检查是否还活着，而不是去读实际的值，那就是验证上的缺口。
- 对委托出去的或异步的工作：代码核的是实际的输出产物，还是信任自我报告和摘要？

## 复杂度预算

这份复杂度，被代码完成的事情证明是合理的吗？

- 可以更简单、又不损失正确性或清晰的代码
- 只服务一个调用点的抽象
- 为还不存在的情况做的配置或参数化
- 死代码、没用到的导入、残留参数
- 过度工程：没有当前调用方的「以防万一」路径
- 为了过渡期的稳定而留着、但这份稳定已经不再需要的过时兼容路径。迁移做完了，就删掉脚手架
- 用户体验撑得起这份复杂度吗？每一个功能、控件和选项都该挣到自己的位置。做了一半的功能比没有更糟

更简单更好，除非更简单是错的。

## 安全

每一条安全发现，都把输入路径在代码里追出来，并展示它。

- 用户输入未经清洗就流向危险汇（SQL、shell、eval、innerHTML）
- 新端点上的认证或授权缺口
- 代码、日志或错误信息里的秘密
- 安全关键路径上的 TOCTOU（检查时刻与使用时刻）
