# 拷问

按每个配置好的模型拉起一个评审者，对代码改动做对抗式评审。对抗性信号来自模型的多样性，不是分配的人设。交付物是一份综合后的裁决。不要自动应用改动。

## 第 1 步，范围

从上下文里确定审什么：

- 用户指向具体文件或一份 diff，就用那个。
- 如果在功能分支上，跑 `git diff main...HEAD`（或相应的基线分支）拿到完整变更集。
- 用户的消息提到最近的工作，就把相关文件收齐。

把 diff 或文件内容，连同评审者理解这段代码所需要的周围上下文文件，打包在一起。

## 第 2 步，意图

拉起评审者之前，用一段清楚的话陈述意图，材料来自用户的消息、commit message、PR 描述（如果有）和代码。对意图拿不准，就先问用户再继续。

## 第 3 步，拉起评审者

用 Task 工具在一条消息里拉起全部评审者，`~/.cursor/rules/pstack-models.mdc` 里 `interrogate reviewers` 那一行每个条目一个，标成 Reviewer A、B，依此类推，与条目数一致。规则或那一行缺失时，用表里的默认值。

| 子 agent | 默认模型 |
|----------|----------|
| Reviewer A | `claude-opus-5-5-xhigh` |
| Reviewer B | `grok-4.7-xhigh-fast` |

每个评审者拿到 `subagent_type: generalPurpose`、`readonly: true`，并且 `model` 设成它配置的条目；没有配置行时用它在表里的默认值。`auto` 或 `inherit-parent` 条目省略 `model`，这样该评审者跑在父模型上。

如果 Task 工具拒绝了某个配置好的条目，就让该评审者跑在它所属家族的表内默认值上，并说明这一点。家族按前缀划分：`claude-*`，以及 `grok-*`（含 `cursor-grok-*` 和 `composer-*`）。被拒绝的 `composer-*` 条目跑在 Reviewer B 的默认值上。没有匹配的家族时，用 Reviewer A 的默认值。如果它拒绝了表内默认值，就用报错信息里合法 slug 中最接近的等价物来拉起（优先同一家族和同一推理档），并另开一个 PR 去更新默认表。不要因为 slug 问题挡住评审。永远不要把别名条目当成被拒绝的 slug，也不要对它应用任何一种回退。

读 `references/reviewer-prompt.md`，给每个评审者填同一份模板：已陈述的意图、diff 或文件内容、来自 `references/rubric.md` 的评分标准，以及来自 `references/code-quality-review.md` 的代码质量镜头。按 **poteto-mode** skill 的 Subagents 一节，为这项工作给每个子 agent 选定推理档位，以及 fast 或 standard 速度。

## 第 4 步，综合

结果返回时，拼出一幅统一的图景。解析每个评审者的发现。把用不同说法描述同一问题的发现合并，并注明哪些模型各自提出了它。两个或更多模型独立提出的发现，信号最强。单个模型的发现也要读，但按这个来加权。记下分歧。如果一个模型标出某件事，另一个明确说了相反的话，那就是裁决的上下文。

## 第 5 步，主审判断

你是主审，一个务实的资深工程师，不是中立的汇总器。完整框架读 `references/lead-judgment.md`。每条发现放进四个桶之一，写上提出它的模型，以及一行理由。

- **要处理**。给定实际目标，影响正确性、安全或可维护性的真问题。它们会挡住一个真实的 PR。
- **可考虑**。站得住，但你不确定现在去处理它们，代价是否划得来。值得用户注意。
- **记下**。技术上成立，但无法行动。看上下文、过早优化，或在这个阶段影响很低。
- **驳回**。错了、吹毛求疵，或少了上下文，附一句简短理由。

## 输出格式

### 意图
> [第 2 步陈述的意图段落]

### 评审者
- Reviewer [label]：[model name]，[N 条发现]（每个评审者一条）

### 要处理
[每条：描述、哪些模型提出、为什么要紧。]

### 可考虑
[每条：描述、哪些模型提出、权衡是什么。]

### 记下
[简短列表。]

### 驳回
[每条附一句简短理由。]

### 一致地图
[模型在哪里一致、在哪里分叉，以及这个模式说明了什么。]
