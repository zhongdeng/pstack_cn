# 自动化我

一个引导流程，把用户的工作习惯变成智能体会遵循的技能。产出是一个为他们量身定制的 `-mode` 技能（例如 `jay-mode`、`priya-mode`）。

这个技能编排另外三个：一次内联挖掘（见第 1 步）、Cursor 内置的 `create-skill`（撰写）和 **unslop** 技能（行文纪律）。它负责排序，不替代它们。

## 流程

### 0. 检查是否已有技能

递归查找 `.cursor/skills/**/*-mode/SKILL.md` 和 `~/.cursor/skills/*-mode/SKILL.md`，匹配用户的 handle。mode 技能可以放在个人分类目录里（`.cursor/skills/<handle>/`），不只在顶层。如果找到了，用 `AskQuestion` 确认意图（除非他们已经说了"更新我的技能"之类的话）：

- 更新现有技能（重复运行时的默认选项）
- 从头开始（少见，做之前先问为什么）

更新模式会改变后面流程：
- 第 1 步只挖掘技能上次编辑之后的历史（`git log -1 --format=%cI <path>`）。
- 第 2 步问的是有什么变了或缺了什么，而不是从零开始捕获什么。
- 第 4 步原地编辑现有文件。保留用户没有推翻的章节。用新证据修订已有章节。只有真正新的规则才加新章节。

### 1. 挖掘他们的历史

在分发之前先定位当前工作区的对话记录。系统提示里会写明该工作区的 `agent-transcripts/` 目录。只用那个路径。不要用 glob 扫 `~/.cursor/projects/*/`。那会跨工作区边界，读到无关项目的私密聊天。

在这个范围内浏览最近的智能体对话，找反复出现的模式。按历史切片并行跑多个子智能体（例如最近 2-4 周，切成 3 片，让每片都有足够材料）。按 **poteto-mode** 技能里 Subagents 一节的说明，为每个子智能体挑选推理档位和 fast 或 standard 速度。每个切片挖掘子智能体读取父级提供的、限定在工作区路径下的对话记录，寻找下面的信号，并返回一份简短的结构化列表，列出它看到的模式及证据位置。默认值得找的信号：

- 回复偏好（长度、语气、格式、"说人话"式的纠正）
- 委派习惯（子智能体、模型、专门化工作流、并行度）
- 验证姿态（"完成"意味着什么，单元测试还是实机复现，评审者）
- 代码和行文纪律（风格、引用的原则、lint/format 工具）
- 流程惯例（worktree、提交、PR、评审/合并工具）
- 元偏好（任务中途修技能、提议新技能）

在提升某个信号之前先跨切片交叉核对。在 2 个以上切片里出现的模式是高置信度的。孤立信号很弱，通常会被丢掉。

### 2. 直接问用户

挖掘会漏掉还没出现过的意图。用 `AskQuestion` 工具（结构化多选），而不是让用户从零开始打字。

形式：一到两个问题，每个 4-6 个选项，分类问题用 `allow_multiple: true`。先问宽泛的（"哪些方面最重要？"），再针对选中的方面用具体选项追问。结构化几轮之后，用一个自由聊天问题兜住选项没覆盖到的东西。

别一口气甩 20 个问题。

### 3. 聚类发现

把合并后的信号分组成章节。常见的（只用在适用的地方）：

- **回复风格**：长度、语气、格式。
- **自主性**：不问就做多少、MCP 工具使用。
- **先理解**：界定或调查改动时该用哪些技能。
- **子智能体**：默认、并行度、模型对任务、专门化工作流。
- **行文 / 代码纪律**：原则、lint 工具、风格指南。
- **评审与验证**：复现姿态、验证技能、实机测试工具。
- **流程**：git worktree、提交、PR、评审/合并工具。
- **技能**：技能撰写习惯、先修技能、提议新技能。

**poteto-mode** 技能展示了形态。读它来把握颗粒度。别抄它的内容。用户的规则和 poteto-mode 的不一样。

### 4. 起草技能

用 Cursor 内置的 `create-skill` 技能来撰写。放置位置：

- 路径：保留现有 mode 技能的分类。新 mode 的话，如果仓库里已经为该 handle 建立了个人分类，用 `.cursor/skills/<handle>/<handle>-mode/SKILL.md`。否则默认放到项目里的 `.cursor/skills/<handle>-mode/SKILL.md`（或者如果用户偏好个人技能，用 `~/.cursor/skills/<handle>-mode/`）。
- Handle：用户的名字或选定的标识。
- Frontmatter `description`：以他们的名字 + `/<handle>-mode` + "按他们的风格工作" 触发，而不是 "写代码" 或 "评审 PR" 这类泛化关键词。
- Frontmatter 格式：遵循 `create-skill` 的 YAML 规则。`description` 保持为一个 YAML 标量。需要时加引号，或用 `description: >-` 配缩进续行。
- Frontmatter `disable-model-invocation: true` 默认开启。只有用户明确希望他们的 mode 在每一轮都生效时才关掉。

### 5. 迭代行文

对每一行应用 **unslop** 技能和 `create-skill` 的写作指南。

把草稿给用户看，收集反馈。预期多轮迭代。狠心删。mode 技能不是手册。

### 6. 落地

在基于 main 的 worktree 里干活。提交并开 PR。别直接推到 main。

## 护栏

- **别对单次对话过拟合。** 一次说过、另一次又被推翻的偏好是噪音。要多次出现才能固化。
- **别耍聪明。** 复述其他技能的内容、发明比喻、给智能体读者写"诗意"文字，都是只有成本没有收益。保持可操作。
- **引用，不要内联。** 用户依赖的其他技能应该以路径引用的形式出现，而不是粘贴摘录。他们在别处维护的原则文档也一样。
- **章节保持精简。** 只有当用户在某方面有具体的、非默认的规则时才加章节。"清晰沟通"不是一个章节。"短段落。比较选项时用表格。只有条目真正并列时才用列表。"才是。
- **命名惯例保持通用。** 祈使句里用"用户"或"人"，不要用作者的名字。
- **别强行对称。** 如果用户没有值得写下来的流程规则，整个流程章节就跳过。

## 评估

`-mode` 技能是主观产出。`create-skill` 那种测试/迭代基准循环在这里没用。和用户凭感觉核对：读起来像他们吗？漏了什么吗？然后发布。

只有当技能的触发准确率在实践中真的成了问题时，才跑描述优化循环。

## 何时不用

- 用户想要任务特定的技能（不是工作习惯）：单用 `create-skill`，不需要挖掘。
- 用户想固化一个很窄的工作流（例如"我怎么写提交信息"）。那是普通技能，不是 mode 技能。
