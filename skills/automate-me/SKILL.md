# 把我自动化

一条引导式流程，把用户的工作约定变成 agent 会遵守的 skill。产出是一份按他们定制的 `-mode` skill（例如 `jay-mode`、`priya-mode`）。

这个 skill 编排另外三个：一轮内联的挖掘（见第 1 步）、Cursor 内置的 `create-skill`（执笔），以及 **unslop** skill（正文纪律）。它给它们排顺序。它不替代它们。

## 流程

### 0. 检查是否已有 skill

递归查找 `.cursor/skills/**/*-mode/SKILL.md` 和 `~/.cursor/skills/*-mode/SKILL.md`，匹配用户的 handle。Mode skill 可以放在个人分类目录（`.cursor/skills/<handle>/`）里，不只是顶层。如果已经有一份，用 `AskQuestion` 确认意图（除非他们已经说过「更新我的 skill」或类似的话）：

- 更新已有的 skill（重复运行时的默认）
- 从头开始（少见；动手之前先问为什么）

更新模式会改变后面的流程：
- 第 1 步只挖掘 skill 上次被编辑以来的历史（`git log -1 --format=%cI <path>`）。
- 第 2 步问的是变了什么或少了什么，不是从零开始要捕捉什么。
- 第 4 步就地编辑已有文件。用户没有推翻的节保留。有新证据的节修订。只有真正的新规则才加新节。

### 1. 挖掘他们的历史

铺开之前，先定位当前工作区的对话记录。系统提示里写了这个工作区的 `agent-transcripts/` 目录。只用那条路径。不要对 `~/.cursor/projects/*/` 做 glob。那会跨过工作区边界，读到无关项目里的私人聊天。

在这个范围内查看最近的 agent 对话，找反复出现的模式。对历史的若干段跑多个并行子 agent（例如最近 2 到 4 周，切成 3 段，让每段都有足够的材料）。按 **poteto-mode** skill 的 Subagents 一节，为这项工作给每个子 agent 选定推理档位，以及 fast 或 standard 速度。每一段的挖掘子 agent 从父级给出的、限定在这个工作区的路径读取对话记录，寻找下面这些信号，并返回一份简短的结构化列表：它看到的模式，附上证据指针。默认值得搜的信号：

- 回应偏好（长度、语气、格式、「说简单点」这类纠正）
- 委派习惯（子 agent、模型、专门的工作流、并行）
- 验证姿态（「做完」是什么意思、单元测试还是现场复现、评审者）
- 代码和正文纪律（风格、引用的原则、lint/格式工具）
- 流程约定（worktree、commit、PR、评审/合并工具）
- 元偏好（任务做到一半去修 skill、提议新的）

把一个信号抬升之前，先在各段之间交叉核对。在不少于 2 段里出现的模式是高置信的。落单的信号很弱，通常丢掉。

### 2. 直接问用户

挖掘会漏掉还没出现过的意图。用 `AskQuestion` 工具（结构化的多选），而不是让用户从零开始打字。

形态：一到两个问题，每个 4 到 6 个选项，分类问题用 `allow_multiple: true`。先问得宽（「哪些方面最要紧？」），再对选中的方面用具体选项追问。结构化几轮之后，用一个自由形式的聊天问题，接住选项漏掉的任何东西。

不要一下子倒出 20 个问题。

### 3. 把发现归成簇

把合在一起的信号分成节。常见的有这些（只用适用的）：

- **回应风格**：长度、语气、格式。
- **自主程度**：不问就做多少，MCP 工具怎么用。
- **先理解**：框定或调查一次改动时，该伸手去拿哪些 skill。
- **子 agent**：默认、并行、模型与任务的搭配、专门的工作流。
- **正文 / 代码纪律**：原则、lint 工具、风格指南。
- **评审与验证**：复现姿态、验证 skill、现场测试工具。
- **流程**：git worktree、commit、PR、评审/合并工具。
- **Skill**：写 skill 的习惯、先修 skill、提议新 skill。

**poteto-mode** skill 展示的是这个形态。读它是为了看粒度。不要抄它的内容。用户的规则和 poteto-mode 的不是一回事。

### 4. 起草 skill

用 Cursor 内置的 `create-skill` skill 来写这份 skill。放置位置：

- 路径：保留已有 mode skill 的分类。新的 mode，如果仓库里已经有这个 handle 的个人分类目录，就用 `.cursor/skills/<handle>/<handle>-mode/SKILL.md`。否则默认放在项目里的 `.cursor/skills/<handle>-mode/SKILL.md`（如果用户更想要个人 skill，就用 `~/.cursor/skills/<handle>-mode/`）。
- Handle：用户的名，或他自己选的标识。
- Frontmatter 的 `description`：用他们的名字 + `/<handle>-mode` + 「按他们的风格工作」来触发，不要用「写代码」或「评审 PR」这类泛关键词。
- Frontmatter 格式：遵循 `create-skill` 的 YAML 规则。`description` 保持为一个 YAML 标量。标点或换行需要时，给它加引号，或用 `description: >-` 配上缩进的续行。
- Frontmatter 默认 `disable-model-invocation: true`。只有用户明确希望他们的 mode 在每一轮都生效时，才关掉这一点。

### 5. 打磨正文

每一行都套用 **unslop** skill 和 `create-skill` 的写作准则。

把草稿给用户看，收下反馈。预期会迭代多轮。狠砍。一份 mode skill 不是一本手册。

### 6. 落地

在从 main 拉出的 worktree 里做。提交并开一个 PR。不要直接推到 main。

## 护栏

- **不要过拟合到一次对话。** 只说过一次、另一次又被推翻的偏好是噪声。要有多次实例才把它写进规则。
- **不要耍聪明。** 复述其他 skill 的内容、发明隐喻，或给 agent 读者写「诗意」的正文，是有代价没有收益。保持可操作。
- **引用，不要内联。** 用户依赖的其他 skill 应该以路径引用出现，不要粘贴摘录。他们在别处维护的原则文档也一样。
- **节保持最小。** 只有用户在那里有一条具体的、非默认的规则时，才加一节。「沟通要清楚」不算一节。「短段落。比较选项时用表格。只有各项真正并列时才用条目。」才算。
- **约定用泛称来命名。** 祈使句里用 "the user" 或 "the human"，不要用作者的名。
- **不要强行对称。** 如果用户没有值得写下来的流程规则，就把流程这一节整个跳过。

## 评估

`-mode` skill 是主观产出。这里用不上 `create-skill` 那种测试/迭代的基准循环。跟用户对一下感觉：读起来像他们本人吗？有没有漏掉什么？然后就交付。

只有这个 skill 的触发准不准在实践里真成了问题，才跑一轮描述优化。

## 何时不要用

- 用户要的是针对具体任务的 skill（不是工作约定）：只用 `create-skill`，不需要挖掘。
- 用户想捕捉一条窄的工作流（例如「我怎么写 commit message」）。那是普通 skill，不是 mode skill。
