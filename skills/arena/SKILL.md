# Arena

在启动任何东西之前，先开一个 todolist，每个阶段一条（Frame、Fan out、Cross-judge、Pick、Graft、Verify）。

## 阶段 A：框定

每个候选拿到的是同一个 prompt，所以 prompt 就是契约。

1. 写清每个候选要产出的产物。
2. 推导出评分标准，3-6 条具体、可打分的判据，说明在*这个*任务上成功长什么样。这是阶段 D 里挑选者的工具。候选只看得到任务。
3. 选 runner。用 `~/.cursor/rules/pstack-models.mdc` 里的 `arena runners` 那一行。如果规则或那一行缺失，默认在 `claude-opus-5-5-xhigh` 和 `grok-4.7-xhigh-fast` 上各跑一个。这一行里的 `auto` 或 `inherit-parent` 条目表示父模型，所以对它省略 `model`。如果 Task 工具拒绝某个已配置的条目，那个席位就用它所属家族的默认模型跑，并说明这一点。家族按前缀划分：`claude-*`，以及 `grok-*` 连同 `cursor-grok-*` 和 `composer-*`。被拒绝的 `composer-*` 条目改用 `grok-4.7-xhigh-fast` 跑。如果该家族没有默认模型，或者 Task 工具拒绝那个默认模型，就用它错误信息里同家族最接近的有效 slug，没有的话就丢掉这个席位并说明。如果丢掉的席位让 runner 少于两个，就补 runner 直到有两个，或者当那一行只有一个条目时补到一个。每个补上的 runner 用某个剩余 runner 的模型跑，或者在没有剩余时省略 `model` 让它跑在父模型上，并说明。当 arena 覆盖多个设计方向时，多开几个 runner。当工作受生成能力限制而不是对判断敏感时，同一个模型用 N 次。按 **poteto-mode** 技能的 Subagents 一节，为每个子智能体挑选适合该工作的推理级别和 fast 或 standard 速度。
4. 给每个候选各自的输出位置（尽量用 git worktree，否则用 `/tmp/arena-<slug>/candidate-<n>/`），按 **separate-before-serializing-shared-state** 原则技能。

## 阶段 B：并行铺开

在一条消息里用 `run_in_background: true` 启动全部 N 个子智能体，每个都带上任务、共享背景资料的路径、自己的输出路径，以及要求它产出产物和一段简短理由，说明它考虑过哪些替代方案、否决了什么。

如果某个候选没有产出，就用 N-1 继续，并记下这个掉队的。

## 阶段 C：交叉评审

等阶段 B 的所有候选完成后，从 `~/.cursor/rules/pstack-models.mdc` 里的 `arena cross-judge pool` 那一行选一个模型。如果规则或那一行缺失，就从 `claude-opus-5-5-xhigh` 和 `grok-4.7-xhigh-fast` 里选。启动一个只读的评审子智能体。评审永远不来自父模型所属的家族，家族按阶段 A 第 3 步的定义。只按池中顺序尝试其他家族的条目。`auto` 或 `inherit-parent` 条目就是父模型，所以它永远不做评审。用默认池时，Claude 父模型拿到 `grok-4.7-xhigh-fast`。其他任何家族的父模型先拿到 `claude-opus-5-5-xhigh`。如果 Task 工具拒绝某个条目，就用错误信息里同一模型最接近级别或速度的有效 slug，没有的话就换下一个条目。如果其他家族没有任何条目能跑，就用同样的方式尝试默认池里其他家族的条目。如果这些也都跑不了，就跳过评审，在阶段 D 独自挑基底，并说明。如果你不知道父模型是什么，就按池中顺序尝试池里真实的 slug，并说明家族检查没有执行。评审看到评分标准和按路径标签标识的候选，逐条打分，并推荐一个基底附上理由。它和你在阶段 D 的阅读并行进行。候选还在写的时候不要启动它。

## 阶段 D：挑一个基底

挑之前把每个候选从头到尾读一遍。按评分标准逐条打分，不要凭整体感觉，并在阶段 C 跑了评审时和交叉评审对比。对基底的一致意见确认这次挑选。分歧意味着你们中有一个有偏见，或者评分标准有歧义。决定前把两边的理由都读一遍。

挑那个未来的维护者最容易扩展、又不会破坏不变量的基底。两个感觉打平时，按 Laziness Protocol 优先选边界更干净或 API 更小的那个。

## 阶段 E：嫁接

把每个落选候选再走一遍，找出值得移植进基底的东西，通常每个候选一到两样，而不是大部分。按 **redesign-from-first-principles** 原则技能，手工把每处嫁接折进去，让结果在一个心智模型下保持连贯。不要机械粘贴。

如果候选收敛到同一个形态，那是强烈的一致。记下来，直接交付这个共识形态。不需要嫁接。如果它们严重发散，说明阶段 A 定得不够细。重新框定再跑一遍，而不是把发散平均掉。

## 阶段 F：验证

按 **prove-it-works** 原则技能，像验证任何其他输出一样验证合成后的产物。如果验证发现了 arena 漏掉的问题，要么是阶段 A 错了（重新框定再跑），要么是某个候选抓到了而你漏掉了嫁接（回到阶段 E）。不要把它糊过去。

## 输出

一个合成后的产物，旁边附一段简短的合成说明，写明基底是哪个以及为什么、交叉评审的结论或阶段 C 跳过了评审、每处嫁接及其来源候选、否决了什么以及为什么、任何收敛或掉队情况，以及验证结果。
