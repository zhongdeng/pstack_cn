# 维护形式化验证技能

形式化检查证明的是它所描述的东西的性质。代码变了而验证没变，检查可以一直通过，同时它描述的代码已经不存在了。这种通过最危险，因为它看起来像一份证明。这个技能是维护循环，针对 `/create-formal-verification-skill` 生成的验证技能，或者任何项目本地的、对具名代码跑模型检查器、证明器或代码级验证器的技能。项目本地技能处理的是智能体在使用该技能时做出的改动。这个技能处理的是绕过了它的改动：合并、没用技能做的编辑，以及跨很多提交积累起来的漂移。

## 结果

给每个检查一个结果，并说明是哪一个：

- **in sync**：自上次同步以来没有任何改动会改变检查所描述的内容，并且检查通过。
- **updated**：代码变了，验证现在描述的是新代码，并且检查通过。
- **bug**：验证描述的是当前代码，而代码违反了性质。这是关于代码的发现。它不是漂移。
- **blocked**：检查无法重新对齐，或者无法运行。说清楚具体原因。

一个检查可以既是 updated 又是 bug：更新让验证重新描述代码，然后性质在它上面失败。

## 编辑范围

只编辑验证：模型、harness、性质文件和验证技能本身。一次运行中绝不编辑产品代码，除非用户要求你这么做。当性质在当前代码上失败时，不要为了让检查通过而削弱性质或模型。报告这个失败。

## 流程

1. **找到检查。** 验证技能没有固定名字，所以按它做什么来找：一个对具名代码跑模型检查器、证明器或其他验证器的项目技能。读你找到的每一个，或者用户指定的那一个。对每个检查，收集性质、它覆盖的代码、边界和假设、运行它的命令，以及最后一次确认它描述代码的那个提交。如果没有验证技能，停下来，指向 `/create-formal-verification-skill`。如果技能没有记录同步提交，就用最后一个改动验证文件的提交，并说明你是这么做的。

2. **按原样运行。** 在改动任何东西之前，把每个检查跑一遍，记录结果。这里的通过并不告诉你代码是对的。它告诉你旧描述仍然成立。这里的失败可能是漂移，也可能是 bug。在第 5 步之前不要下结论。

3. **读被覆盖代码的每一处改动。** 从同步提交到当前提交，diff 被覆盖的文件，并读每一条提交信息。还要找移动过的代码：被覆盖的函数被重命名、拆分或移到另一个文件，仍然是覆盖代码。还要找触及某个检查所守护的状态的新代码，比如一个写同样字段的新函数。对每一处改动，判断它属于哪一种：
   - **没有影响。** 改动没有改变验证所描述的任何东西，比如格式化、注释，或者验证不覆盖的代码路径。对照模型或 harness 来确认这一点，不要对照提交信息。
   - **验证不再描述代码。** 原本一个不可分割的动作现在变成了两个，增加或删除了一个分支，一个检查移动了位置，一条新路径到达了被守护的状态，或者一个值的范围变了。模型或 harness 必须改。
   - **承诺是有意改变的。** 改动改变了代码承诺的东西，并且改动中的证据说明这是有意的：文档注释、测试、changelog 或提交信息。性质必须改，而且你必须引用那条证据。
   - **承诺可能被破坏了。** 代码变了，没有任何证据说明承诺变了。把随之而来的失败当作 bug 候选。

4. **从代码更新，不要从结果更新。** 改模型或 harness，让每个改动过的部分重新指向评审者能打开的代码，并让代码里一个不可分割的步骤在验证里也是一个步骤。在重新运行之前，从代码出发写更新，不要按什么能让检查通过来塑造它。只对有意改变的承诺改性质。写下旧措辞、新措辞和证据。保留边界，除非改动让它们不再正确。如果你必须降低一个边界，在报告里说明。

5. **重新运行并判断每个结果。**
   - **通过：** 检查现在可能在一个已经失去失败能力的描述上通过。按性质所防范的方式破坏新代码，比如删掉一个新检查或重排一个新步骤，确认检查能抓到它。然后撤掉这个破坏。
   - **失败：** 把反例逐步回放到真实代码上。如果某一步在代码里不可能发生，验证就是错的。修验证，并说明错在哪。如果每一步都能发生，那就是 bug。指出引入它的提交，用代码自己的话把反例讲成一串步骤，用一句话说明危害。如果针对真实代码的一个廉价测试或复现能展示这个 bug，把它作为证据加进报告。不要把它提交到产品代码里。

6. **更新验证技能。** 更新每个检查覆盖的代码、命令、边界、假设和同步提交。把同步提交设为你检查的那个提交。对 blocked 的检查不要移动同步提交，并在报告里说明。然后像下一个智能体那样把验证技能走一遍，确认它的步骤仍然能跑。

## 报告

对每个检查，告诉用户：

- 结果，以及你读过的提交；
- 验证里改了什么、为什么改，每个改动给一个简短理由：代码形状变了，或者承诺有意改变了（附证据）；
- 重新运行的结果，以及你用来证明更新后的检查仍然能失败的破坏；
- 每个 bug，用平实的话说：用代码自己的话把反例讲成步骤，危害，以及引入它的提交；
- 验证仍然不覆盖什么，包括它应该覆盖却没有覆盖的新代码。

直接说明哪些失败是验证漂移，哪些是代码里的 bug。对于一个在你更新之前通过、更新之后失败的检查，说明之前的通过是在一个过时的描述上。

把验证更新放在单独的改动里，与任何产品修复分开。
