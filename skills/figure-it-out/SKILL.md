# 自己搞定

任务对不上任何 playbook 时，就设计一份。写任何代码之前要交付的，是工作流本身：一串阶段，按任务来缩放严格程度，跑科学方法，并留下一条人走开之后还能审计的决策轨迹。

## 开始

开一份待办清单，第一条是读 **poteto-mode** skill 的 Principles 一节。然后把下面这些阶段加进去当待办。

## 阶段 A：定框

先摸清，再定下来。能把下面几点说清楚之前，不要开始这次运行：

- 把完成定义成一个可证伪的谓词（**prove-it-works** 原则 skill）。
- 范围要量化：粗略的单位和工作量，加上摸底浮现出来的阻塞项。
- 严格程度，偏向定高。单向门和爆炸半径大的，给得更多。可逆且赌注低的步骤，给得更少。严格是门禁和产物，不是「再努力试试」。

在投入一次很长的运行之前，先摆出这个定框和其中的权衡。可逆的工作继续推进（**never-block-on-the-human** 原则 skill），但一次要好几个小时的运行，值得设一个检查点。

## 阶段 B：设计工作流

拆成原子的、可以独立落地的单元。按最冒险的未知优先来排。脚手架和验证先于功能（**foundational-thinking** 原则 skill）。

- 干活之前先建验证测试装置，基线从改动前的状态采集，让检查读起来是「旧值对新值」。
- 对单向门的设计决策，跑 **architect** skill（它会跑 **arena**）。形态已经具体的机械性工作，跳过它。对已经定下来的设计再跑第二次 arena，就是过度工程（**laziness-protocol** 原则 skill）。
- 决定什么要铺开。只沿着接缝并行，并给每个工人自己的 worktree 或分支（**separate-before-serializing-shared-state** 原则 skill）。不要铺得过开。按 **poteto-mode** skill 的 Subagents 一节，为这项工作给每个子 agent 选定推理档位，以及 fast 或 standard 速度。
- 把设计好的阶段清单写下来。人要审的就是这份清单。

然后执行这个设计。把它的步骤作为具体条目加进待办清单，放在阶段 C 和阶段 D 两条之间。每一步都按阶段 C 的循环纪律来跑，并把阶段 D 的日志织进这些步骤，每落地一步记一行，而不是把整条轨迹留到最后。

## 阶段 C：跑循环

每个单元都是一次实验。写下假设，做最小的改动，在真实产物上对照谓词来量，推进了就留下，没有就回退。应用 **sequence-verifiable-units** 原则 skill，开始下一个之前先验证这一个，而不是把检查攒到最后一起做。

- 靠检视产物来验证，永远不要靠自我报告。某件事轻易就通过时，先怀疑观察方法，再怀疑系统。
- 委托出去的工作配上一个评判者。如果工人在钻门禁的空子，就重置并加硬契约。如果门禁本身是错的，用它自己的一次改动去修门禁，而不是绕过去。
- 结论是 VERIFIED、NOT VERIFIED 或 INCONCLUSIVE。Inconclusive 不是通过。不要藏起一个否定结果。

## 阶段 D：留下审计轨迹

用 **show-me-your-work** skill 记录这次运行。figure-it-out 的工作通常大到值得把轨迹提交进去，让审阅者能在 PR 里读到。轨迹加上 diff，才让人回来之后信任这项工作。

## 阶段 E：验证并交回

在真实产品上，用阶段 A 的谓词检查整体，不只是测试装置。把任何反复出现的纠正编码成一道门禁、一条 lint 规则、一项检查或一个脚本（**encode-lessons-in-structure** 原则 skill）。

**回复：** 你设计的 playbook、严格程度及原因、决策轨迹的路径、对照谓词已验证的部分，以及仍然敞开的部分。
