# 自己想办法

任务套不上任何作战手册时，就自己设计一份。写代码之前，交付物就是工作流本身：一串阶段，按任务规模调整严谨度，跑科学方法，留下人离开一段时间后回来还能审计的决策轨迹。

## 开始

开一个 todolist，第一项是读 **poteto-mode** 技能的 Principles 部分。然后把下面这些阶段加成 todo。

## 阶段 A：框定

先摸清底，再承诺。说不清下面这些就别开跑：

- 完成标准写成一个可证伪的谓词（**prove-it-works** 原则技能）。
- 范围要量化：大概几个单元、多少工作量，加上摸底时冒出来的阻塞项。
- 严谨度，往高了偏。单向门和高影响面多给点。可逆、低风险的步骤少给点。严谨度是关卡和产物，不是"再努力点"。

长时间开跑之前，先把框定和取舍摆出来。可逆的工作直接推进（**never-block-on-the-human** 原则技能），但跑好几个小时的工作值得一个检查点。

## 阶段 B：设计工作流

拆成原子的、能独立落地的单元。最不确定的先做。脚手架和验证排在功能前面（**foundational-thinking** 原则技能）。

- 先搭验证工具，基线从改动前的状态抓，这样检查读起来就是"旧值 vs 新值"。
- 单向门的设计决策，跑 **architect** 技能（它会跑 **arena**）。形状已经定死的机械活就跳过。设计已定还再开一轮 arena 是过度工程（**laziness-protocol** 原则技能）。
- 决定哪些并行铺开。只在接缝处并行，每个 worker 给独立的 worktree 或分支（**separate-before-serializing-shared-state** 原则技能）。别铺太开。按 **poteto-mode** 技能的 Subagents 部分，给每个子智能体挑推理档位和快或标准速度。
- 把设计好的阶段列表写下来。人审的就是这份列表。

然后执行设计。把它的步骤作为具体条目加进 todolist，放在阶段 C 和阶段 D 条目之间。每一步都按阶段 C 的循环纪律跑，阶段 D 的日志穿插其中，每落一步记一行，而不是把整条轨迹留到最后。

## 阶段 C：跑循环

每个单元都是一次实验。陈述假设，做最小的改动，拿真实产物对着谓词量，有进展就留下，没进展就回滚。套用 **sequence-verifiable-units** 原则技能，每个单元验证完再开下一个，而不是把检查攒到最后一起做。

- 靠检查产物来验证，绝不靠自述。东西过得太容易时，先怀疑观察方法，再怀疑系统。
- 委派出去的工作配一个裁判。worker 钻了关卡的空子，就重置并加固契约。关卡本身错了，就单独改关卡，而不是绕过去。
- 结论只有 VERIFIED、NOT VERIFIED、INCONCLUSIVE 三种。INCONCLUSIVE 不算通过。别藏负面结果。

## 阶段 D：留审计轨迹

用 **show-me-your-work** 技能记录这次运行。figure-it-out 的活通常够大，值得把轨迹提交上去，让评审在 PR 里就能读。轨迹加 diff，才是人回来能信任这份工作的原因。

## 阶段 E：验证并交回

拿真实产品对着阶段 A 的谓词检查整体，不只是检查工具。任何反复出现的纠正，都固化成关卡、lint 规则、检查或脚本（**encode-lessons-in-structure** 原则技能）。

**回复：** 你设计的作战手册、严谨度档位和理由、决策轨迹路径、哪些对着谓词验证过了、还有什么没定。
