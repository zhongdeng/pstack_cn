# Statechart

这张图用读它的那个人的话，显示一个系统如何在状态之间移动。那个人，读者，决定行为对不对。

## 运行

在仓库之外的一个草稿文件夹里工作。写一份 TLA+ 规格和它的配置。然后运行：

```sh
<skill dir>/scripts/statechart SPEC.tla [--config FILE] [--view FILE] [--out DIR]
```

`scripts/statechart.ts` 是 TypeScript，所以用一个能执行 TypeScript 的运行时来跑它。

第一次运行会用 mise 安装 TLC 和 Java，并且需要网络。

## 写规格

- 把读者同意的每一条规则写成一条 INVARIANT。一条规则可以关于一个屏幕、一个结果、一个存下来的值，或一条消息。如果模型里没有一条规则所关于的变量，就加上这个变量。绝不要为了让一条规则成立而把它放宽。
- 把 `Next` 写成各个动作的析取，例如 `YouPressPlay \/ YouPressStop`。如果不这样做，TLC 会把每一步都命名为 `Next`。
- 一个没有步子走出去的状态会打破 `NoDeadlock`，即使它是一个正确的结束状态。当一条 INVARIANT 或 PROPERTY 已经用了这个名字时，这条规则是 `CHECK_DEADLOCK`。往 `Next` 里加一个只在结束状态为真、并且什么都不改的动作，例如 `Done == phase \in {"paid", "failed"} /\ UNCHANGED vars`，并在 `step()` 里给它一个标签。

## 选定这张图

需要判断的工作由你来做：每个状态和每条箭头上的词、阶段和它们的颜色、标题，以及给读者的报告。把你的工作放进一个 view 模块，并用 `--view` 交给它。

要显示读者的话，这个 view 导出 `state(vars)`。`state()` 返回的值决定图的形状：

- 一个字符串给出一张扁平的图：`export const state = (v) => (v.paid ? "Paid" : "Paying");`
- 一个数组给出父状态：`export const state = (v) => v.main.split(".");`
- 一个对象给每个键一个并行区域：`export const state = (v) => ({ Playback: v.playback, Volume: v.volume });`

用读者能看见或在意的东西给每个状态贴标签，例如 "Paying" 或 "Lease held, write pending"。标签里不要出现变量名。在 `vars` 里，一个 TLA+ 序列是一个键从 1 开始的对象，所以 `v.pc[1]` 就是 `pc[1]`。一个集合是一个数组。

这个 view 也可以导出 `step(action, from, to)`。它拿到 TLC 的动作名，以及这一步之前和之后的值，并返回箭头的标签。把每个步骤标签写成用户看见它发生的样子，例如 "you press play" 或 "the connect fails"。不要点名代码或 TLA+ 动作。在图上以同样方式结束的两个动作用同一个标签，这样它们共享一条箭头。

当一步只在某些条件下才能发生时，用读者的话，把条件放在方括号里，写在标签末尾，例如 `you press play [while the file loads]`。在一张区域图里，命令会把其他区域上的条件写在箭头上，用它们标签的话，例如 `[when Offline]`。你的方括号会替换它，于是从一个状态出去的两条箭头可能看起来一样。所以在一张区域图里，不要为另一个区域上的条件写方括号。当一个没有任何标签显示的值决定一步走向哪里时，在标签里点名这个结果，例如 "the roster read fails"。

这个 view 还可以导出这些：

- `group(vars)` 返回一个阶段的名字。每个图状态得到它所属分组的颜色。当一个图状态背后的模型状态落在不同的分组里时，这个状态没有颜色。
- `colors` 给每个分组名一个颜色类。
- `title` 是一个字符串，图把它显示在顶部。

命令对每个模型状态最多调用一次 `state()` 和 `group()`，对每一步最多调用一次 `step()`。图和报告都用这些答案。所以让每个函数只依赖它的参数。

图不画停留在同一个标签里的一步。当读者必须看见这样一步时，把标签拆开。

目标大约是 20 条箭头或更少，因为更挤的图难读。先从 `state()` 返回更粗的标签。给行为相同的值同一个标签，并略去读者不需要的细节，例如一次返回什么都不改变的在途调用。保留缺陷路径上的每一个状态，并保留每一个标记。当一次合并把一个 `breaks` 状态变成 `mayBreak` 时，它藏起了规则在哪里打破。不要合并打破不同规则的两个状态，因为读者那时看不出哪条规则在哪里打破。如果图仍然太挤，对读者不需要的步骤从 `step()` 返回 `null`，例如每个状态都有的一次重置，或一条箭头重复了其他箭头已经显示的内容。隐藏步骤时遵守这些规则：

- 让每个图状态都能从某个起始状态沿箭头到达。
- 对模型里有步子走出去的每个图状态，至少保留一条箭头出去。
- 一条箭头的步骤要么全部隐藏，要么一个都不隐藏。只隐藏其中一些时，它的条件会变窄。
- 在交接里说明图隐藏了哪些步骤。

## 读报告

- 在图里，一个打破规则的状态带有类 `breaks`。当它背后只有一部分模型状态打破这条规则时，它带有类 `mayBreak`。Legend 点名每个标记的规则。两条规则都打破时，它把两者标在同一个标记上，所以在交接里说明哪个状态打破哪条规则。在一张区域图里，当每一种包含某个状态的区域状态组合都可能打破一条规则时，这个状态得到一个标记。当一种组合可能打破一条规则、而它的状态都没有标记时，这个组合里的每个状态都得到一个标记。
- TLC 会走过一个打破规则的状态，所以图显示缺陷之后的状态。
- 因为 TLC 会走过缺陷，一个状态没有上限的模型可以一直跑下去。把常量保持得小，或加一条 CONSTRAINT。
- 有 VIEW 或 SYMMETRY 时，TLC 把它视为相同的状态计成一个状态，图就画这一个状态。一条箭头可能通向它，而不是通向这一步实际到达的那个状态，报告会这样说。
- TLC 检查 CONSTRAINT 或 ACTION_CONSTRAINT 之外的每个状态里的规则，但它不探索那个状态，也不检查它是否死锁。当 TLC 为一条规则找到的最短路径结束在这样一个状态时，图画出这个状态，报告给出这条路径。图不画边界之外的其他状态。这样一个状态里的死锁不会显示。TLC 也会在 ACTION_CONSTRAINT 排除的每一步之后检查规则，即使它从另一条路到达了下一个状态。当 TLC 为一条规则找到的最短路径以这样一步结束时，图画出这一步。
- 命令用 TLC、按所写的配置、用一个 worker 来检查规则。一条规则打破时，命令去掉这条规则并再次运行 TLC，直到没有规则打破。第一次打破之后，每一次运行在 100,000 个不同状态处停止，这样大模型不会一直跑下去。当一次运行到达这个界限或因错误停止时，报告在 "Rules not checked" 下列出它没有检查的规则，图也不标记它们。一条没有被检查的规则可能成立，也可能打破。要检查它，从配置里去掉打破的规则，或把模型做小。这个界限会加入一个改变 TLC 变量顺序的模块，所以对一条性质，TLC 可能找到一个与没有这个界限的运行不同的反例。
- `tlc.out` 是 TLC 在所写配置上打印的内容。当图没有显示一条打破的规则的缺陷路径时，`tlc-RULE.out` 是 TLC 为找到它的那次运行打印的内容。当 TLC 重复它的第一条警告时，普通 TLC 会把它打印两次，但 `tlc.out` 只显示一次，因为 TLC 把第二份留在了这条命令所读的输出之外。这只发生在 Java 以 `-XX:+UseParallelGC` 运行时，因为否则 TLC 的第一条警告是建议传入这个旗标，而它只打印一次。

## 展示这张图

把 `chart.mmd` 作为 `mermaid` 代码块展示给用户。这张图有 500 个状态的预算，由 TLC 在所写配置上计数。超过这个数时，图只画通往打破的规则的路径，并且当没有规则打破时，命令不写 `chart.mmd`。它仍然检查每一条规则，报告给出状态数和每一条缺陷路径。要看见整张图，把模型做小。

用 Pele 渲染图。当用户要一张图，或一张图大到无法当文本来读时，遵循 `references/render.md`。除非用户要求，不要用别的渲染器。

## 交接

把每张图和它的 Mermaid 文本交给必须做决定的那个人。每个缺陷加一行：规则、读者对这条规则的那句话，以及报告所编号的路径。说明模型略去了什么。给出重新生成这些文件的命令，并用一个新的 `--out` 文件夹。

当模型描述的是代码时，把每一条缺陷路径对着真实代码重放，作为一次测试或一次实机复现，每个动作一步。如果一个缺陷没有发生，先认为模型是错的，直到你证明它不是。
