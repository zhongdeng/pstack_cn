# Statechart

这张图用读它的那个人的话，显示一个系统如何在状态之间移动。脚本把那个人叫做读者，如 `readerActions` 和读者步骤。读者决定行为对不对。读者可以是读产品流程的 PM、读协议或服务的工程师，或读一份设计的审查者。用读者能观察到的、或在意的东西给每个状态贴标签，例如应用里的「Paying」，或锁服务里的「Lease held, write pending」。用移动系统的那个事件给每一步贴标签，例如应用里的「tap Pay」，服务里的「the request reads the count」，或锁服务里的「the lease expires」。标签里不要放变量名和动作名。

运行 `node <skill dir>/scripts/statechart.mjs --help`，查看命令以及如何读一张图。在仓库外的一个草稿文件夹里工作。命令把它的文件写在输入旁边。第一次运行会用 mise 安装 TLC 和 Java，大约下载 305 MB，并且需要网络。帮助里的 TLC 一节说明如何使用你已经有的 TLC 和 Java。

## 选定方向

当已经有 TLA+ 模型，或代码或设计已经具体到可以建模时，用 `from-spec`。当还没有模型，并且拥有这个行为的人应该在任何人构建或改动它之前先对它达成一致时，用 `from-chart`。

如果代码已经有一份 TLA+ 规格，从那份规格的一份副本开始。加上标签和规则所需要的变量，并保留规格已有的不变量。要对照那份规格审计代码，就让副本去建模代码实际做的事，并把规格原样作为 `--against` 传入。用它的作者所说的、它能通过的那份配置来检查，并把那份配置作为 `--against-config` 传入，除非它的文件名就是规格的文件名。一份映射同时给两个模型贴标签，所以从两者都有的变量来给状态和步骤贴标签。一个标签若读取只有副本才有的变量，必须先测试 `"name" in v`，并用另一种方式给规格的状态贴标签。当一个模型描述代码时，把每一个变量和动作系到审查者能打开的代码上，并从那段代码取它的名字。让每个动作成为代码里一个不可再分的步骤。把检查一个动作的每个条件的代码的文件和行，放在那个条件的注释里，例如 `\* pay.ts:120`。

## 从规格到图

1. 选择图的状态。当读者在意某件会被标签藏起来的事时，把它放进标签，例如第二次扣款之后屏幕仍然显示「Paying」时，写成「Paying, charged twice」。从很少的状态开始。当一次拆分能分开两个缺陷，或读者必须看见一个离开后标签仍然相同的步骤时，才拆开一个状态，例如一次读取计数的请求，因为图不会画出这样的步骤。
2. 把读者同意的每一条规则写成一个不变量，用读者的那句话作为它的注释。一条规则可以关于模型里的任何状态：屏幕显示什么、请求返回什么、一个存储的值，或部件之间的一条消息。当模型描述代码时，规则还要点名能够改变那个状态的代码。如果模型没有一个变量来表示规则所关于的东西，就加上这个变量。不要丢掉这条规则。对一条在一切安定之后才适用的规则，定义 `Settled == ~ENABLED System`，其中 `System` 是那些没有读者也会发生的动作的析取。对一条在更窄的点上适用的规则，例如每个请求结束之后，为那个点写一个谓词，并让规则在它为真的地方成立。对一个系统必须能够到达的目标，写一条说这个目标从不发生的规则，并用 `--expect-broken` 传入那条规则。打破它的那条路径于是成为到达目标的一条路。图仍然把目标画成一个打破规则的状态，而 `stories.md` 把它讲成一个缺陷，所以在交接里点名每一条目标规则。把其他每一条被打破的规则报告为缺陷。绝不要为了让图通过而削弱一条规则。
3. 运行 `from-spec`，然后填上它写出的映射文件。把标签放进 `state` 和 `step`。当图必须把读者做的事和读者周围发生的事分开时，按动作名把读者的动作列在 `readerActions` 里。当每一个动作都同等计入时，把列表留空。当总览大到读不了时，加上 `--cover`。总览于是只保留到每一个已安定状态的最短路径，加上每一条缺陷路径，并且命令会列出它省掉了什么。当两个缺陷因不同原因结束在同一个状态时，加上 `cause`，并让它点名每一个原因。要按读者在意的东西给状态上色，例如「Order shipped」，就从 `group` 返回那个组。图例点名这些组，并且在 PNG 里，一个打破规则的状态用红色代替它的组颜色。
4. 如果有一个提议的修复，给它建模，并把那个模型作为 `--fixed` 传入。
5. 用 `--png` 渲染每一张图，并看每一张 PNG。检查每一条带编号的路径是否按顺序读得通。如果一个标签读起来像代码，就修 `state` 或 `step`，并再跑一次命令。
6. 当模型描述代码时，把每个缺陷的故事对着真实代码重放，作为测试或实机复现，每个模型动作一步。只驱动用户、客户端或系统另一部分会到达的入口，并且只断言他们能观察到的东西。一个断言它自己所设置的标志的测试，或一个搜索源码文本的测试，什么都证明不了。当一次运行证明了故事的一部分、读代码证明了其余部分时，说明每一部分各证明了什么。当测试复制了它无法导入的代码时，给出副本的提交和行范围，并列出副本省掉了什么。如果一个缺陷不能复现，就假定模型是错的，直到你证明并非如此。修模型，不修规则。对一份还没有代码的设计，TLC 追踪就是证据，交接必须这样说。

## 从图到规格

1. 画出读者同意的那张图。对每一个独立变化的部分用一个区域，例如一台设备的连接，以及这台设备所跑的作业。每条规则加一行 `%% never`，带上读者的那句话。把一个停止或重启某个部分的事件画成一条边，指向接下来的那个状态，例如「the app closes」或「the process restarts」。运行 `render CHART.mmd`，给读者一张图的 PNG。
2. 运行 `from-chart`。如果一条规则被打破，这张已经同意的图里有一个设计缺陷。把这个缺陷带给同意这张图的那些人。
3. 把真实代码的守卫和变量加到 `from-chart` 写出的规格里，并再跑一次 `from-chart`。对它打印出的每一处差异，问读者是代码错了，还是图需要一处修正。

## 交接

把每一张图的 PNG 和 Mermaid 源交给必须做决定的那个人。每个缺陷一行，写上它打破的规则、图给它编的步骤号、它是否复现，以及提议的修复是否修好了它。一个被打破的 PROPERTY 在图上没有路径，所以给出 `stories.md` 为它点名的 TLC 反例。有 `--against` 时，还要说明规格是否已经列出了它：在 `stories.md` 所点名的配置里、在规格关于模型省掉了什么的笔记里，或根本没有。当模型描述代码时，不要在命令列出了没有文件和行的条件时，报告一条规则成立。你引用的每一个计数都取自 `summary.json`。附上 `stories.md`，以及重新生成一切的那条命令。说出模型省掉了什么。
