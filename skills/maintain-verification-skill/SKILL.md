# 维护验证技能

功能地图在应用一变的时候就开始腐烂。本技能是由 `/create-verification-skill` 生成的技能（或任何带功能地图的、项目本地的验证技能）的维护循环。严格性的单位是功能，不是每一句话：从源码覆盖每一个功能文件，并实机演练每一个功能，而不把每一条要点都做到终态。

## 结果

选一个，并说明是哪一个：

- **干净** — 每个功能都得到了源码覆盖和实机覆盖；没有值得交付的东西。不要分支，不要 PR。
- **已变更** — 一个 PR 交付已证明的文档、测试夹具或地图更正。
- **受阻** — 覆盖没能完成，或一个已证明的修复无法安全交付。确切说明是什么挡住了它。

## 编辑范围

只编辑验证技能自己的目录（它的 SKILL.md、features/，以及它拥有的任何测试夹具脚本）。运行期间绝不编辑产品代码：地图所描述、而应用不再做的行为，要么是文档漂移（修好地图），要么是产品回退（报告它，不要在文档里把它盖过去）。

## 这一遍

0. **定位目标。** 找到要维护的验证技能：正文里有启动/驱动各节和一张功能地图的项目本地技能（通常是 `.cursor/skills/verify-*/`）。几个候选 → 问要哪一个；一个都没有 → 停下并指向 `/create-verification-skill`，而不是发明一个目标。

1. **索引整洁。** 阅读功能地图的 README，并 glob 它的同级文件。修掉缺失、多余、重复或死掉的条目。从轻；不要生成清单。

2. **源码一轮。** 每个功能文件一个只读子代理，同时启动。每个都从源码解释「这个面向用户的功能如何工作？」，用引用标出可能的文档漂移，并返回一份简洁的实机验证配方。子级绝不驱动应用，也绝不编辑文件。返回形状：功能摘要 / 源码入口 / 可能的漂移或没有 / 一份配方。

3. **核对。** 每个功能文件都有一份返回的摘要。把重叠的配方合并成尽可能少的应用状态。抽查被引用的漂移；不要重新证明那些干净的说法。扫一遍最近的改动，找地图里缺的、面向用户的界面——在认定某一个缺失之前，要求有一条具体的源码路径。

4. **实机一遍。** 即使源码看起来干净也必须做。协调者拥有全部驱动；遵循验证技能自己的启动模型——对服务器和界面，一个长期存活的实例串行驱动；对短命的 CLI，每次驱动一个全新的隔离会话（由该技能的 Launch 一节决定，不是这一节）。每个功能至少演练一次，并且整遍过程无论遇到什么失败都守住三条不变量：（1）自从某个实例上次做出意外行为以来，如果你还没对它做过健康检查，就绝不要驱动它——第一次驱动之前先 doctor，在以会话为单位的每个新会话上 doctor，任何一次失败的驱动之后再 doctor；而在 doctor 看不到失败的地方（进程健康但界面卡住），重置到已知状态或重新启动，而不是指望它自己好；（2）到目前为止捕获的证据要挺过每一次清理，在它被点名的位置核对，而不是假定还在；（3）一次驱动启动的任何东西都不应活过这次驱动的用处——失败迭代的残留都要清理，无论会话是卡住、已退出还是共享的（对共享实例，清理残留，而不是实例本身）。由技能漂移引起的 doctor 失败就是漂移：在编辑范围内修好它，并重试一次——把这次修复所失效的东西重新启动，除此之外不要多做——然后再把这一遍称为 `blocked`。一个够不着的功能，只有在写明具体前提（认证、权益、操作系统、外部状态）和尝试过的路径时，才标为 `verified-unreachable`；如果地图漏了那个前提，那就是漂移。分诊中产生的任何测试夹具修复，在交付之前都要重新实机驱动。最终拆卸发生在这次运行的最后一次驱动之后——包括那些重新证明——因此没有东西活过这次运行（证据留下，依照该技能）。

5. **分诊。** 错误或缺失的用户视角描述 → 文档漂移，修好它。实际能工作、但测试夹具驱动不了的行为 → 测试夹具缺口，修好它；测试夹具修复遵循与生成时相同的 helpers 规则（脚本可执行，调用方式写在技能正文里）。应用行为确实坏了 → 产品缺口；记下来给用户，不要放进这个 PR。

6. **交付或停止。** 若为已变更：一个只含已证明更正的 PR，先重读每个改过的文件。若为干净或受阻：不要 PR，如实报告结果和覆盖情况。

把简洁的运行笔记（覆盖了的功能、够不着的前提、已确认的漂移、结果）放在一个临时位置；不要提交它们。
