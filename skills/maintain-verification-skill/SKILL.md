# 维护验证技能

应用一改，功能地图就开始烂。这个技能是维护循环，用来维护由 `/create-verification-skill` 生成的技能（或任何带功能地图的项目本地验证技能）。严谨的单位是功能，不是每一句话：从源码覆盖每个功能文件，再现场跑一遍每个功能，不用把每一条都逐字验证。

## 结果

选一个，并说明是哪个：

- **clean** — 每个功能都拿到了源码覆盖和现场覆盖；没有值得发的东西。不开分支，不提 PR。
- **changed** — 一个 PR 发出经过证实的文档、harness 或地图修正。
- **blocked** — 覆盖没跑完，或者证实的修复没法安全发出。说清楚到底是什么卡住了。

## 编辑范围

只改验证技能自己的目录（它的 SKILL.md、features/，以及它拥有的 harness 脚本）。运行期间绝不改产品代码：地图描述的行为应用已经不做了，要么是文档漂移（改地图），要么是产品回归（报告出来，别在文档里糊过去）。

## 流程

0. **定位目标。** 找到要维护的验证技能：项目本地技能，正文里有启动/驱动章节和功能地图（通常是 `.cursor/skills/verify-*/`）。有多个候选就问是哪个；一个都没有就停下，指向 `/create-verification-skill`，别自己编一个目标。

1. **索引卫生。** 读功能地图 README，glob 它的同级文件。修掉缺失、多余、重复或失效的条目。轻量处理，不生成清单。

2. **源码波次。** 每个功能文件一个只读子智能体，并发启动。每个子智能体从源码回答"这个面向用户的功能是怎么工作的？"，带引用标出可能的文档漂移，并返回一份简洁的现场验证配方。子智能体绝不驱动应用，也绝不改文件。返回格式：功能摘要 / 源码入口 / 可能的漂移或无 / 一份配方。

3. **对账。** 每个功能文件都有返回的摘要。把重叠的配方合并成尽量少的应用状态。抽查被引用的漂移；对干净的结论不重新证明。扫一遍最近的改动，找地图里缺的面向用户的面，认定缺失之前必须给出具体的源码路径。

4. **现场跑。** 即使源码看起来干净也必须做。协调者负责所有驱动；遵循验证技能自己的启动模型：服务器和 UI 用一个长期存活的实例串行驱动，短命的 CLI 每次驱动用一个全新的隔离会话（由技能的 Launch 章节决定，不是这里）。每个功能至少跑一次，整个过程中无论出什么故障都守住三条不变量：(1) 绝不驱动一个自上次出现意外行为后没做过健康检查的实例：首次驱动前 doctor，以会话为单位的场景每个新会话都 doctor，任何一次驱动失败后再 doctor，doctor 看不到的故障（进程健康但 UI 卡死）就重置到已知状态或重启，别赌；(2) 已经拿到的证据要扛过每一次清理，到它该在的位置去查，不能假设；(3) 驱动启动的东西不能比这次驱动有用期活得更久：失败迭代的残留要清掉，不管会话是卡住、已退出还是共享的（共享实例就清残留，不动实例）。技能漂移导致的 doctor 失败就是漂移：在编辑范围内修掉，重试一次，只重启被这次修复作废的东西，别多动，然后再决定这次跑是不是 `blocked`。够不着的功能只有给出具体前置条件（认证、权限、操作系统、外部状态）和尝试过的路径，才能标 `verified-unreachable`；地图漏了这个前置条件，那就是漂移。triage 出来的 harness 修复，发出前要重新现场驱动一遍。最终清理放在本次运行最后一次驱动之后，包括那些重新证明，这样没有东西活过这次运行（证据按技能规定保留）。

5. **Triage。** 用户视角的描述错了或缺了 → 文档漂移，修。行为正常但 harness 驱动不了 → harness 缺口，修；harness 修复遵循和生成时一样的 helpers 规则（脚本可执行，调用方式写在技能正文里）。应用行为确实坏了 → 产品缺口；记下来给用户，别放进这个 PR。

6. **发出或停下。** changed：一个 PR 装经过证实的修正，发之前把每个改过的文件重读一遍。clean 或 blocked：不提 PR，如实报告结果和覆盖情况。

在一个临时位置留简洁的运行记录（覆盖了哪些功能、够不着的前置条件、确认的漂移、结果）；不要提交。
