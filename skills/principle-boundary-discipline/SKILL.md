# 边界纪律

把校验、类型收窄和错误处理放在系统边界。无条件信任内部代码。业务逻辑住在纯函数里。外壳薄，而且机械。

**为什么：** 散落的校验吵、重复，并且给人虚假的安全感。把逻辑留在框架接线之外，这样不靠框架也能测试。

**模式：**
- **在边界上**（CLI 参数、配置文件、外部 API、网络协议）：校验，返回错误，防御性地处理。
- **在系统内部：** 类型化的数据，错误向外传播，不再重新校验。信任类型。
- **跨越边界时。** 暴露领域概念，而不是边界私有的表示。通用机制留在内部，专用策略放在边缘。

**应用：**

校验与错误处理：
- 在解析时校验配置（那是边界），而不是在业务逻辑内部
- 在边界把原始数据解析成领域类型
- 不要把传输、存储、框架或线路类型通过公共表面再导出
- 如果边界已经校验过，调用链深处不要再做多余的 nil 检查

代码组织：
- 业务逻辑放在没有框架依赖的纯函数里
- 解析函数：从原始字节到类型化状态的纯变换
- 提示词构造：结构化状态进去，字符串出来
- 评分与评估：从状态到结果的纯变换

**检验：**
- “这份数据此刻正在越过系统边界吗？”如果不是，校验就是多余的。
- “这能不能做成一个纯函数，让外壳只负责调用？”如果能，就抽出来。
