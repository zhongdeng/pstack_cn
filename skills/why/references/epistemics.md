# 认识论

当证据是历史性的、碎片化的、有时还互相矛盾时，该怎么判断置信度，以及怎么告诉用户而不把它压平成虚假的确定性。代码展示的是它做了什么，而不是*它为什么存在*。为什么存在于提交、PR、工单、文档和对话里，这些全都不完整、有偏差，有时干脆缺失。假装不是这样，就会产出听起来很笃定的猜测，把用户带偏。

## 置信度分层

输出里的每一条论断都必须落在某一层。层级决定了它放在哪一节、用什么措辞。

### 1. 直接

有一条明确的、文本化的引用回答了问题：作者真正*写下*的、说明了原因的东西，而不是“代码做了 X，所以作者肯定想要 X”。比如，PR 描述里写“这修复了用户超过 1000 个条目时无法分页的 bug”，工单里写“我们加这个是因为客户 Acme 在他们的安全审查里提了要求”，代码注释里写“// 钳到 100，因为上游 API 拒绝更大的值”，设计文档里写“我们选了方案 A 而不是方案 B，因为我们需要跨重启的持久化”，或者作者的一条聊天消息“换成这个方案，因为旧方案在测试里不稳定”。

措辞：笃定，现在时，带引用。“这之所以存在，是因为 X。”

### 2. 有支撑

多条间接证据汇聚到同一个结论。没有任何单一来源明确说出来，但跨来源的模式让它很可能成立。比如，PR 标题写“提升性能”，工单标了“perf”，周围的提交全都动同一条热路径。或者随改动一起加的若干测试全都在跑非常大的输入。或者作者同一周的其他 PR 全都提到同一起事故。

措辞：笃定但明确是推导出来的，逐条引用。“证据强烈指向 X：[具体的几条]。”

### 3. 推断

对上下文的一种合理解读，没有任何东西明确支撑它。这是*你的解读*，不是记录里的事实。比如，PR 没说为什么，但错误当时正在生产环境发生（根据事故频道的时间线），而且修复很仓促（当天就合了），所以它很可能是个热修。或者函数名暗示是重试逻辑，而它的重试次数 3 和代码库里别处团队惯用的 3 次重试约定一致。

措辞：留有余地，把推理链摆明。“给定 A 和 B，C 看起来很可能，因为 D。”

### 4. 猜测

证据薄弱下的一个合理假设，别的解释也同样说得通。值得摆出来，因为用户可能知道哪个对，但要标明这是猜测。比如，“这可能是针对某个浏览器 bug 的绕过方案，那个 bug 后来已经修了，但我们没找到当时的证据”，或者“这个阈值有可能是为了对齐某个 SLA 承诺而选的，但没有任何 SLA 文档提到它。”

措辞：“一种可能是 X，但我们没有直接证据。”通常放在竞争假设里，和其他可能性并列。

### 5. 未知

你查了，但查不出来。这是一个有效且重要的结果。把它记录下来。

措辞：“我们搜了 X、Y 和 Z，没找到关于原因的证据。”要具体说明你搜了*什么*。“我们查不出来”不如“我们用关键词 A 和 B 搜了工单系统，扫了 2023 年以来动过这个文件的 6 个 PR，还在仓库里 grep 了匹配该阈值的字符串字面量。都没有浮出任何理由”有用。

## 措辞指南

**置信词**暗示是直接或有支撑的证据，必须紧挨着一条引用。绝不要用在推断上：“因为”、“原因是”、“是为了”（断言作者意图）、“修复了”/“解决了”/“处理了”（断言改动达成了目标）、“团队决定”（断言发生过一次集体决策）。

**模糊语**表示这是解读，不是陈述。在“我们能合理推断什么”里大胆用：“看起来”、“似乎”、“很可能”、“暗示”、“与……一致”、“一种读法是”、“说得通的是”、“可能是”、“证据指向”。

**要避免的词：**

- “显然”。如果真显然，用户就不会问了
- “很明显”。几乎总是出现在一条并不明显的论断前面
- “当然”。同上
- “只是”（比如“这只是为了性能”）。轻慢，而且通常掩盖了不确定性
- “我认为”/“我相信”。你是在综合证据，不是在给个人意见。改用“证据表明”。

## 避免合理化

今天看起来“说得通”的代码，当初可能是出于已经不再适用的理由写的，或者当时就是错的。别给混乱的历史硬套一个干净的理由。别假设作者做了“对”的事，再倒推去给它找依据。别假设一个一致的模式是有意为之，它可能是复制粘贴。别把证据的缺失变成缺失的证据（“没人提过安全顾虑，所以肯定不是顾虑”）。

## 谄媚陷阱

用户常常夹带一个假设：“我们为什么这么做，我猜是为了性能？”别直接确认它。这个猜测是让你去调查的提示，不是要你去验证的结论。把它当作众多候选之一，独立去核对证据。如果证据支持它，就带引用地说支持。如果不支持，就说不支持，并摆出证据*确实*支持的东西。

## 当证据互相矛盾

在输出里把两个来源都摆出来，带引用。别挑那个更符合整洁叙事的。比如，工单说“我们需要这个是为了客户 X 的合规要求”，PR 说“清理这块的技术债”。两者可能都对（工单是这项工作的动因，PR 是作者给的框定），也可能有一个是错的。让用户来定。

## 当证据缺失

一句诚实的“我们不知道”是最有价值的输出之一。用户由此知道答案不在显而易见的地方，知道他们得去问人（原作者、产品负责人、团队负责人），或者知道他们可以判定这个问题不值得再追下去。不标出缺口、反而用一个笃定的猜测去填，是在实实在在地害用户，因为他们会照着这个猜测行动。把每个缺口具体地写出来：问题是什么、搜了哪些来源、在每个来源里搜了什么、找到了什么（什么都没有，或者只有边角料）。

## 定稿之前

在综合者交付输出之前，它会检查“我们发现了什么”和“我们能合理推断什么”里的每一条论断。每条论断要么带引用，要么挪到推断或假设里。它的措辞和它的层级匹配。它不把代码当作代码自身意图的证据（如果这么做了，删掉或重新归类）。输出里有一个“我们不知道什么”小节。如果没提到任何缺口，那很可疑。要么是证据异常完整，要么是有东西被扫到地毯下面了。
