# 认识

当证据是历史的、碎片的、有时相互矛盾时，如何推理置信度，以及如何告诉用户，而不把它压扁成虚假的确定。代码显示它做什么，不显示*它为什么存在*。为什么活在提交、PR、工单、文档和对话里，全都是不完整的、有偏向的，有时还缺失。假装不是这样，就会产出听起来很有信心、却误导用户的猜测。

## 置信层级

输出里的每一条说法都必须落在一个层级里。层级决定它的节和它的措辞。

### 1. 直接

一条明确的、文字上的引用回答了问题：某个作者实际*写下*的、说出为什么的东西，而不是「代码做了 X，所以作者一定想要 X」。例如，一条 PR 描述「这修复了用户有超过 1000 项时无法分页的缺陷」，一张工单「我们加上这个，是因为客户 Acme 在他们的安全审查里要求了它」，一条代码注释「// 钳到 100，因为上游 API 拒绝更大的值」，一份设计文档「我们选了方案 A 而不是方案 B，因为我们需要跨重启的持久化」，或来自作者的一条聊天消息「改用这种做法，因为旧的在测试里不稳定」。

措辞：有信心，现在时，带引用。「这之所以存在，是因为 X。」

### 2. 印证

多条间接证据收敛到一个结论。没有单一来源明确说出它，但跨来源的模式使它很可能。例如，PR 标题说「提升性能」，工单标了「perf」，周围的提交全都碰到同一条热路径。或者随这次改动加上的几个测试全都在操练非常大的输入。或者作者同一周的其他 PR 全都点名同一次事故。

措辞：有信心，但明确是推导出来的，并引用每一项。「证据强烈指向 X：［那些具体的片段］。」

### 3. 推断

对上下文的一种合理读法，没有任何东西明确支持它。它是*你的解释*，不是记录里的事实。例如，PR 没有说为什么，但错误当时正在生产中发生（按事故频道的时间），而且修复很赶（当天就合并了），所以它很可能是一次热修。或者函数名暗示重试逻辑，而它的重试次数 3 与团队在代码库别处的 3 次重试惯例相符。

措辞：有保留，推理链写明。「给定 A 和 B，C 看起来很可能，因为 D。」

### 4. 推测

在稀薄证据上的一个说得通的假设，其他解释同样合适。值得呈现，因为用户可能知道哪个是对的，但要把它标成猜测。例如，「这可能是对一个此后已经修好的浏览器缺陷的绕过，但我们没有找到当时的证据」，或「这个阈值有可能是为了匹配一项 SLA 承诺而选定的，但没有 SLA 文档提到它。」

措辞：「一种可能是 X，但我们没有直接证据。」通常活在相互竞争的假设里，和其他可能性并排。

### 5. 未知

你找过了，没能弄清。这是一个有效的、重要的结果。把它记下来。

措辞：「我们搜了 X、Y 和 Z，没有找到为什么的证据。」具体说明你搜了*什么*。「我们没能弄清」不如「我们用工单跟踪器搜了关键词 A 和 B，扫了自 2023 年以来碰过这个文件的 6 个 PR，并在仓库里 grep 了与该阈值匹配的字符串字面量。没有任何一处浮现出理由。」更有用。

## 措辞指南

**置信用词**意味着直接或印证的证据，并且紧挨着就要有引用。绝不要用它们来表达推断：「因为」「原因是」「设计出来就是为了」（声称作者意图）、「修复了」/「针对」/「解决了」（声称这次改动达成了它的目标）、「团队决定」（声称发生过一次集体决定）。

**保留用语**表示解释，不是报告。在我们可以合理推断的里面放开用：「看起来」「似乎」「很可能」「提示」「与……一致」「一种读法是」「说得通」「可能曾经是」「证据指向」。

**要避开的词：**

- 「显然」。如果真那么显然，用户就不会问
- 「明显」。后面几乎总是一个并不明显的说法
- 「当然」。同上
- 「不过就是」（如「这不过就是为了性能」）。轻飘，而且通常藏着不确定
- 「我觉得」/「我相信」。你是在综合证据，不是在发表个人看法。改说「证据表明」

## 避免合理化

今天「说得通」的代码，可能是为了已经不再适用的理由而写的，或者当时就是错的。不要把一条干净的理由回套到凌乱的历史上。不要假定作者做了「对」的事，然后倒推去为它辩护。不要假定一种一致的模式是有意的，而它可能是复制粘贴。不要把证据的缺失变成缺失的证据（「没有人提到安全顾虑，所以它一定不是一项顾虑」）。

## 迎合陷阱

用户常常嵌进一个假设：「我们为什么这样做，我猜是为了性能？」不要简单地确认它。这个猜测是调查的提示，不是要去验证的结论。把它当作候选之一，并独立地检查证据。如果证据支持它，带引用这样说。如果不支持，也这样说，并呈现证据*确实*支持的东西。

## 当证据相互矛盾

在输出里把两个来源都摆出来，带上引用。不要挑选那个更适合一个更整齐叙事的。例如，工单说「我们需要这个，因为客户 X 的合规要求」，PR 说「清理这块的技术债」。两者都可能为真（工单推动了这项工作，PR 给出了作者的说法），或者其中一个可能是错的。让用户来判断。

## 当证据缺失

一个诚实的「我们不知道」是最有价值的输出之一。用户由此知道答案不在那些明显的地方，他们需要去问一个人（原作者、产品负责人、团队负责人），或者他们可以决定这个问题不值得再追。没有标出缺口，反而用一个有信心的猜测去填它，会主动伤害用户，因为他们会按这个猜测行动。具体地点名每一个缺口：问题、搜过的来源、你在每一个里搜了什么，以及你找到了什么（什么都没有，或只有沾边的材料）。

## 定稿之前

在综合者交出输出之前，它检查「我们发现的」和「我们可以合理推断的」里的每一条说法。每一条说法都有引用，或者移到推断或假设。它的措辞与它的层级相符。它不把代码当作其自身意图的证据（如果这样做了，就去掉或重新归类）。输出有一节「我们不知道的」。如果没有提到任何缺口，那就可疑。要么证据异常完整，要么有什么被扫到了地毯下面。
