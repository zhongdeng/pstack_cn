# Notion 文档

## 这个来源包含什么

- PRD（产品需求文档）
- 技术规格和 RFC
- 架构决策记录（ADR）
- 设计评审的会议笔记
- 带有领域上下文的团队页面
- 事故复盘
- 可能解释防御性代码的 runbook
- 设定优先级的策略文档

Notion 是“为什么”在变成代码之前，常常以长文存在的地方。一个重要功能通常会有一份文档。

## 如何搜索

使用 Notion MCP。

1. **用 `notion-search` 做关键词搜索。** 试这些：
   - 功能名
   - 目标代码里的关键符号 / 类名
   - 作者账号（设计文档常常在代码落地之前就写好了）
   - 错误字符串或用户可见的术语
   - 如果你知道代码何时发布，做有时间边界的查询
2. **用 `notion-fetch` 取回候选页面。** 读全文，不要只读预览。理由常常埋在文档中部。
3. **顺着反向链接和子页面走。** 设计文档常常有子页面，写考虑过的替代方案、附录或实现笔记。
4. **检查相关数据库。** `notion-query-data-sources` 和 `notion-query-meeting-notes` 可以找出讨论过这个决定的会议笔记。
5. **搜索作者自己的空间。** 如果 PR 作者有个人笔记本（有些公司很常见），里面可能有先于代码的探索性思考。

## 这里的好证据长什么样

- 一份 PRD，带有与目标代码目的相匹配的 “Problem statement” 或 “Motivation” 一节
- 一节 “Alternatives considered” 或 “Rejected approaches”
- 一份复盘，把目标代码点名为某次具体事故的修复
- 会议笔记记下 “we decided X because Y”，并且作者/日期范围与 PR 相同
- 一份被认真填过的 ADR 模板（状态、上下文、决定、后果）

## 常见陷阱

- **过时的文档。** 规格常常在实现之前写好，之后不再更新。文档描述的可能是一个已经变了的计划。对照实际的 PR 交叉检查。
- **文档与现实的漂移。** 规格可能说“我们将做 X”，代码实际做的是 Y。标出这个分歧。综合者会把矛盾摆出来。
- **套话模板。** 有些组织要求一个 “Why” 节，填进去的是空话。找具体的东西。
- **没有被链接的文档。** 最相关的文档可能哪里都没链到。宽一点的关键词搜索有帮助。
- **多份草稿。** 如果一个主题有多份文档，找出定稿的或最近更新的那份。核对日期。
- **访问受限的页面。** 如果一个页面你访问不了，把它记成缺口。

## 要返回什么

对每一份相关文档：
- 标题和 URL
- 作者和最后更新日期
- 动机文本（逐字引用），以及页面/章节位置
- 相关的链接页面（这样综合者可以引用它们）
- 这份文档是定稿还是草稿
