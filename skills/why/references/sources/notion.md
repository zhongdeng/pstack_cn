# Notion 文档

## 这个来源包含什么

- PRD（产品需求文档）
- 技术规格和 RFC
- 架构决策记录（ADR）
- 设计评审的会议记录
- 带领域背景的团队页面
- 事故复盘
- 可能解释防御性代码的 runbook
- 设定优先级的策略文档

在 Notion 里，"为什么"常常以长文形式存在，之后才变成代码。一个重要的功能通常都有一份文档。

## 怎么搜

用 Notion MCP。

1. **用 `notion-search` 做关键词搜索。** 试试：
   - 功能名称
   - 目标代码里的关键符号 / 类名
   - 作者 handle（设计文档常常在代码落地之前就写好了）
   - 错误字符串或用户可见的术语
   - 如果你知道代码什么时候上线的，加上时间范围
2. **用 `notion-fetch` 拉取候选页面。** 读全文，不要只看预览。理由常常埋在文档中间。
3. **顺着反向链接和子页面走。** 设计文档常常有子页面，讲考虑过的替代方案、附录或实现说明。
4. **查相关数据库。** `notion-query-data-sources` 和 `notion-query-meeting-notes` 能翻出讨论过这个决策的会议记录。
5. **搜作者自己的空间。** 如果 PR 作者有个人笔记本（有些公司很常见），里面可能有代码之前的探索性思考。

## 这里的好证据长什么样

- 一份 PRD，它的 "Problem statement" 或 "Motivation" 部分和目标代码的目的一致
- 有 "Alternatives considered" 或 "Rejected approaches" 部分
- 一份复盘，把目标代码点名为某个具体事故的修复
- 会议记录里写着 "we decided X because Y"，并且作者/时间范围和 PR 对得上
- 一份认真填写的 ADR 模板（status、context、decision、consequences）

## 常见坑

- **过时的文档。** 规格常常在实现之前写，之后不更新。文档描述的可能是已经变了的计划。和实际的 PR 交叉核对。
- **文档和现实脱节。** 规格可能说"我们要做 X"，但代码实际做的是 Y。把这个分歧标出来。综合环节会暴露这个矛盾。
- **模板化的套话。** 有些组织要求写一个 "Why" 部分，结果被填满空话。找具体的内容。
- **没被链接的文档。** 最相关的文档可能哪里都没链到。广撒网的关键词搜索有帮助。
- **多个草稿。** 如果一个主题有多份文档，找定稿的那份或最近更新的那份。看日期。
- **有访问限制的页面。** 如果你访问不了某个页面，把它记为一个缺口。

## 返回什么

对每份相关文档：
- 标题和 URL
- 作者和最后更新日期
- 动机部分的文字（逐字引用），附上页面/章节位置
- 相关的链接页面（方便综合环节引用）
- 文档是定稿还是草稿
