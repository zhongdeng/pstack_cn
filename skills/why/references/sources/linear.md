# Linear 工单

## 这个来源包含什么

- 描述功能、bug 及其动机的 issue
- 附在 issue 上的项目文档（通常是 PRD 或规格说明）
- 父/子 issue 关系（更大的计划 → 具体工单）
- issue 上的评论（澄清、范围变更、"我们为什么做这个"的理由）
- 标签（例如 `compliance`、`customer-request`、`perf`），用来标示动机的类型
- 解释范围变更的状态更新
- 附件和关联的 GitHub PR

Linear 往往是产品/业务背景所在的地方：也就是"我们做这个是因为客户 X 提了"或者"这是为了 Q3 合规计划"这一层。

## 怎么搜

用 Linear MCP。

1. **从关联工单入手。** 如果种子 commit 或 PR 引用了工单 ID（例如 `ENG-1234`、`[BUG-567]`），先用 `get_issue` 拉取这些工单。读完整的 issue，包括评论。
2. **按关键词列出相关 issue。** 用 `list_issues` 按功能名、关键符号或业务术语做文本搜索。多试几种说法。
3. **沿 issue 树往上走。** 如果你落到一个子 issue 上，就拉取它的父 issue。子 issue 是战术层面的。父 issue 往往承载着"为什么"。
4. **读项目文档。** 如果这个 issue 属于某个项目，用 `get_project` 并检查附带的文档。项目级文档是最常记录规格和理由的地方。
5. **看标签和里程碑。** 标签暗示动机的类别（customer-request、incident-followup、compliance）。里程碑把工作和截止日期绑在一起，这往往能揭示动机。

## 这里什么样的证据算好

- issue 描述里写明了业务问题："客户 Acme 需要 X，因为他们的 SOC2 审计"
- 一条评论记录了决策："我们决定采用方案 B，因为方案 A 需要改动计费服务"
- 一个标题像计划的父 issue："Q3 Enterprise Readiness" 或 "Reduce Payment Failures"
- 附带的 PRD 或规格说明
- 像 `customer:acme`、`incident-followup`、`compliance`、`perf-regression` 这样的标签

## 常见坑

- **范围漂移。** PR 引用的那个工单可能被关闭后又以不同的范围重新打开。要读完整的历史。
- **机械模板。** 有些团队要求写"为什么"部分，但填的是套话。泛泛的文字（"提升用户体验"）大概率不是真正的答案。
- **过时的工单。** 旧工单往往反映的是已经变化了的计划版本。核对日期，并和代码的上线日期交叉比对。
- **关闭为重复的链条。** 沿着 duplicate-of 关系回溯到那个标准工单。
- **私有工作区内容。** 如果你访问不了某个 issue，把它记为一个缺口，而不是去猜。

## 返回什么

对每个相关工单：
- 工单 ID 和标题
- 从描述或评论中引用的原话，说明问题/动机（不要转述。综合环节需要原文来引用）
- 标签、父 issue、项目
- 作者、创建日期、关闭日期
- 工单链接（如果有的话）
