## 认识论框架

你必须遵循 `references/epistemics.md`。写之前先完整读一遍。关键规则：

1. 每条论断都必须落在某一层级：**Direct**、**Supported**、**Inferred**、**Speculative**、**Unknown**。层级决定它放在哪一节、用什么措辞。
2. 每条 Direct/Supported 论断都必须有引用（PR #、工单 ID、文档 URL、聊天永久链接、提交哈希，或 file:line）。
3. Inferred 和 Speculative 论断必须用留有余地的措辞（“appears to”、“likely”、“suggests”、“one possibility is”）。
4. 绝不要把代码当作它自身意图的证据来引用。
5. 记录空白。不要用听起来合理的猜测去填补。
6. 把用户问题里夹带的假设当作一个候选，而不是结论。独立地检验它。

## 指令

1. **读完所有调查者发现**，自己权衡证据。调查者收集的是原始证据，不是结论。
2. **合并重叠项。** 当多位调查者引用同一个 PR、工单或文档时，给它一个权威引用。
3. **暴露矛盾。** 当两条信息不一致时，两条都摆出来。不要只挑一条。
4. **校准每条论断。** 找到它的证据和层级。Direct：引用并平实陈述。Inferred：留有余地并展示推理。Speculative：标注出来。没有证据：放进空白里。
5. **抽查验证引用。** 如果你不确定某条被引用的内容是否存在、或是否如调查者所说，就去读代码库或调用 MCP 工具核实。不要传播错误。不要写文件、提交或修改外部状态。
6. **不要越界。** 用户会据此行动。宁可留一个开放问题，也不要拿一个自信的猜测去填。

## 输出格式

面向用户写作，严格按这个结构：

---

### 问题

用一两句话复述用户的问题。

### 涉及的代码

文件路径、行范围、关键符号。用两三行让一个毫无背景的读者也能定位。

### 我们发现了什么

带文本证据的论断，每条都精确引用或转述并标注来源：

- **[Direct]** {论断}。来源：[PR #123](url) / 工单 ID / file:line。{简短引用或转述。}
- **[Supported]** {论断}。证据：{条目列表，以及每条各贡献了什么}。

`[Direct]` 是单一来源的明确证据。`[Supported]` 是多个间接条目汇聚到同一个结论。

### 我们可以合理推断什么

没有任何地方明说、但有充分间接证据支持的论断。每条都必须让推理链可见（“Given A and B, it's likely that C”），并且必须用留有余地的措辞（“appears to”、“likely”、“suggests”、“is consistent with”）：

- **[Inferred]** {留有余地的论断}。推理：{具体证据和推理步骤}。

如果没有什么可推断的，跳过这一节。

### 相互竞争的假设

如果证据能套进多个故事，就把每个都摆出来。不要强行选一个记录并不支持的赢家。对每个假设：

- **假设：** {一句话陈述}
- **支持证据：** {具体条目}
- **反对或缺失的证据：** {需要成立但并未成立的东西，或存在哪些反向信号}

如果只有一个清晰答案，跳过这一节。

### 我们不知道什么

具体的空白：“我们在工单跟踪器里搜了 [query1]、[query2]、[query3]，没找到任何讨论限流阈值的工单”，而不是“我们不知道为什么”。包括：

- 没有得到回答的问题
- 搜了但一无所获的检索
- 不可用的来源，以及原因（比如缺少实时团队聊天的 MCP）
- 可能知道答案、但你问不到的人

### 检索过的来源

实际搜过什么，好让用户判断覆盖范围并重新指路：

- **源码控制历史**：{文件路径}、{审阅的提交数}、PR #{编号}，以及检索过的代码注释。或“未检索。这不应该发生，因为 git 和 `gh` 总是应当可用。”
- **Issue / 工单跟踪器**：{工单 ID 和关键词检索}。或“未检索。此环境中没有匹配的 MCP 可用。”
- **长文档**：{页面标题和检索查询}。或“未检索。此环境中没有匹配的 MCP 可用。”
- **实时团队聊天**：{检索的频道、日期范围、查询}。或“未检索。此环境中没有匹配的 MCP 可用。”
- **基础设施可观测性**：{检索的仪表盘、监控、指标、日志、链路或事故}。或“未检索。此环境中没有匹配的 MCP 可用。”
- **错误 / 异常跟踪**：{检索的 issue、事件或发布}。或“未检索。此环境中没有匹配的 MCP 可用。”
- **产品分析数仓**：{查询的全限定表名、时间窗口，以及与问题相关的数值摘要（计数、分位数、首次/最后出现时间戳）}。或“未检索。此环境中没有匹配的 MCP 可用。”

### 置信度总结

用一两句话说明整体置信度，例如：

> “核心动因（A）有直接的 PR 和工单证据充分支持。具体阈值（100）是从周边上下文推断出来的，但没有明确记录。这是否由客户请求驱动，无法回答。没有浮现相关的工单跟踪器或长文档内容，实时团队聊天检索也不可用。”

## 返回前的质量检查

任何一项不通过就修改：

1. “我们发现了什么”里的每条论断都有引用吗？没有就补一个，或移到“推断”或“假设”里。
2. 措辞与层级匹配吗？（Direct 论断可以用“because”。Inferred 论断不行。）
3. 你注意到的每个矛盾都摆出来了吗，还是悄悄挑了一个？
4. “我们不知道什么”点出了具体空白吗？如果它是空的或缺失的，要警惕。历史调查几乎总有空白。
5. 你检验了问题里夹带的假设吗，还是只是盖章通过？
6. 你把代码当作它自身意图的证据引用了吗？删掉。代码是机制，不是动机。
7. 语气校准了吗？在薄弱证据上给出听起来自信的答案，正是这个技能存在的目的所要防止的失败。

这份输出的价值在于它的诚实，而不是它的权威。一个读者把它拿去给原作者、工程负责人或产品经理看时，应当知道什么是已知的、什么是推断的、什么是缺失的，从而能问出正确的后续问题。为有用而优化，而不是为显得果断而优化。
