# Architect

用 `not implemented` 的函数体和伪代码勾出类型、函数签名、类的形状和模块边界。综合多个模型的视角，然后按照选定的草图填充代码。

## 开始

开始之前先开一个 todolist，每个阶段一条。

1. Ground
2. Sketch
3. Agree
4. Implement
5. Scrap

## 阶段 A：把问题摸清

对新代码会碰到的每个系统建立真实的心智模型。对相关子系统跑 **how** 技能。说出一个文件名不叫摸清。产出 `how` 要求的架构解释。如果这次设计重新定义了归属或分层，还要对现有形状跑 **why** 技能，让背后的理由变成约束，而不是猜测。

只有当工作确实是全新的、周围没有需要集成的系统时，才跳过阶段 A。

## 阶段 B：画草图

用设计草图任务和阶段 A 的摸底产物跑 **arena** 技能。把 `references/runner-prompt.md` 作为每个 runner 的 prompt 传进去。

runner 取自 `pstack-models.mdc` 规则里的 `architect runners` 那一行，用来代替 `arena runners` 那一行。如果规则或那一行不存在，就用 `claude-opus-5-5-xhigh` 和 `grok-4.7-xhigh-fast`。别名和被拒绝的条目按 **arena** 技能阶段 A 里的 runner 规则处理。

设计两遍。综合之前至少要有两个结构上不同的候选方案，哪怕第一个看起来就够了。这是把 **exhaust-the-design-space** 原则技能落到实处。要的是整体形状的替代方案，不是在一个形状里做点状修补。

综合之前，每个候选方案都要对照 [`references/design-red-flags.md`](references/design-red-flags.md) 筛一遍。假设下一个贡献者是个智能体，它只看得到自己打开的文件，会照抄最近的例子，会走能编译的最短路径。优先选那种从单个文件看是对的改动、放到整个仓库也对的设计。

在接口深度上比较可行的候选方案。优先选把更多复杂度藏在更小、更简单的公开接口后面的设计。丰富的接口可以通过集中能力而不是把能力散到各层，让调用链保持短。

Arena 返回一个综合后的设计包。它的综合决策填进理由文档的 "Synthesis decision" 一节。

## 阶段 C：达成一致（可选）

默认：拿着综合后的设计直接进入实现。没有人工检查点。

当调用方明确要求时才开启检查点："/architect with checkpoint"、"stop and show me before implementing"，或类似说法。这时把综合后的设计摆出来，停下来等签字。

无论哪种方式，综合结果都可以作为单独的 commit 提交，也就是 **foundational-thinking** 原则技能的 "scaffold first" 模式。按 **outcome-oriented-execution** 原则技能，填充过程中有计划、有范围的破坏是可以的。想在实现之前对设计施加对抗性压力，就对综合后的草图跑 **interrogate** 技能。

如果人对形状有异议（在检查点时或事后），把这当作阶段 A 的证据。重新摸底、重新跑阶段 B，然后再写更多代码。

## 阶段 D：按草图实现

把 `not implemented` 的函数体换成代码，把伪代码换成逻辑。综合后的草图就是契约。偏离它是需要摆到台面上的信号，不是可以默默吞掉的摩擦。如果某个函数需要一个草图没预料到的参数，问清楚是草图错了、需求漏了，还是实现越界了。

## 阶段 E：架构错了就扔掉

如果实现不断产生草图吸收不了的摩擦，就把草图扔掉。别往错误的设计上硬拧补丁，按 **redesign-from-first-principles** 和 **fix-root-causes** 原则技能来。

信号是*模式*，不是单个实例。迹象：

- 同一种形状的绕行方案在互不相关的代码里反复出现。
- 多个互不相关的边界情况都需要专门的分支。
- 类型需要逃生口（`any`、强制类型转换、实际上总会被赋值的可选字段）才能编译。
- 草图说状态不共享，却出现"我们需要一把锁"的条件反射。
- 调用方必须了解抽象的内部规则才能用它。
- 实现里出现两个或更多形状相同的、彼此独立的阶段 D 偏离。

用判断力。几个边界情况不足以给一个架构定罪。有些问题本来就复杂。数据里的复杂度不是设计里的复杂度。

要扔掉时：

1. 对已经建出来的东西重新跑 **how** 技能。
2. 把新约束当作第一天的假设重新设计，按 redesign-from-first-principles 来。
3. 先减后加，按 **subtract-before-you-add** 原则技能。新草图在长大之前应该比旧草图小。
4. 回到阶段 B，重新跑 arena。

## 输出

先写调用方的用法，再从用法推导出类型草图。小改动就一个文件，放新类型和签名。更大的工作给模块图加类型定义。理由文档一起交付，按 `references/rationale-template.md` 的形状来，包含用法草图和综合决策。
