# 架构

用 `not implemented` 的函数体和伪代码，勾出类型、函数签名、类的形态和模块边界。综合多个模型的视角，再按选定的草图把代码填进去。

## 开始

开始之前先开一份待办清单，每个阶段一条。

1. 摸清
2. 草图
3. 确认
4. 实现
5. 推倒

## 阶段 A：摸清问题

给新代码会碰到的每一个系统建立真实的心智模型。对相关子系统跑 **how** skill。点出一个文件名不算摸清。要产出 `how` 所规定的架构说明。如果设计会重定义所有权或分层，也对现有形态跑 **why** skill，让那份理由变成约束，而不是猜测。

只有工作确实是从零开始、周围没有要对接的系统时，才跳过阶段 A。

## 阶段 B：草图

带着设计草图这项任务和阶段 A 的摸底产物，跑 **arena** skill。把 `references/runner-prompt.md` 作为每个 runner 的 prompt 传进去。

runner 取自 `pstack-models.mdc` 规则里的 `architect runners` 那一行，用来代替 `arena runners` 那一行。规则或那一行缺失时，用 `claude-opus-5-5-xhigh` 和 `grok-4.7-xhigh-fast`。别名条目和被拒绝的条目，遵循 **arena** skill 阶段 A 里的 runner 规则。

把设计做两遍。综合之前至少要有两个结构上截然不同的候选，哪怕第一个看起来已经够用。这是把 **exhaust-the-design-space** 原则 skill 落实成具体做法。要的是整体形态的替代方案，不是在同一个形态里面打的点状补丁。

综合之前，对照 [`references/design-red-flags.md`](references/design-red-flags.md) 筛每一份候选。假定下一个贡献者是一个 agent：它只看自己打开的文件，抄最近的例子，走能编译通过的最短路径。优先选这样的设计：从一个文件看起来对的改动，对整个仓库也是对的。

按接口深度比较站得住的候选。优先选把更多复杂度藏在更小、更简单的公开表面后面的设计。丰富的接口可以把能力集中起来，从而让调用链保持短，而不是把能力散到各层。

Arena 返回一份综合后的设计包。它的综合决策填进理由说明的「综合决策」一节。

## 阶段 C：确认（选择加入）

默认：拿综合后的设计直接进入实现。没有人工检查点。

调用方明确要求时才加入检查点：「/architect with checkpoint」、「实现之前先停下来给我看」，或类似说法。然后把综合后的设计摆出来，停下来等签字。

无论哪条路，综合结果都可以作为它自己的一个 commit 交付，也就是 **foundational-thinking** 原则 skill 的「scaffold first」模式。填充期间有计划、有范围的破坏是可以的，见 **outcome-oriented-execution** 原则 skill。想在实现之前对设计施加对抗性压力，就对综合后的草图跑 **interrogate** skill。

如果人反对这个形态（在检查点上，或事后），就把它当作阶段 A 的证据。写更多代码之前，重新摸清并重跑阶段 B。

## 阶段 D：按草图实现

把 `not implemented` 的函数体换成代码，把伪代码换成逻辑。综合后的草图就是契约。偏离它是要摆到台面上的信号，不是默默吞掉的摩擦。如果某个函数需要草图没预料到的参数，就问：是草图错了，是需求漏了，还是实现越界了。

## 阶段 E：架构错了就推倒

如果实现一直产生草图吸收不了的摩擦，就把草图扔掉。不要往错误的设计上打补丁，见 **redesign-from-first-principles** 和 **fix-root-causes** 原则 skill。

信号是一种*模式*，不是单次出现。迹象：

- 同一种形态的变通在互不相关的代码里反复出现。
- 多个互不相关的边界情况，全都需要特殊分支。
- 类型得靠逃生口（`any`、强制转换、实践中总会被设上的可选字段）才能编译。
- 草图说状态并不共享，却冒出「我们需要一把锁」的本能反应。
- 调用方必须知道这个抽象的内部规则才能用它。
- 实现过程中出现两处或更多同一种形态的、彼此独立的阶段 D 偏离。

要靠判断。几个边界情况不足以否定一套架构。有些问题本来就复杂。数据里的复杂不是设计里的复杂。

推倒的时候：

1. 对已经建出来的东西重跑 **how** skill。
2. 把新约束当作第一天就有的假设来重新设计，见 redesign-from-first-principles。
3. 先减再加，见 **subtract-before-you-add** 原则 skill。新草图在长大之前，应该比旧的更小。
4. 回到阶段 B，重跑 arena。

## 产出

先写调用方的用法，类型草图从用法推导。小改动用一个文件写下新类型和签名。更大的工作用模块地图加上类型定义。理由说明一并交付，形态按 `references/rationale-template.md`，包括用法草图和综合决策。
