# 理由说明模板

和类型草图一起交付的正文。一页。标题用句首大写，不要套话。把斜体提示换成实际内容。

## 问题

*一段话。我们想做什么，以及现有系统或约束里的什么让这个形态并不显而易见。如果[阶段 A](../SKILL.md#phase-a-ground-the-problem)浮现出设计必须遵守的约束（要互通的现有类型、不能弄坏的调用方、越过我们边界的不变量），在这里点名，让读者看到和你一样的约束。*

## 用法（调用方视角）

*先写这个，再写类型草图。展示消费者会读到的 README 或快速上手，再加上他们自己代码里两三处真实调用点。他们导入什么、调用什么、返回什么。[形态](#shape)里的类型草图从这里推导。两者必须一致。不一致时，改草图去贴合用法，而不是反过来。调用方的体验就是规格。类型为它服务。*

## 形态

*推荐的架构。先写数据结构。再写数据如何流过这些签名。点名承重的决策。说明哪些不变量编码在类型里、校验放在哪里、系统刻意不做什么。明确评判接口深度。说明公开表面藏起了什么复杂度、还有什么暴露给调用方，以及为什么接口没有比需要的更大。每个决策引用它背后的原则（例如 `per boundary-discipline`）。不要把原则再复述一遍。*

## 综合决策

*由 [arena](../../arena/SKILL.md) 填写。记录哪个候选成了底稿以及为什么，从其他每一个改编了什么，拒绝了什么以及为什么。*

## 接受的权衡

*选定形态所做的每一项权衡一条。句式：「我们接受 X，以换取 Y。」把未来的读者可能误当成疏忽的东西点出来，包括看起来像过早优化或过早简化的东西。*

## 考虑过的替代方案

*必填。至少点名一个具体的替代形态，用一行说明它为什么落选。评判每个替代方案时看接口深度，不要只看实现简不简单。点名它暴露给调用方的复杂度，以及它藏起来的复杂度。设计空间里真有竞争者时，这里放两到三个替代方案。约束逼出答案时，一个就够，结论写成「这是唯一站得住的形态，因为……」。不要罗列同一形态的不同变体。这一节覆盖的是选定形态考虑过并拒绝的设计替代方案，不是其他 runner 候选。*

## 未决问题与风险

*草图期间你注意到的、需要人来权衡的事情，以及实现开始前值得标出来的风险。写成问题，不要写成断言，这样人的回答就是决议，而不是一条评论。*

## 下一步实现

*对着草图要先构建的第一件事。一句话。综合刚结束（或者如果选择加入了检查点，在阶段 D 签字之后）你会立刻动手写的东西。*
