# 理由模板

和类型草图一起交付的说明文字。一页。标题用句首大写，不要套话。把斜体提示换成实际内容。

## 问题

*一段话。我们要做什么，以及现有系统或约束的哪一点让这个形状不那么显然。如果 [Phase A](../SKILL.md#phase-a-ground-the-problem) 暴露了设计必须遵守的约束（要互操作的现有类型、不能破坏的调用方、跨过我们边界的不变量），在这里点名，让读者看到你看到的同一组约束。*

## 用法（调用方视角）

*先写这一节，再写类型草图。展示消费者会读的 README 或快速上手，加上他们自己代码里两三个真实的调用点。他们 import 什么，调用什么，拿回什么。[Shape](#shape) 里的类型草图是从这里推导出来的。两者必须一致。不一致时，把草图对齐到用法，而不是反过来。调用方的体验就是规格。类型为它服务。*

## 形状

*推荐的架构。先写数据结构。再写数据如何流经各个签名。点名承重的决策。说明哪些不变量编码在类型里，校验放在哪里，系统刻意不做什么。明确判断接口深度。说明公共表面隐藏了什么复杂度，还有什么暴露给调用方，以及为什么接口没有做得更大。每个决策都引用背后的原则（例如 `per boundary-discipline`）。不要复述原则本身。*

## 综合决策

*由 [arena](../../arena/SKILL.md) 填写。记录哪个候选成为基底以及为什么，从其他每个候选里吸收了什么，否决了什么以及为什么。*

## 接受的取舍

*选定的形状每做一个取舍写一条。形式是"我们接受 X，换取 Y"。点名未来读者可能误认为疏漏的地方，包括看起来像过早优化或过早简化的东西。*

## 考虑过的替代方案

*必填。至少点名一个具体的替代形状，用一行说明它为什么落选。每个替代方案都按接口深度来评判，不能只看实现是否简单。点名它暴露给调用方的复杂度和它隐藏的复杂度。设计空间里真有竞争者时，这里放两三个替代方案。约束逼出唯一答案时，一个就够，结论写成"这是唯一可行的形状，因为……"。避免罗列同一形状的不同变体。这一节讲的是选定形状考虑过并否决的设计替代方案，不是其他 runner 候选。*

## 未决问题和风险

*画草图时你注意到、需要人来权衡的事，以及实现开始前值得标出的风险。用问句写，不要用断言，这样人的回答就是结论，而不是一条评论。*

## 下一步实现

*照着草图要动手做的第一件事。一句话。综合之后（或者如果选择了检查点，在 Phase D 签核之后）你会立刻开始写的东西。*
