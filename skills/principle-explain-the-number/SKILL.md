# 解释这个数字

- **先写下决策，再跑。** 说清楚哪个结果会改变一个决策，以及噪声底。当跑与跑之间的波动比效应本身还大时，就停下。
- **问一句“为什么不是翻倍？”** 指出限制住结果的那个资源或代码路径，比如某个核、某把锁、磁盘、网络，或者负载生成器本身。从 profile 里拿，或者从跑的时候采的系统计数器里拿，再映射回源码。光读代码猜出来的不算限制因素。如果你说不出这个数字为什么没有好上一倍，那你就不清楚自己测了什么。
- **列出这个数字还可能测的是什么，然后逐条用证据排除。** 常见的嫌疑是：报错、被跳过或被缓存的工作、根本没跑到的代码、没调优的一侧（还留在默认设置上）、噪声，以及一块小到端到端根本看不出来的部分。
- **把证据和数字放在一起。** 把跑的次数、波动范围、限制因素写进笔记或链接的产物里。

对于性能数字，用 [benchmark-checklist](../benchmark-checklist/SKILL.md) 技能走完整流程。对于 eval 结果，对各个 trial 问同样的问题：每次跑都做了这个任务吗，差距在多个 trial 和模型上都成立吗，这个场景重要吗。

以下情况说明你跳过了这一步：一次跑开始时没有写下会改变决策的那个结果；一个数字背后的证据没有跑的次数、没有波动范围、也没有点名的限制因素；或者省下来的时间比改动那块本身花的时间还多。

这和 [Prove It Works](../principle-prove-it-works/SKILL.md) 不同，那个检查的是输出是不是真的。
