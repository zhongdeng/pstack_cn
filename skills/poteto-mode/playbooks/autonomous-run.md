### 自主运行

**退出条件由你负责。先定义完成，然后不停地开到那里。**

1. 在第一次迭代之前，把退出条件说成一个可检查的谓词（测试全绿、复现已修复、全部 N 个 PR 已合并、像素 diff 为零）。
2. 用 Cursor 的 `/loop` 命令选择唤醒机制（这是内建命令，不是 pstack 技能）。要盯的事件（CI、一次合并、一个 ref 在前进）配一个看守子代理，事件发生时唤醒你，并以基于时间的长心跳作为后备。没有事件时，用固定间隔的心跳，间隔按结果值得再查一次的时机来定。按子代理一节，为每个子代理选择这项工作所需的推理档位，以及 fast 或 standard 速度。
3. 每次迭代做证据所支持的最小改动，对照谓词验证，有推进就提交，没有帮助的改动丢掉。那些「也许有用」的双保险要回退，不要留着搭车走。
   通过 **sequence-verifiable-units** 原则技能来安排工作顺序，先验证每个单元再进入下一个，而不是把检查攒到最后。
4. 运行中途的发现归你。坏掉的技能、相关缺陷、不稳定的验证器、审查噪声、工具失败、孤儿后续，以及可修的漂移，都由你通过 poteto-mode 自己处理。把主线之外的修复放进它们自己的 PR。不要把可逆的工作停给人，也不要使用 `AskQuestion`。只上报不可逆动作、实验无法裁定的真正产品或偏好决定，或真正的死胡同。让谓词保持为主要驱动力，每次旁路修复之后回到它。
5. 每次迭代都通过 **show-me-your-work** 技能做检查点，一行记录变了什么、谓词有没有动。
6. 谓词满足时停止。平台期不是停止，所以继续，并换一种做法冲过它。上报真正的死胡同，而不是空转，并且绝不要放宽谓词来宣布胜利。

**回复：** 退出条件、跑了多少次迭代、合入了什么、丢掉了什么、谓词的最终状态。
