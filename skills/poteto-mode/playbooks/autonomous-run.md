### 自主运行

**退出条件由你负责。先定义完成，然后不停顿地推进到完成。**

1. 在第一次迭代之前，把退出条件写成一个可检查的谓词（测试全绿、复现问题已修复、N 个 PR 全部合并、像素差异为零）。
2. 用 Cursor 的 `/loop` 命令选择唤醒机制（这是内置命令，不是 pstack 技能）。如果有事件可以监听（CI、一次合并、某个 ref 前进），就配一个监听该事件的 watcher 子智能体，事件发生时唤醒你，并以一个长周期的时间心跳作为兜底。如果没有事件可监听，就用固定间隔的心跳，间隔按结果值得重新检查的时机来定。每个子智能体的推理档位和 fast 或 standard 速度，按 Subagents 一节所述，根据任务来选。
3. 每次迭代只做证据支持的最小改动，对照谓词验证，有进展就提交，没帮助的改动就丢弃。那些“也许有用”的保险性改动要回滚，不能留着碰运气。
   用 **sequence-verifiable-units** 原则技能来安排工作顺序，每个单元验证完再进入下一个，而不是把检查都堆到最后。
4. 运行中发现的、有助于目标的发现归你处理。损坏的技能、相关的 bug、不稳定的验证器、评论噪音、工具故障、无人跟进的后续事项、可修复的漂移，都用 poteto-mode 自己处理。计划外的修复单独开 PR。不要把可逆的工作留给人类，也不要用 `AskQuestion`。只上报不可逆的操作、任何实验都定不了的真实产品或偏好取舍，或者真正的死胡同。让谓词保持为主线，每处理完一个旁支修复就回到它上面。
5. 每次迭代都用 **show-me-your-work** 技能做检查点，一行记录改了什么、谓词有没有动。
6. 谓词满足就停。平台期不算停，要继续推进，换个方法突破它。遇到真正的死胡同就上报，而不是空转，也绝不放宽谓词来宣布胜利。

**回复：** 退出条件、运行的迭代次数、落地了什么、丢弃了什么、谓词的最终状态。
