### 缺陷修复

**这个任务由你负责。计划、审查、验证。** 把调查和修复委托给子代理，你留在主位。按子代理一节，为每个子代理选择这项工作所需的推理档位，以及 fast 或 standard 速度。

要科学。每一行交付出去的代码都追溯到运行时证据。那些「也许有用」的双保险是假设，不是修复。它不交付。证据推翻一条假设时，回退它所推动的改动。证据所支持的最小改动才交付，多一点都不要。

1. 经控制技能，在对应的交互面上自己复现（见不可让步项），即使某份调试或仪器协议说要让用户去复现。只有在控制交互面到不了目标、并且你已经把它开到尽头之后，才向用户提问，而且要说出具体理由。如果它不能直接复现，就合成触发条件、收紧条件，或装上仪器，直到它触发。
2. 对原因做二分。形成候选假设，然后逐个排除，直到剩下一个。用受影响子系统上的 `how`，以及回归历史的 **why** 技能，来给它们播种。每一轮都取那个切掉最多剩余问题空间的分割，拿到运行时证据，排除。程序状态不清楚时，加上仪器或日志，在代码运行时读它。不要猜。用 Cursor 的 `/loop` 命令驱动一场很长或很顽固的追查。在第 3 步的 architect/interrogate 扇出之前，用运行时证据确认活下来的*机制*。
3. 计划修复。如果它跨过函数边界，先用 `architect`。把实现委托给一个子代理，使用你配置的 bug-fix 模型（默认 `grok-4.7-xhigh-fast`），并给一个具体范围。
4. 在同一交互面上验证。原来的复现现在通过。「Inconclusive」或交互面不对，都不算通过。标出来。单元测试显示的是分支行为，不是缺陷不存在。
5. 安排提交，让失败的复现在 git 历史里先于修复落地。当这个缺陷有一条廉价的本地测试路径时，失败测试先行的节奏见 **tdd** 技能。测试会很贵、集成很重，或不清楚时，跳过它。
   这就是那条规范的 **sequence-verifiable-units** 原则技能：失败的测试在先，修复在上。
6. 运行 **打开 PR**。

**回复：** 坏了什么、根因、修复、你如何验证。把先失败后通过的复现输出原样贴上。
