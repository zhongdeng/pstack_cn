### Bug 修复

**这个任务由你负责。规划、审查、验证。** 把调查和修复委派给子智能体，你自己留在主导位置。按 Subagents 一节，为每项工作挑选子智能体的推理级别和 fast 或 standard 速度。

要讲科学。每一行上线的代码都能追溯到运行时证据。那些“也许有用”的保险措施只是假设，不是修复。它不上线。当证据推翻了某个假设，就回滚由它引出的改动。只上线证据能证明其合理性的最小改动，不多做。

1. 自己通过 control skill 在匹配的界面上复现问题（见 Non-negotiables），即使某个 debug 或 instrumentation 协议说要让用户来复现。只有在能说出具体理由、说明 control 界面无法触及目标时，才去问用户，而且要先把它推到极限。如果它不能直接复现，就合成触发条件、收紧条件，或者加埋点，直到它能触发。
2. 二分查找原因。列出候选假设，然后逐个排除，直到只剩一个。用 `how` 在受影响的子系统上做种子，再用 **why** 技能查回归历史。每一轮都选能砍掉最多剩余问题空间的那个切分，拿到运行时证据，排除。程序状态不清楚时，加埋点或日志，在代码运行时读它。不要猜。遇到漫长或顽固的排查，用 Cursor 的 `/loop` 命令来驱动。在进入第 3 步的 architect/interrogate 扇出之前，先用运行时证据确认幸存下来的*机制*。
3. 规划修复。如果跨了函数边界，先跑 `architect`。把实现委派给子智能体，用你配置的 bug-fix 模型（默认 `grok-4.7-xhigh-fast`），给它明确的范围。
4. 在同一个界面上验证。原来的复现现在通过了。“不确定”或错误的界面都不算通过。要标出来。单元测试展示的是分支行为，不是 bug 不存在。
5. 把提交分阶段安排好，让失败的复现在 git 历史里先于修复落地。当这个 bug 有便宜的本地测试路径时，按 **tdd** 技能里失败测试先行的节奏来。如果测试代价高、偏集成、或者不清楚，就跳过。
   这就是 **sequence-verifiable-units** 原则技能的标准做法，先写失败的测试，再把修复叠上去。
6. 运行 **Opening a PR**。

**回复：** 哪里坏了、根因、修复、你怎么验证的。把先失败后通过的复现输出原样贴出来。
