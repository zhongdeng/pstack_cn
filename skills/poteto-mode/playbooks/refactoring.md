### 重构

**契约归你管。结构可以变，行为不能变。** 这和 Feature 不同，Feature 是加行为；也和 Bug fix 不同，Bug fix 是修行为。

如果清理过程中冒出一个缺失的功能或一个真实的 bug，把它拆出去，先针对钉住的契约把结构性改动发出去。重新设计是允许的，但要明确说出来，并走 Feature。大范围或横切的结构性工作归 **figure-it-out** 技能。这份作战手册管的是聚焦到中等规模的改动。

1. 先钉住行为契约。对受影响的子系统跑 **how** 技能，把契约搞清楚，然后在任何结构动之前，写一个表征测试、快照或等价性 harness，把当前行为捕获下来。如果这块区域没有覆盖，先写 pin 再碰结构。类型检查和 lint 不算 pin。
2. 按 **principle-model-the-domain** 说出代码缺的是什么结构。形状已经清楚且局部的时候，无聊的代码就留着。重塑必须删掉分支或非法状态，而不是加一层间接。
3. 说出目标形状。讲清楚如果今天从头建，模块布局、类型和调用图应该是什么样（**principle-foundational-thinking**、**principle-redesign-from-first-principles**）。如果目标跨了函数边界，在动手之前跑 **architect** 技能，对形状做并行设计探索。
4. 先减后加。在引入新形状之前，删掉死代码、合并只有一个调用者的包装、去掉多余的校验器、清理孤儿引用（**principle-subtract-before-you-add**）。能到达目标形状的最小改动才发（**principle-laziness-protocol**）。那种"也许有用"的投机性清理，回滚。
5. 用小的、保持行为的步骤来搬，每一步都让 pin 保持绿色。对于 API 重塑，在同一波里迁移所有调用者并删掉旧 API（**principle-migrate-callers-then-delete-legacy-apis**）。不要兼容垫片，不要新旧并行的路径。每个重命名都对着实际文件抽查一遍。重命名会悄悄漏掉字符串、散文和反向引用里的用法。把机械性编辑交给子智能体，用你配置的重构模型（默认 `grok-4.7-xhigh-fast`），给出明确的范围（文件路径、要搬的名字、要保持的行为）。按 Subagents 那一节，为每个子智能体挑好推理档位和快或标准速度。
6. 在真实产物上证明行为没变，不是"它能编译"（**principle-prove-it-works**）。对于更大的重塑，跑一次等价性检查：一个 diff 新旧输出的脚本、一份录好的基线在新代码上重放，或者通过相关 control 技能在匹配的表面上跑一次冒烟。
7. 确认这个改动值得留。成功的衡量标准是读者负担降低（**principle-minimize-reader-load**）。如果 diff 没有在任何地方降低读者负担，回滚。
8. rebase 成小的、有序的提交。一个减法提交，然后是重塑，然后是后续清理。用 **sequence-verifiable-units** 原则技能来塑形，让每个保持行为的切片在下一个之前都保持绿色。跑 **Opening a PR**。

**回复：** 变了的结构、你拿它对照的 pin、等价性证明、读者负担的差值、发了什么、回滚了什么。没有新行为。
