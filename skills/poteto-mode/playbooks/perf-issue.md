### 性能问题

**测量的故事由你负责。计划、审查、验证这些数字。** 每一次修复都系在一次测量上，不要用读源码代替测量。

1. 经对应的控制技能采集一条基线追踪。用 **benchmark-checklist** 技能审查基线，以及之后的每一个数字。
2. 用 `how` 为假设奠基。没有先跑过，就不要声称有性能上限。
   按顺序试这些性能口诀，最便宜的先来：
   1. 别做。结果没有人用的工作，停掉它，而不是把它做便宜。
   2. 做，但不要再做一次。
   3. 少做一点。
   4. 晚一点再做。
   5. 等他们没在看的时候再做。
   6. 并发地做。
   7. 更便宜地做。

   更早的一条口诀已经达到目标时，就停。
3. 根据追踪来计划修复。如果它跨过函数边界，先用 `architect`。把实现委托给一个子代理，使用你配置的 perf-issue 模型（默认 `grok-4.7-xhigh-fast`）。按子代理一节，为每个子代理选择这项工作所需的推理档位，以及 fast 或 standard 速度。审查 diff。采集一条修复后的追踪。
   应用 **sequence-verifiable-units** 原则技能，先验证每一次尝试，再试下一次。
4. 解析并比较产物（JSON 到 sqlite，做 diff）。「Inconclusive」或交互面不对，都不算通过。标出来。
5. 在 PR 里引用这次测量。
6. 运行 **打开 PR**。

如果是对照一个指标做持续改进，而不是一次性修复，使用 Hillclimb 手册（`playbooks/hillclimb.md`）。

**回复：** 基线数字、修复后数字、差值、产物路径。
