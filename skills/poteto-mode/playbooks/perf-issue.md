### 性能问题

**测量这件事由你负责。规划、审查、核实数字。** 每个修复都要对应一次测量，不要用读源码代替测量。

1. 用对应的控制技能抓一份基线 trace。用 **benchmark-checklist** 技能审查基线，以及之后每一个数字。
2. 用 `how` 来支撑假设。没跑过就不要声称性能上限。
   按顺序尝试性能口诀，从最省事的开始：
   1. 别做。结果没人用的工作直接停掉，而不是把它做得更便宜。
   2. 做，但别做第二次。
   3. 少做一点。
   4. 晚点再做。
   5. 趁没人看的时候做。
   6. 并发做。
   7. 做得更便宜。

   某条口诀达到目标就停。
3. 根据 trace 规划修复。如果跨了函数边界，先 `architect`。把实现委派给子智能体，用你配置的 perf-issue 模型（默认 `grok-4.7-xhigh-fast`）。按 Subagents 一节，为每个子智能体挑选适合任务的推理级别和 fast 或 standard 速度。审查 diff。抓一份修复后的 trace。
   应用 **sequence-verifiable-units** 原则技能，每次尝试都先验证再试下一个。
4. 解析并对比产物（JSON 转 sqlite，diff）。“Inconclusive”或测错了面都不算通过。标出来。
5. 在 PR 里引用这次测量。
6. 运行 **Opening a PR**。

如果要针对某个指标做持续改进，而不是一次性修复，用 Hillclimb 作战手册（`playbooks/hillclimb.md`）。

**回复：** 基线数字、修复后数字、差值、产物路径。
