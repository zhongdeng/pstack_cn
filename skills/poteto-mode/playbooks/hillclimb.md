### 爬山

**指标和实验的完整性由你负责。监督和评审。把尝试交给子智能体。** 用于针对一个目标、对某个可度量指标做持续的迭代改进。一次性的修复属于 Bug fix 或 Perf issue。这里讲的是循环。

核心纪律：一次只改一处，一次只测一次，保留或回退。绝不堆叠未经验证的改动，也绝不靠读代码就宣称胜利（**prove-it-works** 原则技能）。

1. 先摸清工作负载和架构，再选指标。对目标跑 **how** 技能，列出能真正影响结果的现实负载维度（数据规模、历史、状态、并发），挑一个能复现用户抱怨的用例。如果没有用例能复现，先修复现，别急着爬山。然后定下一个指标、哪个方向算更好，以及一个可检查的停止谓词，它要把目标和对尝试次数的下限绑在一起，这样早期侥幸赢一次也结束不了整轮（示例“至少比基线好 50%，且至少 10 次迭代”就是这个形状）。用户给了数字就用用户的，没给就一起商定。
2. 搭测量工具，证明它够灵敏，然后冻结它（**build-the-lever** 原则技能）。跑几组对比鲜明的现实负载，确认目标用例能复现症状，而更简单的用例按预期区分开。如果工具区分不出来，就改负载或改指标。冻结之前用 **benchmark-checklist** 技能审查一遍工具，并让它打印错误计数和已完成工作的计数。冻结之后，用一条可重复的命令输出指标，采样要足够多以压过噪声（取 N 次的中位数，不是单次运行）。在任何改动之前，记录基线指标和回归门禁（必须一直通过的测试）的一次绿色运行。
3. 用 **show-me-your-work** 技能打开决策日志。一个 `decision.tsv`，每次尝试一行：id、假设、改动、改前、改后、差值、测试、裁决（保留或回退）、备注。每次尝试前先读它。把它放在代码树之外（gitignored）。
4. 每个假设都要扎根在第 1 步的架构模型上，这样它点出的是具体机制（“把 X 从启动路径上挪走，因为它挡住了首屏绘制”），而不是“试试给某个东西加 memo”。如果是性能指标，按 Perf issue 作战手册（`playbooks/perf-issue.md`）第 2 步里的性能箴言给假设排序。只借它们的顺序，不借那一步的停止规则。
5. 循环，每次迭代一个假设：
   - 把改动交给子智能体，用你配置的 hillclimb 模型（默认 `grok-4.7-xhigh-fast`），范围收紧。按 Subagents 一节，为每个子智能体挑推理档位和快或标准速度。你负责监督和评审 diff，而不是自己敲（**guard-the-context-window** 原则技能）。当几个独立假设同时在场时，把它们分发给并行的子智能体，每个在自己的 worktree 里（**separate-before-serializing-shared-state** 原则技能）。
   - 用冻结的工具测改前改后，并跑回归门禁。
   - 只有当指标越过噪声、门禁保持绿色时才接受。否则把改动完整回退。“也许有用”的小调整不保留。
   - 每个被接受的修复一个 commit，只暂存你改过的文件（`git add <files>`，绝不用 `-A`）。无论保留还是回退，都记一行。
   每次迭代结束都要检查一次，再开始下一次（**sequence-verifiable-units** 原则技能）。如果这轮是无人值守的，只借 Autonomous run 作战手册（`playbooks/autonomous-run.md`）的唤醒机制，不借它的停止规则。
6. 越过第一个平台期。卡住时，连续几次被拒时，换类别、合并差一点的方案、重读源码，或者试更激进的做法，再下结论说山爬完了。正确性和简单性优先于数字。破坏行为的胜利要回退，能保住数字的简化要保留（**laziness-protocol** 原则技能）。
7. 谓词满足时停，或者剩下的想法都很边缘、不值那个成本时停。不要为了达标而放宽谓词，也不要还有便宜的未试假设就放弃。如果卡死了，把它摆出来，别空转。
8. 按落地顺序把被接受的 commit 堆叠起来，跑 **Opening a PR**。

**回复：** 指标和目标，基线到最终值及百分比差值，跑了多少次迭代（保留 vs 回退），每个被接受的修复一行，`decision.tsv` 路径，以及如果继续推进你会试的下一个最好的想法。
