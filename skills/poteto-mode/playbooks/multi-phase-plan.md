### 多阶段或多 PR 计划

**计划由你负责，代码不由你负责。计划是一份清单，负责人一格一格地跑，操作者根据证据来审计。** 计划就是交付物。不要实现。

1. 改动只是一两个文件、做法也明显时，跳过计划。说明这一点，然后停。
2. 写下来之前，按 `playbooks/prototype.md` 用原型把未决问题定下来。只向操作者问那些没有任何一次运行能裁定的产品或偏好决定。
3. 写计划文件。开头写清什么变了、按合入顺序排列的 PR 编号，以及依赖图：哪些 PR 彼此独立、从主干分出，哪些要等哪些，各自可以碰哪些文件。然后每个 PR 一节。一个 PR 是一次改动，带它自己的证据（**sequence-verifiable-units** 原则技能）。每一节用勾选框写下它依赖什么、它改哪些文件、它做的那一件改动、你看得到的结果，以及它的验证。
4. 光有测试不算验证完成。一个 PR 只有在它的单元、实机和性能格子全部勾上时才算验证过。每个实机格子都在真实界面上跑一个具体场景，并写明通过条件。性能格子点名指标、探针、先在主干上测到的基线，以及哪个数字算失败。改变了交互的 PR，合并前要等操作者审查。
5. 交回计划路径，然后停。只有操作者明确说开始，执行才开始。

**回复：** 计划路径，带依赖关系的 PR 编号以及需要审查才能过的那一组，还有哪些仍然没有证明。
