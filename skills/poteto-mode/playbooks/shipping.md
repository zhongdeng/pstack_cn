### 交付

**合入的东西由你负责。独立验证每一个 PR，只从根合入已验证的那一段连续区间，然后把手从栈上拿开。**

1. **先解析托管平台，然后在每个 PR 合入之前独立验证它。** GitHub CLI（`gh`）是默认。如果 `command -v origin` 成功并且 Origin 能解析该仓库，每一次 PR 操作都用 `origin pr`。否则留在 `gh`，并记下这次回退。绝不要求 Graphite（`gt`）。每个 PR 一个验证者，各自是一个 Cursor 云代理，用对应的控制技能（例如来自 `cursor-team-kit` 的 `control-ui` 或 `control-cli`）按用户会用的方式跑这次改动，对照 parent 与 head，并在该 PR 上贴出 `PASS`、`PASS+NOTES` 或 `FAIL`。只有没写过这段代码的代理给出的裁决才算数，因为作者检查的是它打算构建的东西。绿色 CI 和批准性的机器人审查都不是裁决，因为两者都没有按用户会用的方式跑这次改动。
2. **只合入扎根在底部的那一段连续已验证区间。** 从最低的未合并 PR 往上走，停在第一个没有 `PASS` 或 `PASS+NOTES` 的地方。它下面的那些 PR 就是这一段，最上面那个是上限。一个已验证的 PR 若位于未验证的 PR 之上，就要等，因为没有下面的代码它无法合入。如果某个 PR 的分支既不持有也不需要那段代码，它可以挪到主干上独自合入。它需要一份新的裁决，因为旧裁决是在那段代码垫在下面时跑的，而主干上没有那段代码。
3. **再查一次，这些裁决描述的仍然是这段代码。** 一份裁决覆盖一个补丁，而一次链式变基会把它上面的每一个 PR 移到新的 SHA，同时不让任何检查失败。在信任一份较旧的裁决之前，比较裁决 SHA 处的 `git patch-id` 和当前 head。当补丁的差异只在测试、文档或 lint 配置时，如果一条通道所跑的东西在两个 SHA 上除了噪声之外构建结果相同，这条通道的结果就仍然成立。噪声是一种在裁决 SHA 的两次构建之间也会出现的差异，或一个嵌进去的提交 SHA。每种噪声都连同它的文件一起报告，这样读者可以核对这次判断。改动本身仍然要拿到新的检查和一次审查，因为旧裁决从来没见过它。一条没有构建输出的通道，例如开发服务器，无法展示这一点，所以重跑它，并重新验证任何其他漂移了的东西。
4. **自底向上合入，一次一个 PR。** 始终合并这一段里最低的未合并 PR，用 `origin pr merge <pr>` 或 `gh pr merge <pr> --squash`。在 Origin 上，这条普通命令还会合并你点名的那个之下的每一个 PR。在 GitHub 上，一个基仍然是父分支的 PR 会合并进那条分支，而不是主干。把 PR 读回来核对结果（`origin pr view <pr>` 或 `gh pr view <pr> --json state,mergedAt,baseRefName`），因为合并命令可能在合并队列只是把 PR 排上队时就报告成功，而一次被请求的自动合并不是合并。一个已合入的 PR 读出来是已合并，并且基是主干，不是它的父分支。只在裁决覆盖其当前 head 的 PR 上启用 `--auto`（Origin 的 merge-when-ready，或 GitHub 的 auto-merge），因为它会合入任何一个就绪的 head。一次合并落地之后，把基曾经是已合并分支的那个 PR 改目标到主干（`origin pr edit <pr> --base <trunk>` 或 `gh pr edit <pr> --base <trunk>`），把它的补丁移到合并结果上，并用 `--force-with-lease` 推送。裁决覆盖的是补丁，不是它的提交，所以第 3 步的 patch-id 规则决定裁决是否还在。一旦它的检查通过并且裁决还在，就合并它。
5. **栈在合入期间别去动它。** 第 4 步对下一个 PR 的移动，是对分支或基的唯一改动，因为合并会把那一刻分支和基上持有的东西合入，不管有没有裁决。在 GitHub 上，用 `playbooks/babysit.md` 里的排队看守（`scripts/watch-pr/watch-pr --queued-stack --stack-prs <bottom-to-top>`）在 `/loop` 下盯着这一段，直到它在上限处报告 `COMPLETE`。在 Origin 上，每次 `origin pr checks <pr> --watch` 返回时，用 `origin pr view <pr> --checks` 重读当前 PR，直到上限读出来是已合并。父合并时基移到主干是预期的，不是要修的损坏。如果一次合并卡住，先弄清为什么，再改任何东西。
6. **停在上限。** 延伸这一段需要新的裁决，所以那是重新走一遍第 1 步。

**回复：** 已验证的区间及其上限、每个 PR 的裁决以及谁给出的、合入了什么以及你如何确认、下一个缺口需要什么。
