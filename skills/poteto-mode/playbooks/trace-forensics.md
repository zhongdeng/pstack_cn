### 追踪取证

**从产物做出的诊断由你负责。**

与 **运行时取证** 不同，后者给活着的进程装仪器。这里采集已经存在。产物是一份固定的数据集，读它，不要重跑它。工具保持通用：cpuprofile 和 `.json.gz` 用 DevTools 或追踪解析器，spindump 用文本编辑器，heapsnapshot 用你的堆工具。

1. 识别格式，并用合适的工具加载。在子代理里解析大产物（**principle-guard-the-context-window** 技能），把收束后的发现留在主线程。按子代理一节，为每个子代理选择这项工作所需的推理档位，以及 fast 或 standard 速度。
2. 把原始产物变成你可以查询的形式。把追踪或堆快照倒进 sqlite，每个样本、帧或节点一行。先达到可查询的形状，再去读。
3. 收窄到原因。查询占用时间最多的帧，并沿调用树走到热路径。泄漏则沿着保留链，从泄漏对象走到 GC 根。spindump 则找到卡在 CPU 上或被阻塞的线程，以及它的等待原因。
4. 归到源码。通过产物自己的符号，把热帧映到文件、符号和行。一个没有源码映射的帧还不是诊断。把符号解析出来，或者明说产物没有带上它们。
5. 如果有成对的采集，对前后产物做 diff 来确认。否则，把发现标成这份产物所能支持的最强假设，不是已确认的原因。
6. 交回一份带引用的诊断，除非被要求，否则不给修复。原因清楚之后，路由到缺陷修复或性能问题。吞吐检查点保持一行：`throughput checkpoint: n/a, read-only forensics`。

**回复：** 产物和格式、收束后的发现、源码位置、产物路径，以及成对采集是否确认了它。
