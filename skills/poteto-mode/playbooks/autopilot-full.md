### Autopilot-full

**裁决由你负责，PR 从不由你负责。一个负责人把每个 PR 从构建带到合并，并且在你的 swarm 证明了将要合入的代码之前，什么都不合并。这个 swarm 从未写过这段代码。**

一份裁决覆盖一个补丁，绿色 CI 覆盖一个 head。第 4 步跑一次完整 swarm，只有重大改动才再跑。`playbooks/shipping.md` 里的 patch-id 规则可以让一条通道的结果继续有效，而每一个新 head 都需要它自己的绿色 CI。

1. **操作者的门禁优先。** 授权只覆盖队列里的项，所以操作者点名为他们自己的项，以及队列之外的 PR，都停在可合并。要求陈述计划并不是放行。
2. **每个 PR 派生一个负责人，并把它的工作放在替换者找得到的地方。** 为整个项目解析一次托管平台。GitHub CLI（`gh`）是默认。如果 `command -v origin` 成功并且 Origin 能解析该仓库，每一次 PR 操作都用 `origin pr`。否则留在 `gh`，并记下这次回退。绝不要求 Graphite（`gt`）。每个负责人是一个 Cursor 云代理，它构建、按 `playbooks/opening-a-pr.md` 开自己的 PR、在真实产物上证明这次改动、按 `playbooks/babysit.md` Babysit 到绿色，并在第 4 步和第 5 步放行之后合并。

   早点开 PR，这样 CI 和机器人与工作并行。代码只有在去掉 AI 腔那一遍（来自 `cursor-team-kit` 插件的 `deslop` 技能（`/deslop`））和 `/no-comments` 这一遍之后才算就绪，所以完整 swarm 跑在已经完成的代码上。然后变基到当前主干，并在自证之前报告代码就绪的 head，这样验证跑在补丁将要落上去的那个基上。报告之后的每一个 head，并在自证、CI 和 Babysit 都做完时报告可合并。修复轮次留在那个基上，除非主干冲突或弄坏 CI，因为每一次变基都会重启 CI。在代码就绪的推送之前，以及在之后任何需要验证者的推送之前，在已提交的 head 上，对碰到的路径跑仓库的检查。

   假定虚拟机会死。开始后不久，按 **show-me-your-work** 技能，在根代理的存储里推送并开始一条决策痕迹（路径在系统提示里），然后在每一个值得保留的单元之后推送。谁派生了一个子代理，就在那个存储里记下它的 id、状态，以及根据同类过去的运行得出的、判定为卡住的运行时长，这样如果父级死了，根可以探查它。只强制推送你自己的分支，`--force-with-lease` 钉在你上次推送或接手时的那个 SHA，并且对任何不是你做出的推送，停下来向根报告。
3. **负责人并行地从主干跑，绝不堆叠，** 这样每个 PR 各自合入。
4. **只做一次 swarm 验证。** 完整 swarm 在代码就绪的 head 上跑一次。另一次完整 swarm 只为新行为、一次重新设计，或一份很大的新 diff。一次变基、一次合并冲突的解决，或一次小修复，在新 head 上得到单个验证者。按 **swarm** 技能，在代码就绪的 SHA 上扇出独立的验证者。他们重跑门禁，经它的控制技能（例如来自 `cursor-team-kit` 的 `control-ui` 或 `control-cli`）或一个点名的驱动，在真实交互面上实机证明承重行为，并审计 diff。没有实机通道，裁决就不算干净。在你审计可合并报告的回执之前，也不算干净，因为没有一条通道会信任一条它没有检查过的说法。

   把每一个被证明的发现，不论一条通道给它贴了什么标签，在一次向前修复里发给负责人，并在每一个有同样缺陷的位点配一个变红的测试。主干在没有这个 PR 时就表现出来的缺陷，记在主干上，并不门控这个 PR。但这个 PR 复制了或新触及的，就是这个 PR 自己的。绝不要自己推修复，因为每个分支只有一个写入者。换掉卡住的负责人。
5. **负责人只合并你验证过的、并且是在它将要落上去的那份主干上测试过的东西。** 仅有绿色 CI 从不授权合并。一旦 swarm 的通道已经开始，合并准备就变基到当前主干，报告新的 head，并等待绿色 CI。

   就在合并之前，拉取主干，并问它的改动会不会影响这个补丁，因为为每一次主干移动都变基，永远不会结束。当将要合入的代码从未被测试过时，变基并等待 CI，例如一次冲突、一个两边都改过的文件，或对这个 PR 要跑哪些检查的改动。两边都改过的锁文件，当一次冻结安装在合并结果上通过、并且这个 PR 所改的包在那里的解析与在 head 上一样时，不需要变基，因为那次安装测试的是将要合入的锁文件，而安装失败意味着变基必须把它修好。当主干改了这个补丁的一个调用方，或改了这个补丁所依赖的东西，例如它调用的代码或一个依赖版本，就在合并结果上跑这个补丁的检查，通过就合并。否则就合并。如果主干会迫使合并准备之后再来第三次变基，停住并向根报告，由根来给相撞的工作排顺序。
6. **跑根这一层。** 任何放宽一道门禁的东西，例如提高的预算或一条允许名单，都需要一份验证者的证明，然后是你新的会签，因为想要绿色的是负责人。在一份覆盖批准的授权之下，那次会签就是批准，负责人对它的记录指向你的会签，供一条通道来查。一个被禁用或软失败的检查始终要拿出来，因为它不再守卫每一种情况。绝不要给出或绕过托管平台所强制的批准，因为没有一次会签能覆盖它。

   在操作者放行时，启用 `/loop 1h`，一直审计到没有剩余的委托工作，因为长运行会漂移，代理会无声地停住。每一次节拍从主干重读这本手册，并修好漂移，例如一个未报告的 head 或一个未记录的代理，办法是让它的负责人把它记下来，因为漂移是记录里的缺口，不是停住。它探查每一个代理，一直到叶子通道，并且只按副作用判断每一个，因为状态文本和摘要可能藏着一个卡住的子级。一个代理在出错、无法开始回合，或过了它判定为卡住的运行时长仍没有任何新东西时，就是卡住了。到第一次节拍时既没有推送、也没有写过一行痕迹的负责人，同样是卡住。一个在等你或操作者的不算卡住，所以去回答它。立刻换掉卡住的代理，不要等它的停止落地。一次为操作者改变了某件事的节拍，结束时按 **ketchup** 技能把他们补到最新。一次什么都没改变的节拍保持安静。
7. **操作者一说停，立刻撤下。** 一次暂停作为零写入指令到达每一个负责人。各自报告自己站在哪里，并保留自己的简报，直到操作者释放它。

**回复：** 按 **ketchup** 技能把操作者补到最新，覆盖每个 PR 的状态和裁决、合并了什么、会签及其原因，以及未完成的操作者门禁，并附上每个 PR 和各条痕迹的链接。
