### 全自动驾驶

**你负责的是判定，永远不是 PR。每个 PR 从构建到合并都由一个负责人全程带着，而你的 swarm 从没写过这些代码，只有它证明过要落地的代码，才能合并。**

一个判定只覆盖一个补丁，CI 全绿也只覆盖一个 head。第 4 步只跑一次完整 swarm，只有重大变更才再跑一次。`playbooks/shipping.md` 里的 patch-id 规则可以让一条 lane 的结果继续沿用，但每个新的 head 都需要自己的 CI 全绿。

1. **操作者的闸门优先。** 授权只覆盖队列里的条目，所以操作者点名归自己的条目、以及队列之外的 PR，都停在 merge-ready。让你说明计划，不等于放行。
2. **每个 PR 派一个负责人，把它的工作放在替补能找到的地方。** 整个程序只解析一次 forge。默认用 GitHub CLI（`gh`）。如果 `command -v origin` 成功，并且 Origin 能解析仓库，那么所有 PR 操作都用 `origin pr`。否则继续用 `gh`，并记录这次回退。绝不要求 Graphite（`gt`）。每个负责人都是一个 Cursor 云智能体，它负责构建、按 `playbooks/opening-a-pr.md` 开 PR、在真实产物上证明改动、按 `playbooks/babysit.md` 盯到全绿，并在第 4、5 步放行后合并。

   尽早开 PR，让 CI 和机器人跟工作并行跑。代码只有在过完去 AI 腔（`cursor-team-kit` 插件里的 `deslop` 技能（`/deslop`））和 `/no-comments` 之后才算就绪，这样完整 swarm 跑的是成品代码。然后 rebase 到当前 trunk，在自证之前报告 code-ready head，让验证跑在补丁最终落地的基线上。之后每个 head 都要报告，自证、CI、babysit 都完成后报 merge-ready。修复轮次留在这个基线上，除非 trunk 冲突、弄坏了 CI，或者往同样的文件上落了一个已知的并发改动，因为每次 rebase 都会重启 CI。在 code-ready 那次 push 之前，以及之后需要验证者的 push 之前，对已提交的 head 跑仓库里针对所涉路径的检查。

   假设 VM 会死。开工不久就 push，并按 **show-me-your-work** 技能在根智能体的存储里（路径见系统提示）开一条决策记录，然后每完成一个单元就先 push 再开下一个。谁派生子智能体，谁就在那个存储里记下它的 id、状态，以及根据同类历史运行得出的 stuck-after 时长，这样父智能体死了根智能体也能去探查它。只 force-push 你自己的分支，用 `--force-with-lease` 钉死在你最后 push 或接手的 SHA 上；任何不是你做的 push，停下来报告给根智能体。
3. **负责人从 trunk 并行开工，绝不堆叠，** 这样每个 PR 各自落地。
4. **只做一次 swarm 验证。** 完整 swarm 只跑一次，在 code-ready head 上。再跑一次完整 swarm 只针对新行为、重新设计或很大的新 diff。rebase、解决合并冲突或小修复，只在新 head 上派一个验证者；纯措辞改动一个都不派。按 **swarm** 技能在 code-ready SHA 上铺开相互独立的验证者。它们重跑闸门，通过对应的控制技能（比如 `cursor-team-kit` 里的 `control-ui` 或 `control-cli`）或指定的 driver，在真实界面上实测承重行为，并审计 diff。没有 live lane，或者你还没审计 merge-ready 报告里的凭据，判定就不算干净，因为没有哪条 lane 会相信自己没查过的说法。

   只有你能拿出证据的问题才能卡住 PR：head 上有失败的运行，或者 PR 把某行文档写错了。PR 基线本来就有的问题，不管是 trunk 还是栈里它下面那个 PR，都不卡，除非这个 PR 把它抄了过来或新踩到了它。只有用户会撞上的 bug、失败的闸门、或写错的已发布文档才卡，其余一律进后续跟进。
5. **负责人只合并你验证过、并在它落地的那个 trunk 上测过的东西。** CI 全绿本身从不授权合并。swarm 的各条 lane 一旦开跑，合并准备就 rebase 到当前 trunk，报告新 head，等 CI 全绿。

   合并前一刻，fetch trunk，问它的改动会不会影响这个补丁，因为每次 trunk 一动就 rebase 永远没完。如果将要落地的代码从没被测过，比如有冲突、两边都改了同一个文件、或者改了 PR 跑哪些检查，那就 rebase 并等 CI。两边都改了的 lockfile 不需要 rebase，只要在合并结果上跑 frozen install 能过，并且 PR 改的包在那里解析结果和 head 上一致，因为这次 install 测的就是将要落地的 lockfile；install 失败就说明 rebase 必须把它修好。当 trunk 改了这个补丁的调用方或它依赖的东西，比如它调用的代码或某个依赖版本，就在合并结果上跑这个补丁的检查，过了就合并。否则直接合并。如果 trunk 会逼出 merge prep 之后的第三次 rebase，就停下来报告给根智能体，由它来排开相互冲突的工作。
6. **跑好根这一层。** 任何放松闸门的操作，比如提高预算或加白名单条目，都需要验证者的证明，然后你再亲自副签，因为负责人正是那个想要全绿的人。在覆盖审批的授权下，这个副签就是审批，负责人对它的记录会指向你的副签，供 lane 核查。被禁用或软失败的检查一定要拿出来，因为它已经不再守护任何情况。绝不给或绕过 forge 强制的审批，因为没有副签能覆盖它。

   操作者一声令下，就挂上 `/loop 1h` 持续审计，直到没有委派出去的工作为止，因为长跑会漂移，智能体会悄悄卡住。每一拍都从 trunk 重读这本作战手册并修掉漂移，比如没报告的 head 或没登记的智能体，办法是让它的负责人补记，因为漂移是记录上的缺口，不是卡住。它探查每个智能体，一直探到叶子 lane，并按副作用判断，因为状态文字和总结可能掩盖一个卡住的孩子。智能体报错、开不了回合、或者过了它的 stuck-after 时长还没有新动静，就算卡住；到第一拍既没 push 也没写记录行的负责人同样算卡住。在等你或等操作者的不算卡住，所以要去回它。卡住的智能体立刻替换，不等它的停止落地。某一拍如果给操作者带来了变化，就按 **ketchup** 技能在结尾给他同步；没带来变化就保持安静。
7. **操作者喊停就立刻停手。** 暂停令以零写入命令的形式传到每个负责人。各自报告自己处在什么状态，并保留自己的任务简报，直到操作者解除。

**回复：** 按 **ketchup** 技能给操作者同步，覆盖每个 PR 的状态和判定、合并了什么、副签及其理由、未决的操作者闸门、搁置的后续跟进，并附上每个 PR 和记录的链接。
