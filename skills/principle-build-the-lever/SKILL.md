# 造杠杆

当工作不琐碎时，构建完成它的工具，而不是手工去做。

codemod、生成器或脚本每次都以同样的方式完成工作，而且可以免费重跑。工具是一件产物，评审者可以读它、重跑它来检查工作。手工完成的改动只能靠重做来重新验证。确定性脚本把"相信我"变成"跑这个"。

默认造杠杆。只有任务琐碎时才跳过，也就是几处一眼就能看清的明显改动。

- 先手工做第一个单元，摸清配方，然后构建工具。在那个单元上重跑工具，和你手工做的版本 diff，以此证明它。让杠杆可以安全重跑。
- 编辑用 codemod 或脚本，重复文件用生成器，分析用 dump 到 sqlite 的查询，验证用可重跑的检查。
- 确定性杠杆胜过 fan-out。如果工具能一趟处理所有单元，就自己跑。不要把工作 fan-out 给委派者，让他们手工套用脚本能做的事。
- 当你把工作 fan-out 给子智能体时，把杠杆写成它们都会读的技能：配方、验证契约、不许碰的围栏，全放在一件产物里。把它放在委派者的写入范围之外，这样它们没法悄悄改契约。
- 应用这条原则会产生一个文件。如果你引用了它，而 diff 里没有 codemod、脚本、生成器或委派技能，那你就没应用它。
- 当工作会延续到本次会话之后时，提交杠杆。

门槛是琐碎，不是重复。一次性任务也值得造杠杆，只要杠杆是让工作可检查的东西。按照 [Laziness Protocol](../principle-laziness-protocol/SKILL.md)，构建能完成或证明这项工作的最小脚本，绝不要造框架。

区别于 [Encode Lessons in Structure](../principle-encode-lessons-in-structure/SKILL.md)，那条原则把反复出现的指令变成持久的护栏。这条讲的是眼前工作的吞吐量和可评审性。关于把验证本身脚本化，见 [Prove It Works](../principle-prove-it-works/SKILL.md)。
