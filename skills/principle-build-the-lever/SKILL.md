# 建造杠杆

工作不平凡时，建造那个去做它的工具，而不是手工做。

codemod、生成器或脚本每次都以同样的方式干活，并且可以免费重跑。工具是一份产物，审阅者可以读它、重跑它来检查工作。手工做的改动只能靠再做一遍来重新验证。确定性脚本把“相信我”变成“跑这个”。

默认建造杠杆。只有任务平凡时才跳过：两三处一眼就能看清的明显编辑。

- 先手工做第一个单元，学会配方，再建造工具。在那个单元上重跑它，并与你的手工版本做 diff，以此证明它。让杠杆可以安全地重跑。
- 编辑用 codemod 或脚本，重复文件用生成器，分析用倒进 sqlite 的查询，验证用可重跑的检查。
- 确定性杠杆胜过扇出。如果工具能一次处理每一个单元，就自己跑它。不要把委派扇出去，手工应用脚本能做的事。
- 把工作扇出给子智能体时，把杠杆写成他们都会读的一份技能：配方、验证契约，以及不要碰的围栏，放在同一份产物里。把它放在委派的写入范围之外，这样他们不能悄悄改掉契约。
- 应用这条原则会产生一个文件。如果你引用了它，但 diff 里没有 codemod、脚本、生成器或委派技能，你就没有应用它。
- 当这份工作的寿命超过本次会话时，把杠杆提交进去。

标尺是平凡与否，不是重复与否。一次性的工作，只要杠杆是让它可检查的东西，仍然值得造一个杠杆。按 [懒惰协议](../principle-laziness-protocol/SKILL.md)，建造能完成或证明这份工作的最小脚本，绝不要造一个框架。

它不同于 [把教训编码进结构](../principle-encode-lessons-in-structure/SKILL.md)。后者把反复出现的指令变成持久护栏。这条原则是关于你眼前这份工作的吞吐和可审阅性。要把验证本身脚本化，见 [证明它能工作](../principle-prove-it-works/SKILL.md)。
