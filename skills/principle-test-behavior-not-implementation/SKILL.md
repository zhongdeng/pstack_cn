# 测试行为，而不是实现

测试是关于代码为其用户做什么的主张：调用方、最终用户，或其他服务。行为是这些用户通过他们使用的接口能够观察到的东西。这包括返回值、错误、他们能读回的状态，以及对代码之外系统的影响，例如发出的请求、写入的行、发出的消息。实现是他们观察不到的东西：私有辅助函数、内部调用顺序、中间数据，以及是哪个内部协作者干的活。

用两种想象中的编辑来评判每个测试：

- **打破行为。** 让代码返回错误的值、跳过一个效果，或把效果做两遍。如果测试仍然通过，它什么也没证明。常见原因是断言比契约更松、期望值由被测代码算出来、复述了一个从未运行读取它的代码的常量或提示词字符串，以及对测试自己构造的数据做断言。
- **改变内部。** 保持每一个可观察结果不变，并重构底下的代码。如果测试现在失败，它就被钉在实现上。每次重构都要重写它，却仍然抓不住 bug。

保留能抓住第一种编辑、并在第二种编辑下活下来的测试。其余的重写或删除。要写出两者都做到的测试，就通过用户的接口、用具体输入驱动代码。期望值从需求推导，而不是从跑一遍代码推导。断言契约所承诺的，不多也不少。

做决定的是契约，而不是断言的形状。当承诺是“空购物车从不扣款”时，断言支付客户端没有被调用，就是行为。再配一个扣款发生的用例，这样测试表明它能看见调用。被模拟的外部服务收到的载荷是行为，因为那个服务观察得到它。对内部辅助函数的调用是实现，因为没有用户能看见它。没有记录匹配时，空列表是精确答案；测试只需要某个结果时，空列表就是空洞检查。一条精确的错误消息会钉住没有调用方会读的措辞。调用方用来分支的错误类型才是契约。

测试可以钉住一个不变量，而不是一次调用，例如必须同时存在于两张表里的键，或编译期的类型检查。不变量就是行为。
