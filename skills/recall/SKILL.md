# 回顾

**在你开始或恢复工作之前，重建用户最近的工作上下文，并交回一份紧凑的概要，说明事情现在处在哪里、下一步该做什么。**

保持紧凑并扣题。只读范围内的对话线所需要的内容，然后停下。

你的上下文活在两份记录里。你自己的对话历史保存你做了什么、决定了什么。共享记录保存同一份代码周围、以其他名义发生的一切：用户不断报告的症状、已经发布又被回滚的修复、生产环境里仍在触发的错误。第二份记录就是 **why** 技能所搜索的，范围跨越版本控制、问题跟踪、聊天和问题频道、长文文档以及错误跟踪。一个拖着长长缺陷尾巴的功能，它的大部分故事都在那里，所以不要只从你的记录稿来重建。

对话记录位于 `~/.cursor/projects/<slug>/agent-transcripts/<uuid>/<uuid>.jsonl`，其中 `<slug>` 是去掉开头斜杠、并把每个「/」换成「-」的工作区路径（因此 `/Users/you/proj` 变成 `Users-you-proj`）。每一行是一条聊天消息。

1. 先分类，再路由。要恢复的某一段特定的先前对话，是 `session-pickup` 行动手册，不是这个。把习惯变成一项持久技能是 `automate-me`。一份人类可读的工作总结是另一项任务。Recall 在你行动之前，跨最近的对话加载工作上下文。如果用户已经给了你一份完整的状态概要（路径、分支、那项变更），就用它，并跳过挖掘。
2. 搜索之前先锁死范围。钉住时间窗（「最近」是一个真实区间，默认最近 7 天）、话题（如果点了名），以及工作区（默认当前活动的那个。未经要求，绝不读取另一个项目的对话记录）。把范围说回去。绝不要悄悄把「全部」变成「最近 N 条」。
3. 在你的对话历史上扇出。在一个又快又便宜的模型上派出并行子代理，每个负责语料的一片。告诉每个子代理：按真实修改时间（`ls -t`）给候选排序，绝不要按 UUID 名字排序；先按话题 grep，然后只读匹配的对话、并且只读它们相关的区域；跳过当前对话以及明显的噪声（子代理、eval 和测试对话）。每个都返回相同的结构，每段对话一块：话题、用户的目标、决定、未结束的线索、挣扎与纠正，以及产物（PR、工单、分支），每一项都引用对话 UUID。只有一两段对话时，跳过扇出，直接搜索。原始记录留在子代理里。主线程只拿到它们的发现。按 **poteto-mode** 技能的 Subagents 一节，为这项工作选择每个子代理的推理级别以及快速或标准速度。
4. 每当话题点名了一个功能、文件、子系统、区域或缺陷，就扫一遍共享记录。这是默认做法，不是一项判断，而且「我在 X 上的工作」并不免除它。把它交给 **why** 技能的来源调查者，但把他们的问题从「为什么建成这样」扭到「当前状态是什么、试过什么但没站住、用户还在报告什么」。复用它按来源划分的行动手册，让调查者与对话历史挖掘并行运行，并继承它的姿态：每个来源一个调查者，空结果也是发现，跳过不可用的 MCP 并说明。把返回的内容折进简报。只有在没有点名目标的纯活动回顾（「我这周做了什么」）时才跳过这一步，那种情况下你自己的历史和实时状态就是全部答案。
5. 对照实时状态核实。把挖掘和扫查浮出来的 PR、分支和工单，用 `git` 和 `gh` 核对。当答案取决于一个代理实际做了什么（它跑了哪些工具、读了哪些文件、碰到了哪些错误）时，读完整份对话记录，而不是只读一份裁过的本地副本。
6. 按下面的约定写简报。按线索分组。停在被点名的话题上。

## 输出约定

先写概要，然后是线索状态，然后是问题，然后是下一步。更深的细节放在下面，或者砍掉。

- **概要。** 最多 5 条。这项工作是什么，总体上处在哪里。
- **线索。** 每条一行，前面恰好加一个状态标签：`[merged #N]`、`[open PR #N]`、`[in flight <branch>]`、`[verified, uncommitted]`、`[reverted #N]` 或 `[planned, not started]`。没有标签的线索还没写完，所以给它标上。
- **问题。** 最多 5 个，反复出现的那些。包括用户不断报告的症状，以及任何已发布又被回滚的修复，这样下一次尝试从上次失败的地方开始。
- **下一步。** 唯一最有用的下一个行动，要具体。

一个相邻的功能或工单，除非它挡住了这一个，否则留在外面。当概要和线索行超出一屏时，先砍细节，再砍线索。简报要通过 **unslop** 技能来写，对话发现按 UUID 引用，共享记录的发现按它们的来源引用（PR 号、工单 ID、聊天永久链接、错误跟踪器的 issue），并在任何公开输出之前对私人上下文脱敏。

**回复：** 这份简报，按上面的约定。
