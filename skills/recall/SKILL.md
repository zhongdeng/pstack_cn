# Recall

**在开始或恢复工作之前，你重建用户最近的工作上下文，并交回一份紧凑的胶囊，说明现在进展到哪、下一步做什么。**

保持紧凑、紧扣主题。只读范围内线程需要的东西，然后停下。

你的上下文存在两份记录里。你自己的聊天历史记录了你做了什么、决定了什么。共享记录则记录了同一份代码周围以其他名义发生的一切：用户反复报告的症状、上线后又被回滚的修复、生产环境里还在报的错误。第二份记录正是 **why** 技能搜索的对象，覆盖源码管理、issue 跟踪器、聊天与 issue 频道、长文档和错误跟踪。一个 bug 尾巴很长的功能，大部分故事都在那里，所以别只靠自己的聊天记录去重建它。

聊天记录位于 `~/.cursor/projects/<slug>/agent-transcripts/<uuid>/<uuid>.jsonl`，其中 `<slug>` 是工作区路径去掉开头的斜杠、再把每个 "/" 换成 "-"（所以 `/Users/you/proj` 变成 `Users-you-proj`）。每一行是一条聊天消息。

1. 先分类，再路由。要恢复某一段具体的旧聊天，那是 `session-pickup` 作战手册，不是这个。把习惯固化成可复用的技能是 `automate-me`。给人看的你工作的总结是另一件事。Recall 是在你动手之前加载最近若干段聊天里的工作上下文。如果用户已经给了你完整的状态胶囊（路径、分支、改动），直接用，跳过挖掘。
2. 搜索前先锁定范围。钉住时间窗口（"recent" 是真实区间，默认最近 7 天）、主题（如果点名了）和工作区（默认当前活跃的那个。没被要求就绝不读别的项目的聊天记录）。把范围复述回去。绝不悄悄把 "all" 变成 "recent N"。
3. 在你的聊天历史里铺开。用快而便宜的模型并行起子智能体，每个负责语料的一个切片。告诉每个子智能体：候选按真实修改时间（`ls -t`）排序，绝不按 UUID 名字排；先 grep 主题，然后只读匹配的聊天、且只读其中相关的区域；跳过当前这段聊天和明显的噪音（子智能体、eval、测试聊天）。每个子智能体返回同一套 schema，每段聊天一个块：主题、用户的目标、决定、未结的线索、卡壳与纠正、产出物（PR、工单、分支），每项都注明聊天 UUID。只有一两段聊天时，跳过铺开，直接搜。原始聊天记录留在子智能体里。主线程只拿到它们的发现。每个子智能体的推理档位和快/标准速度，按 **poteto-mode** 技能的 Subagents 一节来选。
4. 只要主题点到了某个功能、文件、子系统、领域或 bug，就扫一遍共享记录。这是默认动作，不是判断题，"my work on X" 也不能豁免。把它交给 **why** 技能的来源调查员，但把问题从"这东西为什么这么做"引向"当前状态是什么、试过什么没站住、用户还在报什么"。复用它的按来源作战手册，让调查员和聊天历史挖掘并行跑，继承它的姿态：每个来源一个调查员，空结果也是发现，MCP 不可用就跳过并说明。把回来的东西折进简报。只有纯活动回顾、没有点名目标时（"what did I do this week"）才跳过这一步，那种情况下你自己的历史和实时状态就是全部答案。
5. 对照实时状态核实。把挖掘和扫描浮出来的 PR、分支、工单，用 `git` 和 `gh` 查一遍。当答案取决于某个智能体实际做了什么（跑了哪些工具、读了哪些文件、撞了哪些错误）时，读完整聊天记录，而不只是裁剪过的本地副本。
6. 按下面的契约写简报。按线程分组。紧扣点名的主题。

## 输出契约

先给胶囊，再给线程状态，再给问题，最后给下一步。更细的内容放下面，或者砍掉。

- **胶囊。** 最多 5 条。这项工作是什么，整体进展到哪。
- **线程。** 每个一行，前缀恰好一个状态标签：`[merged #N]`、`[open PR #N]`、`[in flight <branch>]`、`[verified, uncommitted]`、`[reverted #N]` 或 `[planned, not started]`。没有标签的线程就是还没做完，给它打上标签。
- **问题。** 最多 5 条，反复出现的那些。包含用户还在报的症状，以及任何上线后又被回滚的修复，好让下一次尝试从上次失败的地方开始。
- **下一步。** 单个最有用的下一步动作，要具体。

相邻的功能或工单不写进来，除非它挡住了这一项。当胶囊和线程行超出一屏时，先砍细节再砍线程。简报要通过 **unslop** 技能来写，聊天发现按 UUID 引用，共享记录的发现按其来源引用（PR #、工单 ID、聊天永久链接、错误跟踪器 issue），任何公开输出前先脱敏私有上下文。

**回复：** 按上面的契约给出简报。
