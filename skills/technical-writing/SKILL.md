# 技术写作

写到一个疲倦的工程师第一遍就能懂。

- 删掉每一个不干活的词。
- 用短的、日常的词：「use」，不用「utilize」。
- 一条规则把句子写得更差时，换一种办法修，或者别动它。
- 写真实的符号、文件、旗标或命令名，不要写同义词，也不要写对它的描述。
- 不要发明行话。用开发者会说出口的词。有名字的模式，第一次出现时说明它是什么意思。

## 变化节奏

- 句子长短错开。一句话装了两个想法，就拆开。一个想法需要长句，就留着。
- 解释里可以有观点。参考保持干。
- 要具体。不要写「schema 改动可能出问题」，要写「列重命名会让构建失败」。

## 先选定模式（Diátaxis）

一份文档只用一种模式。不要混。拆开，再用链接连起来。

- **教程：边做边学。** 说学习者将做出什么。每一步都产生一个看得见的结果，并告诉他们应该看到什么。解释只留一个从句加一个链接。
- **操作指南：通向一个目标的步骤。** 解决读者的问题。假定对方已经会。只有动作。允许分叉。指南用任务来命名。
- **参考：供查找的事实。** 只描述。干、全、确定。结构和所描述的东西对齐。
- **解释：理解和为什么。** 一个有边界的题目。给出上下文：设计决定、历史、约束、备选。观点只允许出现在这里。

## 把句子写给读者（Google developer style）

- 用「你」对读者说话，用现在时。
- 说清谁做了什么。只有行动者未知或无关时，被动才可以。
- 指令写成命令。条件放在指令前面，常见情况放在前面。
- 不要行话，不要比喻，不要「请」，步骤里绝不要「simply」「easy」或「quickly」。
- 不要预告，也不要让连续的句子用同一个短语开头。
- 链接的文字要说出它通向哪里。
- 标题承载要点，用句子式大小写。每页一个 h1，不要跳级。
- 顺序用编号列表，其余用项目符号。用一个完整的句子引出列表。各项保持平行。
- 代码用代码字体。界面元素用粗体。并列项的最后一项前也加逗号。丢掉「etc.」。

## 让陈述一次只承载一条（STE 规则）

- 一句一条指令。其他地方一句一个想法。
- 指令长过大约 20 个词、其他句子长过大约 25 个词时，拆开。
- 警告或条件放在它所守的那一步之前。
- 保留「the」和「a」。
- 每个词只有一个意思，每个动作只选一个词。
- 步骤写成直接命令，不要叙述，也不要用被动。
- 能不用「-ing」词就不用。

## 不留下可以有两种读法的句子（Global English）

- 「only」「not」这类词紧挨着它们所改变的那个词。
- 拆开长的名词串。
- 每一个「it」「they」「this」都指向一件明显的东西。绝不要用「this」或「which」去指一整句。
- 不要丢掉动词，也不要丢掉标出结构的小词，例如「that」。
- 一连串里重复冠词，如果这样能避免误读。说清「and」或「or」连接的是哪些部分。
- 用句号，不用分号或长破折号。不要斜杠，也不要「(s)」。括号里的文字要是一个完整的语法单位。
- 每一件东西，到处都用同一个名字。
- 跳过习语、口语、拉丁缩写和比喻。

## 声音与仓库细节

- 本技能碰到的每一份文档都应用 **unslop** 技能。那份技能拥有腔调模式的目录：AI 词汇、填充、含糊其辞、版式破绽。
- PR 描述和提交说明也是写作。除了 Diátaxis，每一层都适用于它们。PR 正文是审查者一分钟内能读完的简报。不要粘贴 swarm 日志、SHA 列表或指标表。链过去。
- 产品界面文案不是文档。那些用你们产品自己的文案指南。
- 代码片段用制表符缩进。写真实路径。每一个计数或目录树的说法，在合入它的那次提交上必须为真，并附上重新生成它的命令。
