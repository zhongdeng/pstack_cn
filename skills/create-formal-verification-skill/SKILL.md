# 创建一个形式化验证技能

测试只检查有人想到要写的那些情况。形式化验证检查一个明确范围内的所有情况：模型里步骤的每一种顺序、某个上界以内的每一个输入，或者每一个输入。这个技能找出仓库里最需要验证的那部分代码，验证它的一个性质，并留下一个项目本地技能，让下一个智能体拿这个性质去检查改动。写这个技能时，要假设读者是一个冷启动的智能体，正在改代码，从没见过你的工作。用户必须能信任结果，并且不用学验证语言就能照着行动。

## 从代码里选目标

答案从代码库里找，只问用户你观察不到的东西。如果用户点名了某个区域或某个 bug，就从那里开始。

好的目标是代码做出的一个承诺：一旦被打破就会伤害用户，而测试又很少覆盖到打破它的那种情况。选仓库里最强的这类目标，而不是最容易验证的那个。

## 让问题来选工具

选能最低成本回答问题的工具：模型检查器、证明助手、基于 SMT 的验证器，或者其他工具。事件会不会以坏顺序发生，通常适合用模型检查器在一个小模型上验证，任何语言里 TLA+ 都是默认选择。代码本身对每个输入是否都表现正确，比如内存安全、溢出、数据结构不变量，通常适合用直接跑在代码上的验证器。如果这个语言没有能跑的验证器，就直说，然后用生成的输入去测真实代码，而不是给函数手写一个模型。必须在任意规模都成立、有界不够用的性质，可能需要证明。优先选仓库开发者能安装、能运行的工具，并告诉用户你为什么选它。

## 怎样才算好

- **忠于代码。** 模型或证明的每一部分都指向评审者能打开的代码。验证当作不可分割一步的东西，在代码里也是不可分割的一步。名字都来自这个仓库。
- **能失败。** 从没见过失败的检查证明不了任何东西。让每个性质在它所守护代码的一个坏变体上失败，比如去掉一个检查或调换步骤顺序。
- **发现就是发现。** 当前代码违反性质时，用代码的语言把反例报出来。不要为了让检查通过而弱化性质或模型，也不要改产品代码，除非用户要求。
- **对范围诚实。** 说清楚验证了什么、在什么边界和假设下、漏掉了什么。通过只覆盖模型或边界，不覆盖整个系统。
- **不用工具也能读懂。** 用各一句大白话说清性质和危害。用代码里的词，把反例讲成一小段步骤序列。
- **重跑便宜。** 一条命令、可复现的工具版本，运行时间短到下一个智能体愿意在每次相关改动上都跑一遍。
- **和代码保持同步。** 记录每个检查覆盖哪些文件和函数，以及你最后一次确认验证描述的就是这些代码时的 commit。覆盖的代码在那个 commit 之后变了，下一个智能体就能看出验证需要重新看一眼。

## 生成 verify 技能

写一个项目本地技能，frontmatter 里写明区域和什么时候用。没有 frontmatter，技能根本不会注册。只看这个技能，下一个智能体就必须能判断一次改动有没有碰到被验证的代码、跑检查、分清真 bug 和建模错误，以及在改动是有意的时候更新验证。把覆盖记录和同步 commit 放进技能里，并告诉下一个智能体，只有确认验证描述的就是新 commit 上的代码之后，才能把同步 commit 往前移。用这个仓库真实的命令、路径和名词，不要留占位符。

如果检查是 TLA+ 模型，告诉下一个智能体用 pstack 的 [`/statechart`](../statechart/SKILL.md) 技能读每一个结果。它会把检查器发现的每个不变量违反，用大白话画成最短路径。检查通过时，`/statechart` 会画一张系统在状态之间怎么走的图。按名字引用 `/statechart`。它的命令、选项和文件路径在不同版本和机器上会变，所以一个都不要抄进生成的技能或它的脚本里。

## 交付前先自己证明一遍

像下一个智能体那样，照着生成的技能走一遍，用一个会打破真实代码里该性质的临时改动。它必须能抓到这次破坏。然后撤掉临时改动，确认检查回到原来的状态：通过，或者只在你将要报告的发现上失败。一个从没跑过的 verify 技能只是草稿。如果技能漏掉了破坏，或者某一步跑不起来，就修技能或修验证，不要动临时改动。

## 交付

告诉用户你验证了什么、用了哪个工具以及为什么、边界在哪、检查用大白话发现了什么、怎么跑，以及它不覆盖什么。只有找到相近的第二个目标时才建议它。告诉用户，改动之后如果没重新检查验证，就用 `/maintain-formal-verification-skill` 把验证重新对齐。
