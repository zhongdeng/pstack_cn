# 先分离，再串行化共享状态

当并发操作者可能共享可变状态时，先问一句：他们真的需要同一个可变对象吗？如果不需要，就消除共享。如果共享是真实存在的，就从结构上强制串行化：锁文件、分阶段执行、独占所有权。指令和约定不是并发控制。

**为什么：** 对共享状态的并发写入会产生竞态条件，这类问题时有时无、难以复现、调试成本很高。

**模式：**
1. **找出共享的可变状态**（双方都读写的文件、双方都推送的分支、既定义又消费的 API）。
2. **默认做法：消除共享的写入目标。** 问一句：这些操作者是需要一个权威对象，还是在各自发布独立的事实？给每个操作者分配它自己拥有的文件、键、分支或状态目录，只在读取和汇报的边界上合并。两个 worker 各自把自己的 `lastX` 字段写进同一个 `state.json`，这仍然是共享修改。`indexer-state.json` + `metrics-state.json` 就不是。
3. **只有当单一共享写入目标确实是真正的不变量时，才从结构上串行化访问**（锁文件、分阶段执行、单写入方操作者，或原子 compare-and-swap）。把"我们需要一把锁"当成需要检查的设计坏味道，而不是默认答案。
