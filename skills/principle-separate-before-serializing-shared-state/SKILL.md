# 先分开，再串行化共享状态

当并发参与者可能共享可变状态时，先问他们是否需要同一个可变对象。如果不需要，就消除共享。当共享是真的，用结构强制串行化：锁文件、顺序阶段、独占所有权。指令和约定不是并发控制。

**为什么：** 对共享状态的并发写入会造成竞态，它们间歇出现、难以复现、调试昂贵。

**模式：**
1. **找出共享的可变状态**（双方都读又写的文件、双方都推送的分支、双方都定义又消费的 API）。
2. **默认：消除共享的写入目标。** 问：这些参与者需要一个权威对象，还是在发布各自独立的事实？给每个参与者自己拥有的文件、键、分支或状态目录，只在读取/报告的边界合并。两个 worker 各自把 `lastX` 字段写进同一个 `state.json`，仍然是共享变更。`indexer-state.json` + `metrics-state.json` 则不是。
3. **只有当单一共享写入目标是真正的不变量时，才用结构串行化访问**（锁文件、顺序阶段、单写入者参与者，或原子的比较并交换）。把“我们需要一把锁”当成要检查的设计气味，而不是默认答案。
