# 爆炸半径

在它交付之前，找出一次改动会在别处弄坏什么。用于「X 的爆炸半径」、「这可能弄坏什么」，或评审一份你还不太信任的小 diff。

和 `how`、`why` 配套。`how` 告诉你代码在做什么。`why` 告诉你它为什么长成这样。爆炸半径告诉你它会在别处弄坏什么。

把调用方列出来不是这份工作。agent 一秒就能 grep 到那些。这份工作是 grep 不会让你看见的那种破坏。

## 不要相信你自己写的说明

一份听起来对的爆炸半径说明一文不值。它读起来很有说服力，不管它是不是真的。所以不要把说明交回去就算完。找出整件事依赖的那一两个事实，用跑代码来证明它们。

### 你有多确定

对这次改动的安全性所依赖的每条事实，在便宜的前提下尽量把它在这张清单上往下推，并说明停在了哪一步。

1. 你这么说的。单凭这一点一文不值。
2. 你指向了那一行。一个真实的 `file:line`，或库自己的源码。
3. 你证明了坏情况不会发生。你把失败一步步走了一遍，它到不了那里。
4. 你跑过了。一个脚本或测试调用真实代码，你错了它就大声失败。
5. 你在正在运行的应用里复现了它。

第 4 步通常就是一个小脚本：导入应用实际交付的同一个库，调用你担心的那个确切函数。

## 步骤

1. 读这次改动。diff、它新增、修改和删除的符号，以及它现在有什么不同，包括 diff 没写明的那部分。用 `why` 的第 2 步把 PR 和 commit 拉下来。
2. 找出它之所以安全所依赖的那一个事实。大多数看起来有风险的改动，安全是因为单独一个事实，比如「这次调用只丢掉已经死掉的缓存条目，其他什么都不做」。找到那个事实。它成立的话，大多数有风险的情况就一次清掉了。把时间花在这里，不要花在一长串也许上。
3. 看 grep 停下来的地方。读你调用的那个库的源码，核对它钉住的版本和任何本地补丁。弄清事情在什么时候跑：微任务、卸载和拆卸、Solid 还是 React。跟着符号搜索会漏掉的东西走：API 返回的 JSON、一个数据库列、一种线上格式、另一种语言在读同样的字节、一个功能开关、下游三跳的代码。
4. 对每个风险诚实。给它一个真实的发生可能，以及一旦发生的真实代价。留下你确认了的风险。你检查过并排除的，单独列出来。规则和 `why` 一样。引用真实的 `file:line`，一次什么都没找到的搜索仍然是一个答案，永远不要编造调用方或 API。
5. 证明那一个事实。写一个跑真实代码的脚本或测试，跑它，把发生的事贴出来。
6. 又大又宽的改动，把它当成一次 `arena` 来跑。让不止一个模型回答同一个问题，再把答案合并。不同的模型抓住不同的真缺陷。

## 交回什么

- **它做了什么。** 改了什么，包括不明显的那部分。
- **它之所以安全所依赖的那一个事实。** 陈述它，说明你把它推到了哪一步，并展示证明。证明不了，就写未证明。
- **风险。** 每一条都写明它怎么坏、`file:line`、多可能、多糟，以及怎么检查。要紧的那些把证明贴上。
- **已排除。** 你检查了什么，以及为什么没问题。
- **合并之前。** 能抓住真缺陷的最便宜的测试或复现，包括你写的那个脚本。

用 `unslop` 过一遍再写出来，引用真实代码，公开到任何地方之前去掉任何私密内容。

**回复：** 上面这份说明，其中那一个安全事实要么已证明，要么标成未证明。
