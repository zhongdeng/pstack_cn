# 影响范围

在变更上线前，找出它在别处弄坏了什么。用于 "blast radius of X"、"what could this break"，或审查一个你还不信任的小 diff。

`how` 和 `why` 的搭档。`how` 告诉你代码做了什么。`why` 告诉你它为什么长这样。影响范围告诉你它在别处弄坏了什么。

列出调用方不是这份工作。智能体一秒就能 grep 出来。这份工作是找出 grep 看不到的破坏。

## 别信你自己写的说明

一篇听起来对的影响范围说明一文不值。不管它是不是真的，读起来都很有说服力。所以别把说明交回去。找出整件事依赖的那一两个事实，然后靠运行代码来证明它们。

### 你有多确定

对变更安全性所依赖的每个事实，用尽量低的成本把它推到下面列表里尽可能靠下的位置，并说明它停在哪一步。

1. 你只是这么说了。单凭这一点一文不值。
2. 你指出了那一行。一个真实的 `file:line`，或者库自己的源码。
3. 你证明了坏情况不会发生。你把失败一步步走了一遍，它走不到。
4. 你跑过了。一个脚本或测试调用真实代码，你错了它就大声失败。
5. 你在运行中的应用里复现了它。

第 4 步通常就是一个小脚本，导入应用实际发布的同一个库，调用你担心的那个确切函数。

## 步骤

1. 读变更。diff，它新增、修改、删除的符号，以及它现在行为上有什么不同，包括 diff 没写出来的那部分。用 `why` 第 2 步拉出 PR 和提交。
2. 找出那个让它安全的关键事实。大多数看起来有风险的变更之所以安全，是因为一个单一事实，比如"这个调用只丢弃已经失效的缓存条目，别的什么都不做"。找到那个事实。它成立，大多数有风险的情况就一次性排除了。把时间花在这里，而不是花在一长串可能上。
3. 看 grep 停下的地方。读你调用的库的源码，检查它锁定的版本和任何本地补丁。搞清楚东西什么时候运行：微任务、卸载和 teardown、Solid 对 React。跟进符号搜索漏掉的东西：API 返回的 JSON、一个 DB 列、一种线格式、另一种语言读同样的字节、一个功能开关、下游三跳之外的代码。
4. 对每个风险诚实。给它一个真实的发生概率，和一个真实的代价。保留你确认的风险。把你检查过并排除的单独列出来。规则和 `why` 一样。引用真实的 `file:line`，搜不到东西也是一个答案，绝不编造调用方或 API。
5. 证明那个关键事实。写一个脚本或测试跑真实代码，运行它，把结果贴出来。
6. 对于大或广的变更，把它当作 `arena` 来跑。问不止一个模型同一个问题，然后合并答案。不同的模型能抓到不同的真实 bug。

## 要交回什么

- **它做了什么。** 改了什么，包括不明显的那部分。
- **那个让它安全的关键事实。** 陈述它，说明你把它推到了哪一步，并展示证明。如果你证明不了，写 unproven。
- **风险。** 每个都写明它怎么坏、`file:line`、多可能和多严重、怎么检查。对重要的那些贴上证明。
- **已排除。** 你检查了什么，以及为什么没问题。
- **合并之前。** 能抓到真实 bug 的最便宜的测试或复现，包括你写的脚本。

通过 `unslop` 来写，引用真实代码，在发到任何公开地方之前删掉所有私密内容。

**回复：** 上面那篇说明，其中那个安全事实要么已证明，要么标记为 unproven。
