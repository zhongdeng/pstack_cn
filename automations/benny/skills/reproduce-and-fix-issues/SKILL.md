# 复现并修复问题

等待来源话题串中的可信分诊标记。通过目标应用的真实界面复现完全相同的症状。已有修复时先验证它。只有在确认复现之后，才尝试限定范围的修复。

加载自动化提供的外部 Benny 配置。如果配置、必需操作、控制适配器或已完成的功能映射缺失，就失败即关闭。

## 硬性安全规则

- 在做任何工作之前，先冻结来源频道和根话题串坐标。
- 绝不要在来源频道发送根消息。
- 在每一次向来源话题串发帖之前，先对来源父消息做预检。
- 协调者是唯一向 Slack 发帖的一方。
- 被委派的分析工作者是只读的，只返回发现或媒体笔记。
- 修复阶段的代码工作者只有在其环境可证明排除了 Slack 凭据以及一切 Slack 写操作时，才可以编辑。否则由协调者编辑。
- 每条子提示都必须明确禁止 `SendSlackMessage`、`PostToSlack`、`chat.postMessage`，以及其他一切 Slack 写操作。
- 绝不要给子级 Slack 令牌、发帖指令、用于发帖的来源坐标，或对外报告的权限。
- 如果子级需要 Slack 写权限才能运行，就不要启动它。
- 工具类 bot 是证据来源。除非有人明确把修复委派给它们，否则它们不拥有该修复。
- 完全相同的区分性症状必须通过真实界面交互出现两次。
- 状态检查可以确认一项观察。它不得注入或强制制造该症状。
- 没有确认的复现，就不要编写修复。
- 已有的 pull request 或提交会把本次运行切换到验证模式。不要在其之上另行编写改动。
- 使用 `github.com` 的 pull request 链接。
- 不要把采集物、录屏、日志和令牌放进源代码管理。
- 对被委派的分析使用 pstack 的 `principle-guard-the-context-window`。
- 在复现、修复和验证过程中，应用 pstack 的 `principle-sequence-verifiable-units`、`principle-fix-root-causes` 和 `principle-prove-it-works`。

## 1. 冻结来源坐标

在制定工作清单或委派之前：

1. 要求触发频道等于已配置的来源频道。
2. 若存在 `trigger.thread_ts`，把 `SOURCE_THREAD_TS` 设为它。否则使用 `trigger.ts`。
3. 要求 `SOURCE_THREAD_TS` 非空。
4. 把 `SOURCE_CHANNEL_ID` 和 `SOURCE_THREAD_TS` 存为不可变的值。
5. 阅读来源话题串，并验证它的根具有这些确切坐标。
6. 获取来源永久链接。

绝不要用回复时间戳、运维时间戳或状态消息时间戳替换这些值。

在每一次来源频道发送之前：

1. 按不可变坐标阅读话题串。
2. 确认父消息存在、未被删除，并且仍然属于来源频道。
3. 只使用 `channel=SOURCE_CHANNEL_ID` 和 `thread_ts=SOURCE_THREAD_TS` 发送。
4. 再次阅读话题串，并验证新消息是一条回复。

如果任何检查失败，就什么都不要发。绝不要在根上重试，也不要在回退频道中重试。

## 2. 等待分诊契约

在已配置的结论预算内观察来源话题串。等待期间保持沉默。

仅在以下条件全部成立时接受一条结论：

- 其作者与 `slack.triage_identity_user_id` 相符。
- 它是 `SOURCE_THREAD_TS` 下的一条回复。
- 它恰好包含一个已配置标记。

公开的标记形式：

```text
[benny:bug]
[benny:bug] tracker=https://tracker.example/issue/123
[benny:performance]
[benny:performance] tracker=https://tracker.example/issue/123
[benny:other]
```

仅对 `bug` 或 `performance` 继续。记下可选的跟踪器 URL。对于 `other`、缺失的结论、不可信的作者、相互冲突的标记或超时，静默停止。

该标记取代私有 bot 身份，以及自由格式的结论匹配。

## 3. 应用归属与修复产物门禁

在开始工作之前，立即重读话题串。

### 已有人明确在修复

当某人明确认领修复、给出具体的实现计划，或要求另一个代理去实现、打补丁、修复或打开 pull request 时，停止。

不要把下列情况当作修复归属：

- bot 在总结证据。
- 某个工具在查找日志或工单。
- 有人要求 bot 诊断、解释、检查或复现。
- bot 发出了成因假设，但并没有同意去实现它。

判断的是被请求的动作，而不是有没有 bot 在场。

### 已存在修复产物

如果一个打开的 pull request 或已合并提交有可能修复这份报告，就转去 `references/verify-existing-fix.md`。

产物可以来自话题串、跟踪器 issue、仓库历史，或 pull request 搜索。没有提交或 pull request 的声称，不是修复产物。

如果某人负责这项工作，但还没有产出产物，就停止。不要跟他们抢。

## 4. 打开可选的运维话题串

如果配置了 `slack.operations_channel_id`，协调者可以在那里创建一条根状态消息。这是复现工作流中唯一允许的根消息。

把它的坐标存为 `OPERATIONS_CHANNEL_ID` 和 `OPERATIONS_THREAD_TS`。绝不要把它们和来源坐标搞混。

使用已配置的纯 Unicode 状态字符串。状态文本保持简短：

- 正在复现
- 无法复现
- 已阻塞
- 已复现
- 正在验证已有修复
- 正在尝试限定范围的修复
- 已打开草稿 pull request
- 修复未能落地

优先使用已配置的 Cursor Slack 操作。只有当用户为某个狭窄的缺失能力配置了 `BENNY_SLACK_BOT_TOKEN` 时才使用它，例如编辑这一条状态消息。绝不要把该令牌暴露给工作者。

如果没有配置运维频道，把详细状态留在自动化运行输出中。不要用来源频道的根消息代替。

## 5. 加载并检查控制适配器

阅读 `references/control-adapter.md`，以及 `control.feature_map_path` 处已完成的映射，然后调用 `control.skill_name` 所指定的 skill。

找到与所报告的用户路径相匹配的功能映射小节。在驱动应用之前先阅读它。如果没有小节覆盖该功能，把本次运行标为阻塞，而不是编造路径或选择器。

要求具备全部七项能力：

1. 启动已配置的目标应用和测试环境。
2. 导航到已映射的功能，并演练其文档中写明的状态。
3. 用点击、输入、按键、滚动、拖拽、调整大小或导航来驱动真实界面。
4. 在不改变状态的前提下检查状态。
5. 截取截图。
6. 开始并停止屏幕录制。
7. 清理进程、会话、配置档和临时数据。

如果适配器不存在，或任何必需能力缺失，把运维状态标为阻塞并停止。不要把截图、单元测试、状态改写或阅读源码假装成一次界面复现。

## 6. 研读报告

阅读完整的来源话题串；若有跟踪器 issue，也阅读它。

收集：

- 确切的操作路径
- 预期行为
- 观察到的行为
- 两者分叉处的区分性状态
- 频率
- 版本、环境和平台
- 附件和错误特征
- 候选代码区域

检查截图和视频。有用时，使用只读的并行工作者来做代码历史、测试想法、爆炸半径映射和媒体审阅。每个工作者得到一个范围很窄的问题，以及 Slack 写操作禁令。

使用 pstack 的 `how` skill，在仓库中追溯该操作。使用 `why` 查看回归历史和防御性代码。形成相互竞争的成因假设，并找出能把它们区分开的证据。

## 7. 复现

通过控制适配器启动目标应用。

在操作之前，确认应用、工作区、账号、数据集和功能状态都是正确的。使用稳定的应用标记。不要只依赖窗口顺序，或一个眼熟的标题。

通过真实界面操作，驱动所报告的路径。

在称之为已复现之前：

1. 指出正确的最终状态。
2. 指出损坏的最终状态。
3. 到达两者分叉的那一点。
4. 观察到损坏的状态。
5. 重置足够的状态，使第二次尝试彼此独立。
6. 重复同一条路径，并再次观察到同一个损坏的状态。
7. 在可能时，交叉核对一个真实的状态值。

预期中的对话框、加载状态或准备步骤并不是这个 bug。要采集的是那个把正确行为与损坏行为区分开的最终状态。

使用已配置的复现预算。如果症状没有在该预算内复现，就报告一个干净的 `Could not reproduce` 结果。如果环境无法提供某项必需能力，就报告 `Blocked`，并说明缺了什么。

## 8. 采集并审阅证据

对于一次成功的复现：

- 录下穿过该症状的完整路径。
- 截取损坏的最终状态。
- 保存一份简短记录，写明确切步骤和观察到的状态。
- 把产物放在已配置的临时产物目录中。

让一位只读的媒体审阅者回答一个问题：证据是否明显展示了那个区分性的损坏状态？

如果答案是否定的或不确定的，这次复现就尚未确认。采集更好的证据，或使用 `Could not reproduce`。

只有在配置了运维话题串时，才把详细证据发到那里。来源侧的更新保持简短。

## 9. 报告复现结果

先更新运维状态。

对于 `Could not reproduce` 或 `Blocked`，不要在来源话题串发帖。结果由运维话题串或运行输出承载。

对于已确认的复现，执行来源预检，并最多发送一条未经要求的来源回复：

- 说明该问题已复现。
- 若存在运维证据话题串，附上它的链接。
- 最多包含三条简短发现。
- 若存在跟踪器 issue，附上它的链接。
- 默认不要提醒负责人。

只有当已配置的 Slack 操作能把证据留在同一个来源话题串内，并且组织的保留策略允许时，才附加证据。

等待已配置的驳回窗口。如果有人指出准备或解读是错的，就把这次复现纠正一次。在窗口结束且没有出现有效驳回之前，不要开始修复阶段。

## 10. 验证已有修复

当存在修复产物时，遵循 `references/verify-existing-fix.md`。

验证必须展示：症状在基线上出现，并在修补后的构建上消失。两条路径都通过真实界面走两次。

不要编辑已有修复，不要添加与之竞争的补丁，也不要打开替代的 pull request。

## 11. 判定限定范围的修复是否可做

只有以下条件全部成立时，才尝试修复：

- 结果是一次单纯的已确认复现。
- 媒体审阅确认了损坏的最终状态。
- 没有出现已有的修复产物。
- 在驳回窗口期间，没有人认领这项修复。
- 运行时证据指明了根因。
- 可能的改动落在已配置的修复预算和仓库范围之内。
- 控制适配器能够同时运行基线构建和修补后的构建。

如果任何条件不成立，就保留复现报告，并在不打开 pull request 的情况下停止。

门禁通过后，把运维状态更新为 `Attempting bounded fix`。

## 12. 追溯根因并实现

协调者拥有每一次 Slack 发送、最终的 diff 审阅、提交，以及 pull request。

只读工作者可以：

- 追溯代码和历史
- 提议测试
- 映射爆炸半径
- 审阅 diff
- 审阅媒体

它们不编辑、不执行外部写入、不发布状态，也不拥有该修复。

只有当工具隔离已经从该工作者身上移除 Slack 凭据和一切 Slack 写操作时，才可以在这个阶段委派一次范围收得很紧的代码编辑。它的提示词仍然必须带有明确的 Slack 写操作禁令。协调者审阅这次编辑，并运行或验证必需的测试。如果工具隔离是否成立还不确定，就把编辑留在协调者这里。

用运行时证据确认机制。在编辑之前，排除相互竞争的假设。

用最小的、站得住脚的改动修复根因。

- 当存在成本低的本地测试目标时，调用 pstack 的 `tdd` skill，并在修复之前写下会失败的测试。
- 当这条路径成本高、不清楚，或集成成分很重时，说明为什么跳过了 TDD。
- 不要带上无关的清理。
- 如果改动超出已配置的工作量预算或风险预算，就停止。

## 13. 证明修复有效

保留原来的基线证据。

在修补后的构建上：

1. 走同一条真实界面路径。
2. 重复两次。
3. 展示损坏状态已经消失。
4. 展示预期状态出现在它原来的位置。
5. 采集修复后的录屏和截图。
6. 交叉核对基线所用的同一个真实状态值。

编译、单元测试、代码审阅，或一份看起来说得通的 diff，都不是修复后证据。

先运行聚焦测试，再对改动行为周围的爆炸半径做冒烟检查。覆盖这次改动可能影响的邻近状态、输入、权限、平台和失败路径。如果仍有回归，就在不打开 pull request 的情况下停止。

## 14. 打开草稿 pull request

只有在具备修复前后的证据之后：

- 审阅最终 diff，查找无关改动和密钥。
- 运行仓库所要求的检查。
- 当仓库工作流允许时，创建小而有序的提交。
- 打开一个草稿 pull request。绝不要从本工作流合并或部署。
- 用该跟踪器所支持的 pull request 语法，链接已配置的跟踪器 issue。
- 使用已配置的公开 URL 形式，通常是 `https://github.com/{owner}/{repo}/pull/{number}`。
- 写上复现步骤、根因、测试结果、修复前后的证据，以及爆炸半径检查。
- 让 pull request 正文和所有 Slack 更新都经过 pstack 的 `unslop` skill。

如果 pull request 创建失败，不要声称成功。把提交或分支状态留在运行输出中，并把运维状态标为 `Fix did not land`。

成功时，把运维状态标为 `Draft pull request opened`，并在运维话题串中发送一条简短回复，附上该 pull request 的链接。不要再创建一条来源频道根消息，也不要发送未经要求的来源回复。

## 15. 跟进与清理

在一个跟进窗口内观察已配置的运维话题串。

- 依据已经收集到的证据，回答直接提出的问题。
- 当某条更正否定了原来的准备时，应用这一次具体更正，并重新跑一次复现。
- 不要介入人工协调和旁支闲聊。
- 被要求停止时就停止。

始终调用控制适配器的清理能力。产物只保留到已配置的保留策略所允许的时长。
