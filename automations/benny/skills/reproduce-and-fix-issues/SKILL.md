# 复现并修复问题

在来源线程里等待一个可信的分诊标记。通过目标应用的真实 UI 复现确切的症状。已有修复时，验证那个修复。只有在复现确认之后，才尝试一个有边界的修复。

加载自动化提供的外部 Benny 配置。如果配置、必需动作、控制适配器或已完成的 feature map 缺失，就按失败关闭处理。

## 硬性安全规则

- 在做任何工作之前，先冻结来源频道和根线程坐标。
- 绝不在来源频道里发根消息。
- 每次往来源线程发消息之前，先对来源父消息做预检。
- 协调者是唯一往 Slack 发消息的人。
- 被委派的分析 worker 是只读的，只返回发现或媒体说明。
- 修复阶段的代码 worker 只有在它的环境可证明地排除了 Slack 凭据和所有 Slack 写动作时，才可以编辑。否则由协调者来编辑。
- 每个子任务的 prompt 都必须明确禁止 `SendSlackMessage`、`PostToSlack`、`chat.postMessage` 以及所有其他 Slack 写操作。
- 绝不给子任务 Slack token、发帖指令、用于发帖的来源坐标，或对外汇报的权限。
- 如果子任务必须要有 Slack 写权限才能跑，就不要启动它。
- 工具机器人是证据来源。除非有人明确把修复委派给它们，否则它们不拥有这个修复。
- 那个确切的区分性症状必须通过真实 UI 交互出现两次。
- 状态检查可以确认某个观察。它不能注入或强制制造这个症状。
- 没有确认的复现，就没有编写的修复。
- 已有 pull request 或 commit 时，本次运行切换到验证模式。不要在它们之上另写修复。
- 使用 `github.com` 的 pull request 链接。
- 截图、录屏、日志和 token 不要进源码管理。
- 委派分析时使用 pstack 的 `principle-guard-the-context-window`。
- 在复现、修复和验证的全过程中应用 pstack 的 `principle-sequence-verifiable-units`、`principle-fix-root-causes` 和 `principle-prove-it-works`。

## 1. 冻结来源坐标

在列工作清单或委派之前：

1. 要求触发频道等于配置的来源频道。
2. 存在 `trigger.thread_ts` 时，把 `SOURCE_THREAD_TS` 设为它。否则用 `trigger.ts`。
3. 要求 `SOURCE_THREAD_TS` 非空。
4. 把 `SOURCE_CHANNEL_ID` 和 `SOURCE_THREAD_TS` 存为不可变的值。
5. 读取来源线程，确认它的根消息就是这些确切坐标。
6. 获取来源 permalink。

绝不要把这些值替换成某条回复的时间戳、操作时间戳或状态消息时间戳。

每次往来源频道发消息之前：

1. 用不可变坐标读取线程。
2. 确认父消息存在、未被删除，并且仍属于来源频道。
3. 只用 `channel=SOURCE_CHANNEL_ID` 和 `thread_ts=SOURCE_THREAD_TS` 发送。
4. 再读一次线程，确认新消息是一条回复。

任何一项检查失败，就什么都不发。绝不在根消息下或备用频道里重试。

## 2. 等待分诊契约

在配置的判定预算内盯住来源线程。等待期间保持沉默。

只有满足以下条件才接受一个判定：

- 它的作者匹配 `slack.triage_identity_user_id`。
- 它是 `SOURCE_THREAD_TS` 下的一条回复。
- 它恰好包含一个配置的标记。

公开标记形式：

```text
[benny:bug]
[benny:bug] tracker=https://tracker.example/issue/123
[benny:performance]
[benny:performance] tracker=https://tracker.example/issue/123
[benny:other]
```

只对 `bug` 或 `performance` 继续。记下可选的 tracker URL。遇到 `other`、没有判定、不可信作者、标记冲突或超时，就静默停止。

这个标记取代了私有机器人身份和自由形式的判定匹配。

## 3. 应用归属和修复产物门槛

在开始工作前立刻重读线程。

### 有人明确在修它

当有人明确认领这个修复、给出具体的实现计划，或让另一个智能体去实现、打补丁、修复或开 pull request 时，停止。

以下情况不算修复归属：

- 一个机器人总结了证据。
- 一个工具查了日志或工单。
- 有人让机器人去诊断、解释、检查或复现。
- 一个机器人发了原因假设，但没答应去实现。

判断的是被请求的动作，不是有没有机器人出现。

### 修复产物已经存在

如果有一个 open pull request 或已合并的 commit 看起来能修这个报告，切换到 `references/verify-existing-fix.md`。

产物可能来自线程、tracker issue、仓库历史或 pull request 搜索。没有 commit 或 pull request 的声称不算修复产物。

如果某个人拥有这项工作但还没产出产物，停止。不要和他们抢。

## 4. 可选地开一个操作线程

如果配置了 `slack.operations_channel_id`，协调者可以在那里创建一条根状态消息。这是复现工作流里唯一允许的根消息发帖。

把它的坐标存为 `OPERATIONS_CHANNEL_ID` 和 `OPERATIONS_THREAD_TS`。绝不要把它们和来源坐标搞混。

使用配置的纯 Unicode 状态字符串。状态文字保持简短：

- Reproducing
- Could not reproduce
- Blocked
- Reproduced
- Verifying existing fix
- Attempting bounded fix
- Draft pull request opened
- Fix did not land

优先用配置的 Cursor Slack 动作。只有当用户为某个狭窄的缺失能力（比如编辑这一条状态消息）配置了 `BENNY_SLACK_BOT_TOKEN` 时，才用它。绝不把 token 暴露给 worker。

如果没有配置操作频道，就把详细状态留在自动化运行输出里。不要拿来源频道的根消息来替代。

## 5. 加载并检查控制适配器

读 `references/control-adapter.md` 和 `control.feature_map_path` 处已完成的 map，然后调用 `control.skill_name` 指定的技能。

找到和所报用户路径匹配的 feature-map 小节。在驱动应用之前先读它。如果没有小节覆盖这个功能，就把本次运行标记为 blocked，而不是自己编一条路径或选择器。

要求全部七项能力：

1. 拉起配置的目标应用和测试环境。
2. 导航到已映射的功能并走一遍它记录在案的状态。
3. 用点击、输入、按键、滚动、拖拽、调整大小或导航来驱动真实 UI。
4. 检查状态而不改动它。
5. 截取屏幕截图。
6. 开始和停止屏幕录制。
7. 清理进程、会话、profile 和临时数据。

如果适配器缺失，或任何一项必需能力缺失，就把操作状态标为 blocked 并停止。不要把截图、单元测试、状态改动或读源码当成 UI 复现。

## 6. 研究报告

读完整的来源线程，有 tracker issue 时也读它。

收集：

- 确切的动作路径
- 预期行为
- 观察到的行为
- 两者分岔处的区分性状态
- 频率
- 版本、环境和平台
- 附件和错误特征
- 候选代码区域

查看截图和视频。需要时用只读的并行 worker 做代码历史、测试思路、影响范围映射和媒体审查。每个 worker 只拿一个狭窄的问题，并被告知禁止 Slack 写操作。

用 pstack 的 `how` 技能沿仓库追踪这个动作。用 `why` 查回归历史和防御性代码。提出互相竞争的成因假设，并找出能区分它们的证据。

## 7. 复现

通过控制适配器拉起目标应用。

在动手之前确认正确的应用、workspace、账号、数据集和功能状态。使用稳定的应用标记。不要只靠窗口顺序或一个熟悉的标题。

通过真实 UI 动作走一遍所报的路径。

在宣布复现成功之前：

1. 说出正确的最终状态。
2. 说出出错的最终状态。
3. 走到两者分岔的那个点。
4. 观察到出错的状态。
5. 重置足够多的状态，让第二次尝试是独立的。
6. 重复同一条路径，再次观察到同样的出错状态。
7. 可能的话，交叉核对一个真实的状态值。

一个预期中的对话框、加载状态或初始化步骤不是 bug。截取能区分正确行为和出错行为的最终状态。

使用配置的复现预算。如果症状在预算内没有复现，就报告一个干净的 `Could not reproduce` 结果。如果环境提供不了某项必需能力，就报告 `Blocked` 并说明缺了什么。

## 8. 截取并审查证据

复现成功时：

- 录下穿过症状的完整路径。
- 截取出错最终状态的屏幕截图。
- 保存一份简短说明，写清确切步骤和观察到的状态。
- 把产物放在配置的临时产物目录里。

让一个只读的媒体审查者回答一个问题：证据是否肉眼可见地展示了那个区分性的出错状态？

如果答案是否或不确定，复现就没有确认。截取更好的证据，或者用 `Could not reproduce`。

只有在配置了操作线程时，才在那里发详细证据。来源线程的更新保持简洁。

## 9. 汇报复现结果

先更新操作状态。

对于 `Could not reproduce` 或 `Blocked`，在来源线程里什么都不发。结果由操作线程或运行输出承载。

对于确认的复现，跑一遍来源预检，最多发一条未经请求的来源回复：

- 说明问题已复现。
- 有操作证据线程时，链接它。
- 最多包含三条简短发现。
- 有 tracker issue 时，链接它。
- 默认不 ping 负责人。

只有当配置的 Slack 动作能把证据留在同一个来源线程内，并且组织的保留策略允许时，才附上证据。

等待配置的驳回窗口。如果有人证明环境搭建或解读是错的，就纠正一次复现。在窗口关闭且没有有效驳回之前，不要开始修复阶段。

## 10. 验证已有修复

存在修复产物时，按 `references/verify-existing-fix.md` 执行。

验证必须展示症状在基线上存在、在打过补丁的构建上不存在。两条路径都要走两遍真实 UI。

不要编辑已有的修复，不要加一个竞争的补丁，也不要开一个替代的 pull request。

## 11. 判断有边界的修复是否够格

只有以下条件全部成立时才尝试修复：

- 结果是一个干净的确认复现。
- 媒体审查确认了出错的最终状态。
- 没有出现已有的修复产物。
- 在驳回窗口内没有人认领这个修复。
- 运行时证据定位到了根因。
- 可能的改动落在配置的修复预算和仓库范围内。
- 控制适配器能同时跑基线和打过补丁的构建。

任何一条不成立，就保留复现报告并停止，不开 pull request。

门槛通过时，把操作状态更新为 `Attempting bounded fix`。
## 12. 根因定位与实现

协调者负责每一条 Slack 消息、最终的 diff 审查、提交和 pull request。

只读 worker 可以：

- 追踪代码和历史
- 提出测试方案
- 梳理影响范围
- 审查 diff
- 审查媒体

它们不编辑、不执行外部写操作、不发状态，也不负责修复。

只有在工具隔离能移除该 worker 的 Slack 凭据和所有 Slack 写操作时，才可以在这一阶段委派范围严格受限的代码编辑。它的提示词仍必须带上明确的 Slack 写入禁令。协调者审查这次编辑，并运行或验证所需的测试。如果工具隔离不确定，就把编辑留在协调者手里。

用运行时证据确认机制。编辑之前先排除其他竞争假设。

用最小的合理改动修复根因。

- 当存在成本低的本地测试目标时，调用 pstack 的 `tdd` 技能，先写失败的测试再修复。
- 当路径成本高、不清晰或偏集成时，说明为什么跳过 TDD。
- 不夹带无关的清理。
- 如果改动超出配置的工作量或风险预算，就停下来。

## 13. 证明修复

保留原始基线证据。

在打好补丁的构建上：

1. 走同一条真实 UI 路径。
2. 重复两次。
3. 证明坏掉的状态已经消失。
4. 证明期望的状态出现在原来的位置。
5. 录一段修复后的视频并截图。
6. 交叉核对基线所用的同一个真实状态值。

编译、单元测试、代码审查或看起来合理的 diff 都不算修复后证据。

先跑聚焦测试，再对改动行为周围的影响范围做冒烟测试。覆盖这次改动可能影响的邻近状态、输入、权限、平台和失败路径。如果仍有回归，就停下来，不开 pull request。

## 14. 开一个草稿 pull request

只有在拿到前后对比证据之后：

- 审查最终 diff，检查无关改动和密钥。
- 运行仓库要求的检查。
- 在仓库工作流允许时，创建小的有序提交。
- 开一个草稿 pull request。绝不从这个工作流合并或部署。
- 用 tracker 支持的 pull request 语法关联配置的 tracker issue。
- 使用配置的公开 URL 形式，通常是 `https://github.com/{owner}/{repo}/pull/{number}`。
- 包含复现步骤、根因、测试结果、前后证据和影响范围检查。
- 把 pull request 文本和所有 Slack 更新都过一遍 pstack 的 `unslop` 技能。

如果 pull request 创建失败，不要声称成功。把提交或分支状态留在运行输出里，并把 operations 状态标为 `Fix did not land`。

成功时，把 operations 状态标为 `Draft pull request opened`，并在 operations 线程里发一条简洁的回复，附上关联的 pull request。不要创建第二个 source-channel 根消息，也不要发未经请求的 source 回复。

## 15. 后续跟进与清理

在配置的 operations 线程里观察一个跟进窗口。

- 用已经收集到的证据回答直接提问。
- 当某个具体纠正使设置失效时，应用这一处纠正并重跑一次复现。
- 不介入人的协调和闲聊。
- 被要求停时就停。

始终调用 control adapter 的清理能力。产物的保留时间不超过配置的保留策略允许的时长。
