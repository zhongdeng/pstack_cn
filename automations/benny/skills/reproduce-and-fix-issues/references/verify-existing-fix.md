# 验证已有修复

当一个打开的 pull request 或已合并提交有可能修复该报告时，使用这个模式。

已有产物拥有该修复。验证它。不要编辑它，不要编写与之竞争的补丁，也不要打开另一个 pull request。

## 判定产物是否合格

要求有一个具体产物：

- 一个打开的 pull request，其代码改动针对该症状
- 一个已合并的 pull request
- 一个已合并提交，其代码与意图都匹配

没有 pull request 或提交的话题串声称、跟踪器状态、分支名或成因假设，都不够。

当存在多个产物时，选择来源话题串或跟踪器所链接的那一个。否则选择与受影响代码最接近的匹配，并说明原因。

## 保护工作树

当仓库支持时，使用隔离的 worktree，或其他干净检出。不要覆盖用户的改动。

记录：

- 基线修订版本
- 修补后的修订版本
- pull request 或提交的 URL
- 两次运行共享的构建输入和环境输入

使用常规的 `github.com` pull request 链接。

## 测量基线

对于打开的 pull request，以其 base 分支作为基线。

对于已合并的修复，当修复紧前面的那个修订版本能够构建，并且代表旧行为时，使用该修订版本。

通过已配置的控制适配器：

1. 启动基线应用。
2. 确认应用和环境是正确的。
3. 通过真实界面操作走所报告的路径。
4. 观察区分性症状。
5. 重置并再做一次。
6. 采集基线录屏、截图和状态检查。

如果症状没有在基线上出现两次，就没有基线。不要声称修复有效。

## 测量修补后的构建

用相同的环境和数据构建并运行该 pull request 或修复提交。

1. 走同一条界面路径。
2. 重复两次。
3. 确认损坏状态已经消失。
4. 确认预期状态出现。
5. 采集修复后的录屏、截图，以及同一次状态检查。

不要停在编译或测试。修复后的结果必须来自一个正在运行的、已打上该补丁的应用。

## 结果

### 已确认

基线复现了两次，修补后的构建也两次都解决了它。

- 把运维状态标为已验证。
- 链接该产物。
- 在来源预检之后，向来源话题串发送一条简短回复。
- 写上修复前和修复后的结果。
- 不打开 pull request。

### 修复不足

症状在基线构建和修补后的构建上都出现。

- 把运维状态标为已复现但未修复。
- 链接该产物，并说明它没有解决该症状。
- 如果本次运行还没有发过常规的已确认复现来源更新，就发送它。
- 不打开与之竞争的 pull request。

### 无法定论

基线未能复现，修补后的应用无法运行，或证据没有展示区分性状态。

- 不要声称成功。
- 说明哪一半未能测到。
- 把结果留在运维话题串或运行输出中。
- 除非有直接的问题需要回答，否则不要在来源话题串发帖。

## 清理

停止两个构建，按保留策略移除临时配置档和采集物，并把仓库恢复到先前状态，且不丢弃用户的工作。
