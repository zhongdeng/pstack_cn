# 验证一个已有的修复

当一个开放的 pull request 或已合并的提交看起来能修复报告时，用这个模式。

已有的产物拥有这个修复。验证它。不要编辑它，不要写一个竞争性的补丁，也不要再开一个 pull request。

## 确认产物合格

要求有一个具体的产物：

- 一个开放的 pull request，其代码改动针对该症状
- 一个已合并的 pull request
- 一个已合并的提交，其代码和意图都匹配

只有线程里的说法、tracker 状态、分支名或原因假设，而没有 pull request 或提交，是不够的。

存在多个产物时，选源线程或 tracker 里链接的那个。否则选与受影响代码最接近的那个，并说明理由。

## 保护工作区

仓库支持时，用隔离的 worktree 或另一个干净的检出。不要覆盖用户的改动。

记录：

- 基线修订
- 打补丁后的修订
- pull request 或提交的 URL
- 两次运行共用的构建和环境输入

用常规的 `github.com` pull request 链接。

## 测量基线

对于开放的 pull request，用它的 base 分支作为基线。

对于已合并的修复，用紧挨着修复之前的那个修订，前提是该修订能构建，并且代表旧行为。

通过配置好的 control adapter：

1. 启动基线应用。
2. 确认是正确的应用和环境。
3. 通过真实的 UI 操作走一遍报告里的路径。
4. 观察那个有区分度的症状。
5. 重置并重复一遍。
6. 抓取基线录像、截图和状态检查。

如果症状在基线上没有出现两次，就没有基线。不要声称修复有效。

## 测量打补丁后的构建

用相同的环境和数据构建并运行 pull request 或修复提交。

1. 走同一条 UI 路径。
2. 重复两遍。
3. 确认坏掉的状态消失了。
4. 确认预期的状态出现了。
5. 抓取之后的录像、截图和同样的状态检查。

不要停在编译或测试。之后的结果必须来自一个正在运行的、打过补丁的应用。

## 结果

### 已确认

基线复现两次，打补丁后的构建解决两次。

- 把 operations 状态标为 verified。
- 链接该产物。
- 在源 preflight 之后，在源线程里发一条简洁的回复。
- 包含之前和之后的结果。
- 不开 pull request。

### 修复不足

症状在基线和打补丁后的构建上都出现。

- 把 operations 状态标为 reproduced but not fixed。
- 链接该产物，并说明它没有解决症状。
- 如果这次运行还没用过正常的 confirmed-repro 源更新，就发它。
- 不开竞争性的 pull request。

### 无法定论

基线没有复现，打补丁后的应用跑不起来，或者证据没有显示出那个有区分度的状态。

- 不要声称成功。
- 说明哪一半没能测量。
- 把结果留在 operations 线程或运行输出里。
- 除非有直接的问题需要回答，否则不要在源线程里发任何东西。

## 清理

停掉两个构建，按保留策略删除临时 profile 和抓取物，把仓库恢复到之前的状态，不要丢弃用户的工作。
