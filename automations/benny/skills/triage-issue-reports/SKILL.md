# 分诊问题报告

对一条 Slack 报告做分类，并在其来源话题串中发送一条有用的结论。只为明确的、新的 bug 创建跟踪器 issue。不要在这里复现或修复它。

加载自动化提供的外部 Benny 配置。如果配置缺失、格式错误或不完整，就停止，且不要发帖，也不要写入跟踪器。

## 硬性安全规则

- 来源频道和根话题串坐标是不可变的。
- 绝不要在来源频道发送根消息。
- 绝不要发到另一个频道、广播一条回复、发送私信，或另起一个替代话题串。
- 在任何跟踪器写入之前，以及在发送结论的紧前面，对来源父消息做预检。
- 如果父消息缺失、已删除、无法访问或不确定，就停止，且不做任何写入。
- 发送一条有实质内容的结论。不要叙述进度。
- 协调者是唯一向 Slack 发帖的一方。
- 被委派的工作者只返回发现。它们必须是只读的，并且不接收 Slack 凭据或写操作。
- 每条子提示都必须禁止 `SendSlackMessage`、`PostToSlack`、`chat.postMessage`，以及其他每一种 Slack 写操作。
- 如果工作者隔离无法强制这些限制，就在协调者中完成这项工作。
- 绝不要创建一条无法链回来源话题串的 issue。
- 宁可没有工单，也不要一条猜测出来的或重复的工单。
- 对来源坐标应用 pstack 的 `principle-separate-before-serializing-shared-state`。
- 对最终结论应用 pstack 的 `principle-minimize-reader-load` 和 `unslop` skill。

## 1. 冻结来源坐标

在制定工作清单或委派之前：

1. 从触发信息中读取 `source_channel_id`。
2. 要求它等于已配置的来源频道。
3. 若存在 `trigger.thread_ts`，把 `SOURCE_THREAD_TS` 设为它。否则使用 `trigger.ts`。
4. 要求 `SOURCE_THREAD_TS` 非空。
5. 把 `SOURCE_CHANNEL_ID` 和 `SOURCE_THREAD_TS` 存为不可变的值。
6. 阅读该话题串，并验证它的根恰好具有这些坐标。
7. 获取一个稳定的来源永久链接。

之后每一次来源读取和发送，都必须使用这些存下来的值。绝不要用回复时间戳或运维话题串时间戳替换它们。

## 2. 读完整份报告

在做决定之前，阅读根消息和当前的回复。

记下：

- 报告人的措辞
- 若有的话：产品版本、应用构建、环境和平台
- 预期行为
- 观察到的行为
- 频率和触发条件
- 错误文本或堆栈特征
- 已有的 issue、提交或 pull request 链接
- 任何表明已经有人在修复它的明确陈述

检查每一个相关附件。

- 以完整的可用分辨率阅读截图。
- 审阅视频，寻找把正确行为与损坏行为分开的那次状态转换。
- 阅读日志、追踪和崩溃文本，寻找具体特征。
- 如果媒体需要专门审阅，使用只读的媒体工作者，并问一个范围很窄的问题。该工作者只返回发现。
- 如果某个附件无法阅读，在结论里说明。不要编造它显示的内容。

在向报告人索取更多信息之前，先使用话题串里已经有的证据。

## 3. 路由之前先追溯成因

在选择负责人或目的地之前，做一次限定范围的源码与历史检查。使用 pstack 的 `how` skill，从所报告的操作追溯到观察到的结果。当报告看起来像回归，或触及防御性代码时，使用 `why`。

1. 从所报告的操作到观察到的结果，找出可能的代码路径。
2. 检查可见症状属于这条代码路径，还是属于它下面的某个依赖。
3. 当报告看起来像回归时，检查最近的改动。
4. 检查是否已有已合并提交或打开的 pull request 在处理同一个症状。
5. 把已确认的事实和假设分开。

这一轮不需要完整的根因。它必须足够有力，以免把一个可见症状路由给错误的负责人。

如果无法阅读仓库，不要猜测代码负责人。继续做保守的分类，并说明成因追溯不可用。

## 4. 分类

选择一个类别。

### Bug

有东西违反了本应有的行为。例子包括错误的输出、损坏的状态、报错、崩溃、挂起、静默空操作，或回归。

### 性能

报告描述的是可测量的变慢、内存过量、耗电、卡顿，或其他资源问题。把它当作 bug 处理，但保留测量数据和性能剖析。

### 功能请求

当前行为看起来是有意为之，而报告人想要另一种行为或交互方式。

### 提问或反馈

报告在问某件事如何工作，在没有具体缺陷的情况下表达一种偏好，或给出一般性反馈。

### 改派

成因追溯表明，另一个已配置的目的地负责这个问题。

当 bug 和功能请求的界线不清楚时，不要建单。这一条结论可以问一个聚焦的问题，并使用 `other` 标记。

## 5. 应用已配置的路由

从 `routing.map_path` 读取可选的路由映射。

- 按已确认的产品区域、代码路径或错误特征来匹配。
- 当成因追溯指向别处时，仅凭可见症状是不够的。
- 如果没有路由匹配，就说明负责人不清楚。不要猜测。
- 不要跨频道转发。在来源话题串里告诉报告人该把问题带到哪里。

负责人提醒默认关闭。只有以下条件全部成立时才允许提醒：

1. 路由映射明确写出了该负责人。
2. 配置允许这种提醒。
3. 该项是需要负责人给出意见的功能请求，或者近期历史以有力证据指出了可能的回归作者。
4. 该负责人不是一个宽泛的值班组。

其他任何情况都不提醒。

## 6. 使用问题跟踪器适配器

跟踪器是一个适配器，不是指定的供应商。Linear 适配器是一个有效示例。GitHub Issues 适配器或其他跟踪器可以实现同一份契约。

已配置的适配器必须提供：

- 按文本、状态、标签、来源 URL 和日期范围搜索 issue
- 读取一条 issue 及其链接
- 创建一条带有标题、正文、状态、标签和来源 URL 的 issue
- 更新已有 issue，且不替换无关字段
- 添加来源链接和一条复发说明
- 如果 Slack 交接失败，取消、关闭或删除本次运行创建的 issue

如果某项必需操作不可用，对该次写入失败即关闭。

在运行时解析已配置的团队、项目、状态和标签。不要编造 ID、创建标签、指派负责人或设置优先级，除非配置明确要求这样做。

## 7. 去重

始终检查这条来源永久链接是否已经链到某条跟踪器 issue，或先前的一条分诊回复。如果是，不要发帖，也不要创建重复项。

对于 bug 和性能报告，用下面这些条件搜索跟踪器：

- 精确的错误特征或崩溃特征
- 产品区域
- 触发条件
- 症状
- 版本或日期窗口
- 疑似的回归提交
- 来源永久链接

选择一种结果：

- 确信重复：特征相同，或者区域、触发条件和症状都相同，或者有已确认的共同成因。
- 可能相关：共同成因说得通，但还没有证实。
- 弱相似：相似只停留在表面。
- 无匹配。

对于确信重复，用来源永久链接和一条简短的复发说明更新已有 issue。不要重新打开它、改它的标签或重新指派它，除非配置如此说明。

对于可能的匹配，在结论里把它作为不确定项链接出来，并且什么都不创建。

一条关闭已久的 issue 是回归线索，不会自动成为一条仍然有效的重复项。

## 8. 决定是否创建

只有以下各项全部为真时才创建：

1. 分类是 bug 或性能。
2. 行为明显是坏的。
3. 问题仍然存在，或者还不知道它已经被修复。
4. 去重没有找到确信的、或说得通且仍然有效的匹配。
5. 来源父消息和永久链接通过了预检。
6. 跟踪器的目标字段已经解析出来。
7. 如果结论没能发出，适配器能够补偿。

绝不要为功能请求、提问、反馈项、改派、可能的重复、确信重复，或已经修复的问题创建。

新 issue 必须自成一体：

- 直白的标题，点明区域和症状
- 报告人的原话
- 预期行为和观察到的行为
- 版本和环境，或者 `unknown`
- 触发条件和频率
- 来源话题串的永久链接
- 简短的成因追溯发现，并把假设标明为假设
- 在支持时，内嵌截图或有代表性的视频帧
- 其余产物的链接
- 已配置的入库状态和标签

不要把猜测的根因写进标题。

## 9. 发送一条结论

重新做一次来源父消息预检。然后用 `channel=SOURCE_CHANNEL_ID` 和 `thread_ts=SOURCE_THREAD_TS` 发送恰好一条回复。

绝不要在 `thread_ts` 为空时，调用来源频道的发帖操作。

回复保持简短：

- 先写结果。
- 若有已有的或新建的跟踪器 issue，附上链接。
- 需要时说明改派，或一个缺失的事实。
- 最多包含一次允许的负责人提醒。
- 以恰好一行标记结束。

标记契约：

```text
[benny:bug]
[benny:bug] tracker=https://tracker.example/issue/123
[benny:performance]
[benny:performance] tracker=https://tracker.example/issue/123
[benny:other]
```

只使用已配置的标记字符串。复现自动化只在这个标记来自本来源话题串中、已配置的分诊身份时，才信任它。

发送之后，阅读同一个来源话题串，并验证结论出现在 `SOURCE_THREAD_TS` 之下。如果没有，绝不要到根上重试。

如果本次运行创建了跟踪器 issue，而结论没有落地，就使用适配器的补偿操作。验证该 issue 已被取消、关闭或删除。如果无法验证补偿是否完成，只在自动化运行输出中报告这次失败。

## 10. 观察一个跟进窗口

在已配置的跟进窗口内观察来源话题串，然后停止。

- 只回答直接向分诊身份提出的问题。
- 在安全时，把具体的更正应用到跟踪器 issue。
- 不要在同一次运行中发出第二个标记。
- 不要介入人工协调和旁支闲聊。
- 如果有人要求自动化停止，就提前停止。

不要把这个窗口延长超过一次。一条新报告应当启动一次新的运行。
