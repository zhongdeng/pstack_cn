# 分诊问题报告

对一条 Slack 报告做分类，并在它的来源线程里发一条有用的结论。只有明确、全新的 bug 才创建 tracker 工单。不要在这里复现或修复它。

加载自动化提供的外部 Benny 配置。如果配置缺失、格式错误或不完整，直接停下，不发帖也不写 tracker。

## 硬性安全规则

- 来源频道和根线程坐标不可变。
- 绝不在来源频道发根消息。
- 绝不发到别的频道、广播回复、发私信，或另起一个替代线程。
- 任何 tracker 写入之前、以及发结论之前，都要对来源父消息做一次预检。
- 如果父消息缺失、被删除、无法访问或状态不确定，停下，不做任何写入。
- 只发一条有实质内容的结论。不要直播进度。
- 协调者是唯一往 Slack 发帖的人。
- 被委派的 worker 只返回发现。它们必须只读，不能拿到 Slack 凭据或写操作。
- 每个子提示都必须禁止 `SendSlackMessage`、`PostToSlack`、`chat.postMessage` 以及其他一切 Slack 写入。
- 如果 worker 隔离无法强制这些限制，就在协调者里做这件事。
- 绝不创建无法链回来源线程的工单。
- 宁可不开工单，也不要猜一个或开重复的工单。
- 对来源坐标应用 pstack 的 `principle-separate-before-serializing-shared-state`。
- 对最终结论应用 pstack 的 `principle-minimize-reader-load` 和 `unslop` 技能。

## 1. 冻结来源坐标

在列工作清单或委派之前：

1. 从触发事件里读 `source_channel_id`。
2. 要求它等于配置的来源频道。
3. 有 `trigger.thread_ts` 时，把 `SOURCE_THREAD_TS` 设为它。否则用 `trigger.ts`。
4. 要求 `SOURCE_THREAD_TS` 非空。
5. 把 `SOURCE_CHANNEL_ID` 和 `SOURCE_THREAD_TS` 存为不可变值。
6. 读这个线程，确认它的根消息坐标正好是这两个值。
7. 取一个稳定的来源 permalink。

之后每一次来源读取和发帖都必须用这些存下来的值。绝不用某条回复的时间戳或运维线程的时间戳替换它们。

## 2. 读完整份报告

做判断之前先读根消息和当前回复。

记录：

- 报告人的原话
- 产品版本、app build、环境和平台（如果有）
- 预期行为
- 实际观察到的行为
- 频率和触发条件
- 错误文本或堆栈特征
- 已有的 issue、commit 或 pull request 链接
- 任何明确说明已经有人在修的话

检查每一个相关附件。

- 以完整可用的分辨率看截图。
- 看视频里区分正确和错误行为的那次状态转换。
- 读日志、trace 和崩溃文本，找具体特征。
- 如果媒体需要专人看，用一个只读的媒体 worker，问一个窄问题。worker 只返回发现。
- 如果某个附件读不了，在结论里说明。不要编造它显示了什么。

先用在线程里已有的证据，再去找报告人要更多。

## 3. 分流之前先追原因

在选负责人或目的地之前，做一轮有边界的源码和历史排查。用 pstack 的 `how` 技能追从报告的动作到观察到的结果这条路径。报告看起来像回归或碰到防御性代码时，用 `why`。

1. 从报告的动作到观察到的结果，找出可能的代码路径。
2. 检查可见症状属于这条代码路径，还是它下面的某个依赖。
3. 报告看起来像回归时，检查最近的改动。
4. 检查是否已有合并的 commit 或开着的 pull request 处理了同一个症状。
5. 把确认的事实和假设分开。

这一轮不需要完整的根因。它只要强到足以避免把可见症状分给错误的负责人。

如果仓库读不了，不要猜代码负责人。继续做保守的分类，并说明原因追踪不可用。

## 4. 分类

选一个类别。

### Bug

有东西违反了预期行为。例子包括输出错误、状态损坏、报错、崩溃、卡死、静默无操作或回归。

### 性能

报告描述了可测量的变慢、内存过高、耗电、卡顿或其他资源问题。按 bug 处理，但要保留测量数据和 profile。

### 功能请求

当前行为看起来是有意的，而报告人想要另一种行为或交互方式。

### 问题或反馈

报告在问某个东西怎么工作，表达一个偏好但没有具体缺陷，或给出一般性反馈。

### 改派

原因追踪显示另一个配置好的目的地拥有这个问题。

bug 和功能之间的界线不清楚时，不要开工单。那一条结论可以问一个聚焦的问题，并用 `other` 标记。

## 5. 应用配置好的分流

从 `routing.map_path` 读可选的分流映射。

- 按确认的产品区域、代码路径或错误特征匹配。
- 原因追踪指向别处时，光有可见症状不够。
- 没有匹配的路由时，说负责人不清楚。不要猜。
- 不要跨频道发帖。在来源线程里告诉报告人该把问题带到哪里。

默认不 ping 负责人。只有以下条件全部成立时才允许 ping：

1. 分流映射明确点名了负责人。
2. 配置允许这类 ping。
3. 这一项是需要负责人输入的功能请求，或者最近的历史以强证据指出了可能的回归作者。
4. 负责人不是一个宽泛的 on-call 组。

其他情况一律不 ping。

## 6. 使用 issue-tracker 适配器

tracker 是适配器，不是必须用某个厂商。Linear 适配器是一个有效例子。GitHub Issues 适配器或其他 tracker 也可以实现同一份契约。

配置好的适配器必须提供：

- 按文本、状态、label、来源 URL 和日期范围搜索 issue
- 读一个 issue 及其链接
- 创建带标题、正文、状态、label 和来源 URL 的 issue
- 更新已有 issue，且不替换无关字段
- 添加来源链接和复发说明
- 如果 Slack 交接失败，取消、关闭或删除本次运行创建的 issue

如果某个必需操作不可用，那次写入就失败即关闭。

在运行时解析配置好的 team、project、status 和 label。不要编造 ID、创建 label、指派负责人或设优先级，除非配置明确要求。

## 7. 去重

始终检查这个来源 permalink 是否已经链到某个 tracker issue 或之前的分诊回复。如果是，不发帖也不创建重复项。

对 bug 和性能报告，用以下条件搜索 tracker：

- 精确的错误或崩溃特征
- 产品区域
- 触发条件
- 症状
- 版本或日期窗口
- 疑似回归 commit
- 来源 permalink

选一个结果：

- 确信重复：同一特征，或同一区域、触发条件和症状，或已确认的共同原因。
- 可能相关：共同原因说得通但没被证实。
- 弱相似：只是表面相似。
- 无匹配。

对确信重复，用来源 permalink 和一句简短的复发说明更新已有 issue。除非配置要求，不要重开、改 label 或重新指派。

对可能匹配，在结论里作为不确定项链接它，不创建任何东西。

一个关闭很久的 issue 是回归线索，不自动算作现存的重复项。

## 8. 决定是否创建

只有以下条件全部成立才创建：

1. 分类是 bug 或性能。
2. 行为明显是坏的。
3. 问题仍然存在，或不知道已修复。
4. 去重没有找到确信或可能的现存匹配。
5. 来源父消息和 permalink 通过了预检。
6. tracker 目标字段已解析。
7. 结论发帖失败时适配器能补偿。

功能请求、问题、反馈项、改派、可能重复、确信重复或已修复的问题，一律不创建。

新 issue 必须自包含：

- 平实的标题，点明区域和症状
- 报告人的原话
- 预期行为和观察到的行为
- 版本和环境，或 `unknown`
- 触发条件和频率
- 来源线程 permalink
- 简短的原因追踪发现，假设要标为假设
- 支持时内嵌截图或代表性视频帧
- 其余产物的链接
- 配置好的 intake 状态和 label

不要把猜的根因写进标题。

## 9. 发一条结论

重新对来源父消息做一次预检。然后用 `channel=SOURCE_CHANNEL_ID` 和 `thread_ts=SOURCE_THREAD_TS` 只发一条回复。

绝不在 `thread_ts` 为空时调用来源频道发帖操作。

回复要短：

- 先给结果。
- 有 tracker issue 时，链接已有或新建的那个。
- 需要时提一下改派或一个缺失的事实。
- 最多包含一个允许的负责人 ping。
- 以正好一行标记结尾。

标记契约：

```text
[benny:bug]
[benny:bug] tracker=https://tracker.example/issue/123
[benny:performance]
[benny:performance] tracker=https://tracker.example/issue/123
[benny:other]
```

只用配置好的标记字符串。复现自动化只在这个来源线程里、来自配置好的分诊身份时才信任这个标记。

发完之后，读同一个来源线程，确认结论出现在 `SOURCE_THREAD_TS` 下面。如果没有，绝不在根消息重试。

如果本次运行创建了 tracker issue 而结论没发出去，用适配器的补偿操作。确认 issue 已取消、关闭或删除。如果补偿无法确认，只在自动化运行输出里报告失败。

## 10. 观察一个跟进窗口

在配置好的跟进窗口里观察来源线程，然后停下。

- 只回答直接问分诊身份的问题。
- 安全时对 tracker issue 做具体更正。
- 同一次运行里不要发第二个标记。
- 不掺和人的协调和闲聊。
- 有人要求自动化停下时提前结束。

窗口最多延长一次。新报告应该开一次新的运行。
